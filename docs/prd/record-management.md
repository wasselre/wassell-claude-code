**Auto-stamp actual follow-up time (new 2026-05-31).** The moment a sales rep records a call outcome — picks any value in the Call section's `call_result` (نتيجة المكالمة) dropdown — the Basic Info `actual_datetime` (موعد المتابعة الفعلي) field is filled with the current local date+time, so reps don't have to set it by hand. ## Project models — unit rollups (our_projects 2026-05-23, all_projects 2026-06-01; PERSISTED 2026-06-15)
Two models carry eleven read-only fields whose values are aggregated live from `units` rows:
- **`our_projects`** has a `project` lookup pointing to `all_projects`; its units are those that share that `all_projects` id. Path: `our_projects.data.project → all_projects.id ← units.data.project_id`.
- **`all_projects`** (added 2026-06-01) IS the master that units point at, so its units are matched **directly**: `units.data.project_id === all_projects.id` (no lookup hop). The eleven fields live in its `تفاصيل المشروع` / Project Details section.

Both share the same `computed_kind` recipes — they differ only in how matching units are found (`unitsForOurProject` vs `unitsForAllProject` in `src/lib/ourProjectsRollup.ts`).

The eleven computed fields on **our_projects**, each marked `is_computed: true` on the model schema with a matching `computed_kind`:

| Field slug              | Kind                      | Type     | What it shows                                                                 |
|-------------------------|---------------------------|----------|-------------------------------------------------------------------------------|
| `total_units`           | `units_count`             | number   | COUNT of all units linked to the same all_projects record                     |
| `units_available`       | `units_available_count`   | number   | COUNT where `unit_status` is "available" (English value or متاحة / متاح)      |
| `sold_units`            | `units_sold_count`        | number   | COUNT where `unit_status` is "sold" (English value or مباعة / مباع / مبيع)    |
| `units_reserved`        | `units_reserved_count`    | number   | COUNT where `unit_status` is "reserved" (English value or محجوزة / محجوز)     |
| `price_range`           | `price_range`             | range    | `{ min, max }` of unit `price`                                                |
| `area_range`            | `area_range`              | range    | `{ min, max }` of unit `area_sqm`                                             |
| `bedroom_range`         | `bedroom_range`           | range    | `{ min, max }` of unit `bedrooms`                                             |
| `bathroom_range`        | `bathroom_range`          | range    | `{ min, max }` of unit `bathrooms`                                            |
| `min_price_per_meter`   | `min_price_per_meter`     | currency | MIN of `price / area_sqm`, skipping units with `area_sqm ≤ 0`                 |
| `max_price_per_meter`   | `max_price_per_meter`     | currency | MAX of `price / area_sqm`, skipping units with `area_sqm ≤ 0`                 |

On **all_projects**, the same eleven kinds map to these production slugs (Project Details section): `unit_count`→`units_count`, `available_units`→`units_available_count`, `sold_units`→`units_sold_count`, `reserved_units`→`units_reserved_count`, `price_range`→`price_range`, `area_range`→`area_range`, `bedroom_range`→`bedroom_range`, `bathroom_range`→`bathroom_range`, `avg_min_price_per_m2`→`min_price_per_meter`, `avg_max_price_per_m2`→`max_price_per_meter`, `avg_price_per_m2`→`avg_price_per_meter`. The three per-meter fields were originally `formula` type and were converted to `currency` — a per-record formula can't aggregate across child units. (The engine writes by `field.name`, so slugs don't need to match the kind string.)

**Behaviors:**
- **Stored, trigger-maintained (2026-06-15 — was: live, never stored).** The values are now PERSISTED in `records.data`. A `BEFORE INSERT/UPDATE` trigger on the all_projects rows (`records_fill_project_rollups` → `recalc_project_rollups_data`, SECURITY DEFINER so it counts ALL units regardless of the writer's RLS) recomputes them inline on every write; an `AFTER INSERT/UPDATE/DELETE` trigger on `units` (`records_touch_project_on_unit_change`) touches the linked project(s) — incl. the unit-moved-between-projects case (recompute both) — so any unit change recomputes them automatically and Realtime pushes the new project row to the SPA. `saveRecord` **no longer strips** them (the BEFORE-fill trigger refills authoritatively, so a user edit can't wipe them). Schema flags renamed `is_computed→is_rollup` / `computed_kind→rollup_kind` / `+read_only` (the app dual-reads both during rollout). Because they're stored, `v_all_projects`, the AI sales agent, BI, and every `records.data` reader now see real values. The JS fallback (`applyProjectRollups` / `useRolledUpRecords` / `rollupRecordForMirror` / the copywriter port) was DELETED in Phase 2 (2026-06-15) — the DB trigger is now the only implementation; every consumer reads the stored value. Migration: `supabase/migrations/2026-06-15_persist_project_rollups.sql`. The SQL aggregation mirrors the JS semantics exactly (verified equal to live values for all 11 projects-with-units before cutover).
- **Live updates without reload.** The list view consumes records through `useRolledUpRecordList`, which subscribes to BOTH `records[our_projects.id]` AND `records[units.id]` — flipping a unit's `unit_status` instantly updates the matching project row's counts. The form consumes through `useRolledUpRecord` — opens fresh with live values; mid-edit unit changes refresh on next form mount (acceptable v1 tradeoff for state isolation between user form edits and external updates).
- **Read-only in the form + table.** `lib/permissions.ts` `isComputedField` now returns true for any `is_computed: true` field, alongside the type-level computed kinds (formula / mirror / auto_id / section_mirror). The form input is disabled, the table cell renders without inline-edit.
- **Status matching is bilingual + substring-tolerant.** A unit with `unit_status` of "available" / "Available" / "متاحة" / "متاح" all count toward `units_available`. Lets admins rename the dropdown option labels without breaking the rollups.
- **Per-meter rollups skip zero-area units.** A unit with `area_sqm = 0` is still counted in `units_count` and contributes to `area_range` (the 0 shows as the min), but it's excluded from `min/max/avg_price_per_meter` to prevent Infinity poisoning.
- **Cross-project isolation.** A unit whose `project_id` doesn't match the our_projects record's `project` field is excluded — verified.
- **Mirrored rollups resolve live (2026-06-01).** A `mirror` / `section_mirror` field pointing at a rollup field reads the source record *rolled up* (via `rollupRecordForMirror`), so e.g. an Our Projects record mirroring All Projects' Project Details shows the computed counts/ranges instead of the empty stored slot. Applies to the form, table cells, cards, and maps. Excluded: the bulk ad-hoc-filter path (performance) — filtering by a mirrored rollup value is unsupported.

Implementation (until Phase 2, 2026-06-15) lived in `src/lib/ourProjectsRollup.ts` + `src/hooks/useRolledUpRecords.ts` — both DELETED once the rollups were persisted; the SQL trigger `recalc_project_rollups_data` is now the source and consumers read the stored value. Wired into `RecordListPage` and `RecordFormPage`. (Save-time strip was REMOVED 2026-06-15 — the rollups are persisted now and the DB trigger is authoritative; see the "Stored, trigger-maintained" behavior above.) The live migration that adds the schema flags to existing deployments is `supabase/migrations/2026-05-23_our_projects_unit_rollups.sql` — also adds `bedrooms` + `bathrooms` to units and the `project` lookup to our_projects if either is missing. Idempotent.

The all_projects rollups are wired the same way: the engine was generalized so `applyProjectRollups(record, model, units)` dispatches by model name (`matchingUnitsForProject` → `unitsForOurProject` for our_projects, the new `unitsForAllProject` for all_projects); `applyOurProjectsRollups` remains as a thin back-compat wrapper. The hooks gate on `modelHasUnitRollups(model)` (true for both project models) instead of a literal `our_projects` check. The read-only (`permissions.ts` `isComputedField`) and save-strip (`appStore.saveRecord`) paths already keyed off the generic `is_computed` flag, so they needed no change. Live migration `supabase/migrations/2026-06-01_all_projects_unit_rollups.sql` stamps `is_computed`/`computed_kind` on the eleven all_projects fields and converts the three `avg_*_per_m2` fields from `formula` to `currency` — idempotent. The seed `all_projects` model is intentionally left unchanged (it has drifted far from production; the engine works off whatever schema carries the flags).

**Limitations:**
- Field slugs are hardcoded conventions (`project`, `project_id`, `bedrooms`, `bathrooms`, `area_sqm`, `price`, `unit_status`). Renaming them via the Builder would silently break the rollups. No protection yet.
- No general-purpose rollup field type — the eleven kinds are hardcoded by `OurProjectsComputedKind`. Adding a new kind requires a code change in `ourProjectsRollup.ts`. A generic rollup field type is future work.
- **Dispatch is by model NAME** (`our_projects` / `all_projects`). Renaming either model away from those slugs disables its rollups. Field slugs within a model can be renamed freely (the engine writes to `field.name`).
- The form's `formData` is initialized from the rolled-up record at mount and only re-syncs on navigation. If a unit changes while the form is open, the rolled-up cells in the open form stay stale until the user navigates away and back. The list view IS live.
- Frozen-model interaction is untested. our_projects is not currently frozen; if it were, the save-strip path would need to verify the dispatcher RPC also drops computed fields.

### all_projects `unit_types` — conditional units-derived field (new 2026-06-18)
`all_projects.unit_types` (multiselect, "Unit Types" / "أنواع الوحدات") behaves differently from the eleven numeric/range rollups above — it is a CONDITIONAL units-derived field, not an unconditional rollup:
- **Project WITH ≥1 linked unit** → `unit_types` is auto-calculated from the distinct `unit_type` values of those units (deduplicated) and rendered **read-only** in the form. Units are the source of truth, so a manual value is replaced by the derived set.
- **Project WITHOUT linked units** → `unit_types` stays **manually editable** and the user-entered value is preserved (until units are linked).

Mechanism: the field carries `auto_from_units: true` (NOT `is_rollup` — that would force read-only everywhere and exclude it from imports). The same `recalc_project_rollups_data` trigger function emits a `unit_types` key into its patch ONLY when the project has units; with no units the key is omitted so the BEFORE-fill trigger's `NEW.data || patch` leaves the manual value intact. The form (`SectionBlock.tsx`) decides read-only per-record: it renders the `auto_from_units` field read-only when the project has linked units (checked via the stored `units_count` rollup on the record, with a fallback to a live count of units whose project lookup points at this record). Even if some other write path edits the field while units exist, the trigger re-derives authoritatively on save — the UI read-only is a UX guard, the trigger is the integrity guarantee.

## Market Listings reference dataset (`market_listings`, new 2026-06-27)
A market-intelligence reference model holding ~46,315 external Aqar for-sale ads (Riyadh; villas / apartments / floors / land / buildings / rest-houses, scraped externally — `source = aqar`). It is a single model with 6 sections (Listing / Property Details / Location / Media / Advertiser / Tracking) and an `external_id` dedup key, kept deliberately OUT of the curated project pipeline (`all_projects` / `our_projects` / `targeted_projects`). It is used for market intelligence and as the Sales Assistant's third matching source (see [project-matching-assistant.md](project-matching-assistant.md)). Two things make it different from a normal model in this PRD's terms:

- **It is a lazy-loaded model.** Because 46k rows ≈ 69 MB would ~8× everyone's boot, its rows are excluded from the boot load and paged in on demand — the list page shows a server-driven **"Load more"** instead of a client page-size selector, and the record form fetches one row by id. Full mechanism + v1 limits (Excel export / dashboards / map see only loaded rows; server search has no dropdown-label resolution or range filters) are in [data-storage.md](data-storage.md).
- **Its media fields render raw external URLs inline.** `main_image_url` (`image`), `image_urls` (`multi_image`), and `video_urls` (`multi_video`) store the raw Aqar CDN URLs rather than Drive `files.id`s — the image cells render an external URL via the long-standing legacy-URL shim, and the video field plays external links inline, including Cloudflare Stream `.m3u8` HLS manifests mapped to the Stream `/iframe` player (a native `<video>` can't play HLS in Chrome). See [model-builder.md](model-builder.md) for the field-type details. Its full field tree is in the auto-generated `docs/prd/models/market_listings.md`.
- **On-demand "التواصل مع المعلن" (contact advertiser) button (new 2026-07-01).** Aqar hides the advertiser's phone behind a login+Nafath-gated WhatsApp flow, but every listing carries an official **REGA advertising-license** link (`eservicesredp.rega.gov.sa/.../ElanDetails/<guid>`) — a **public government registry that discloses the advertiser by law** (no login, no cap). A `ContactAdvertiserPanel` on the listing form runs an on-demand lookup: it enqueues a `rega_lookup_jobs` row → the Fly worker drives a **Browserbase** session (residential Saudi IP) that opens the REGA license page **directly from the listing's stored `ad_license_url`** (present on ~92% of listings, already carrying the OfficesBroker/IndividualBroker path — so it skips the Aqar page entirely; it falls back to reading the Aqar page's anchor only when `ad_license_url` is missing), clears the REGA Cloudflare challenge, and scrapes the advertiser name + agent mobile → writes `advertiser_phone` (E.164) + `advertiser_name` (+ `rega_*` provenance + `rega_lookup_status`) onto the record. The SPA watches the record via Realtime and, when the phone lands, opens an in-app WhatsApp chat (`StartChatModal`) pre-filled with the Aqar listing link. The phone is cached, so a second click skips the scrape and opens the chat instantly; closed/unlicensed listings surface a "no license" state. This is the same enqueue→worker→Realtime pattern as the deck / data-migration queues (never holds an HTTP request open for the ~30–60 s scrape). Key files: `supabase/migrations/2026-07-01_rega_lookup_jobs_queue.sql`, `api/rega-lookup.ts`, `worker/src/runRegaLookupJob.ts` (+ the loop in `worker/src/index.ts`, self-disabled until `BROWSERBASE_API_KEY`/`BROWSERBASE_PROJECT_ID` are set), `src/lib/regaLookup/client.ts`, `src/lib/regaLookup/useContactAdvertiser.ts` (the shared cached→chat / enqueue→watch→auto-open state machine, extracted 2026-07-02), `src/pages/Records/components/ContactAdvertiserPanel.tsx` (record-form panel), `src/components/market/ContactAdvertiserButton.tsx` (compact button on Project Finder cards + client Options-tab cards, 2026-07-02 — see [project-matching-assistant.md](project-matching-assistant.md), [clients.md](clients.md)).
- **Listing quality score (new 2026-07-02).** Every listing carries a deterministic DB-computed **`quality_score` (0–100)**, an **A/B/C/D `quality_grade`** (dropdown with brand-colored chips, `show_in_table` → a column in the list view), and a read-only **`quality_breakdown`** table showing the five dimensions in Arabic. The formula lives in ONE place — the `market_listing_quality(data)` SQL function — and is recomputed by the same records BEFORE-trigger that derives the extras signals, so every scraper write re-scores the row (DB-authoritative; user edits can't drift it). Dimensions: completeness 30 (category-aware expected fields — land is judged on street width/frontage instead of bedrooms/bathrooms), media 25 (sqrt curve with category anchors: full credit at 10 photos for housing, 3 for land, 5 for buildings/istirahas; +5 for any video), description 20 (chars capped at 400/300/250 by category + feature count), trust 15 (REGA license + deed number + advertiser rating, where a missing rating or Aqar's default exactly-4.0 counts as neutral), freshness 10 (decay from 7 to 90 days since `source_last_updated_at`). Grades calibrated on the live corpus: A ≥92 (~18%), B 83–91 (~34%), C 70–82 (~33%), D <70 (~15%); per-category means converge (land 79.2 vs villas 81.4). `views_count` is deliberately excluded (demand ≠ quality). `quality_score`/`quality_grade` ride the slim store (`market_listings_summary` view + `SUMMARY_DATA_KEYS` — hard-synced pair) so the list chip + realtime updates work; the finder's candidates RPC returns full `data`, so matching consumers see the score for free. Retuning = replace the SQL function + touch-update the rows (no app deploy). Migration: `supabase/migrations/2026-07-02_market_listings_quality_score.sql` (and the input fields in `2026-07-01_market_listings_quality_signal_fields.sql` + `2026-07-02_market_listings_extras_signals.sql`).
- **Advertisers module (`advertisers`, new 2026-07-01).** A dedicated CRM model normalizing the scraped contacts — **one record per unique agent mobile** (a contact-level broker directory; a firm with two agent numbers = two contacts, each carrying the company `name` + `agent_name` + `fal_license` + `unified_number` + `broker_type` office/individual). `market_listings` gains an `advertiser` **lookup** field. On a successful REGA lookup the worker calls `rega_upsert_advertiser(...)` — **dedup by phone**, race-safe via a partial unique index on `records((data->>'phone')) WHERE model_id=<advertisers>` + an `EXCEPTION WHEN unique_violation` re-merge — then links the listing to the returned advertiser id. So the same broker is never duplicated across their many listings, and the Advertisers list is a working call-list (inline WhatsApp/call actions). `advertiser` rides in the market_listings slim store (SUMMARY_DATA_KEYS + summary view). Migration: `supabase/migrations/2026-07-01_advertisers_module.sql` (fixed model id `a1b2c3d4-…`, lookup add, index, upsert RPC, backfill). **Bidirectional navigation:** the advertiser record form shows a **«الإعلانات المرتبطة / Linked listings»** table (every market listing whose `advertiser` lookup points at it) via the now-generalized `RelatedRecordsPanel` (was clients-only → `recordId` + `targetModelName`); the listing's `ContactAdvertiserPanel` shows a **«عرض بطاقة المعلن / View advertiser record»** link back.

## What it is (in plain English)
This is where users actually enter and browse their data. Each model (Clients, Projects, Follow-Ups, etc.) has a list page where its records are shown as a table or as cards, and a form page for creating or editing one record. The list has filtering, sorting, searching, and bulk import/export. The form dynamically renders the fields defined in the Model Builder, including special types like lookups, multi-select, and the section selector.

## Why it exists
Once models exist, the real day-to-day work of the business happens here — salespeople log calls, property researchers add listings, managers review clients. This is the primary UI of the CRM.

## Key behaviors
- URL structure: `/model/:modelName` (list), `/model/:modelName/new` (create), `/model/:modelName/:recordId` (edit).
- **List view modes:** Table, Card, and Maps. User toggles between them; preference is per-model (persisted as `view_mode_<modelName>` in localStorage).
  - **Table view** shows columns driven by the active **saved view** (if any), or falls back to every field marked `show_in_table` when no view is active.
  - **Card view** uses the model's `card_config` (title, subtitle, badge, shown fields) — any of which may be a local field or a `section_mirror` child resolved via `readExpandedValue`.
  - **Maps view (new 2026-04-23)** uses the model's `maps_config` (Google Maps JS API). Each record resolves to a pin from the configured location field — a `url`/`text` field, **a `mirror` field that surfaces one**, **or (new 2026-06-08) a `section_mirror` CHILD field that is itself a url/text field** (e.g. Our Projects pinning from All Projects' `project_location` surfaced through its بيانات المشروع section mirror, so the link needn't be stored locally) — via: (1) client-side URL parse for long Google Maps URLs, (2) Vercel edge function at `/api/resolve-maps-url` that follows short `maps.app.goo.gl` redirects server-side and extracts coords from the resolved URL — CORS-blocked in the browser but fine server-side, cached in localStorage under `wassell_maps_url_cache` forever so each unique URL only hits the edge function once, (3) optional manual lat/lng number fields as a backup. **Unplaced-records chip (new 2026-06-24):** any record that exhausts all three paths is surfaced in a persistent chip in the map's bottom-start corner — *"Records without a pinnable location (N)"* — that lists each unplaced record by its pin-label/popup-title name (click a name → opens that record to fix its link) and carries a **Retry** button. The chip shows **whenever ≥1 record is unplaced, regardless of how many pins succeeded** — previously this notice only rendered when EVERY pin failed (`resolved.length === 0`), so partial failures (e.g. a short `maps.app.goo.gl` link the edge function couldn't follow on that load — these transient failures are NOT cached, so they retry) vanished silently. Retry re-fires async resolution for the still-unplaced records via a `retry()` callback on `useResolvedLocations`. The centered "configure the location field" empty state now shows only when the map is truly empty (nothing resolved AND nothing unplaced). Pins are **labeled pills** showing the configured `pin_label_field_id` value (project name etc.) auto-sized to the text, on a charcoal-or-`pin_color_field_id`-resolved background; crowded pills auto-cluster into copper count circles via `@googlemaps/markerclusterer` and split on zoom-in. Click action is configurable per model: `popup` opens a custom Wassel-styled popup card (rendered as a `FLOAT_PANE` `<OverlayView>`, not Google's default InfoWindow) showing badge / title / subtitle / shown-fields with a copper "Open record" CTA, with all values formatted via the shared `formatFieldValue` resolver (lookups → target's display field, dropdowns → option labels, ranges → `min – max unit`, currency → `… ر.س`); `navigate` routes straight to the record detail. Full Google Maps style JSON drives the theme; a model that leaves `map_style_json` empty inherits the shared **Wassel-branded** map theme (cream geometry, chocolate labels, copper roads) via `resolveMapStyles()`, so every model's map matches the All Projects formatting by default — paste `[]` to opt back into Google's stock theme. Saved views, text search, and the advanced filter panel all apply upstream — Maps consumes `filteredRecords` so it shows exactly the same set Table would. Page size / page navigator are hidden while Maps is active. Shared `useResolvedLocations(model, records)` hook in `src/hooks/` is used by both MapsView and MapsBuilder so async resolutions fill in live without duplicate work. Requires `VITE_GOOGLE_MAPS_API_KEY`; missing key → bilingual setup state, no crash.
- **Saved views (table only):** Every model gets an implicit "Default view" (the `show_in_table` fallback), plus any number of saved views per user.
  - A view captures: selected columns + their order, sort field + direction, and filter conditions.
  - Views can be **private** (author only) or **shared** (visible to all users under "Shared Views"). Only the author can edit or delete a shared view.
  - Each user can mark at most one view per model as their **default** — it's selected automatically on first visit. The constraint is enforced in-store and by a partial unique index on `model_views`.
  - **Last-used view per (user, model)** is persisted in localStorage (`wassell_view_last_<modelId>_<userId>`), so refreshing the page keeps the same view active.
  - The ViewSelector dropdown above the table lists "My Views" and "Shared Views", plus a "Save as new view" action and per-row edit / delete / set-default controls.
  - When the active view changes, the filter conditions are applied to the record list (ANDed together, in addition to the text search), and the column order + sort are reset to what the view defines.
  - **Range-field conditions:** when a saved-view filter targets a range field (stored as `{ min?: number; max?: number }`), the editor shows a min/max bound picker next to the field dropdown; the chosen bound is stored in `condition.field_path` and used to resolve the scalar that the operator compares. `is_empty`/`is_not_empty` evaluate against the whole range value and don't require a bound. Conditions saved before this support (range field + no `field_path` + numeric operator) are silently skipped at evaluation time rather than filtering every record out.
- **Column-header sorting (table only):** Clicking a sortable column header sorts records by that column; clicking the same header again flips asc ↔ desc. The sort is **type-aware** — it sorts by the value the cell *displays*, not the raw stored value, via the shared `sortRecordsByFieldName` / `buildSortKey` in `src/lib/recordSort.ts`: `lookup` / `assignee` by the resolved record / user name (not the stored UUID, which is why these used to look randomly ordered), `dropdown` / `multiselect` by the option's **position in the model schema** (so Low → Medium → High and status pipelines order logically rather than alphabetically by slug), `number` / `currency` / `formula` numerically, `date` / `datetime` chronologically, `checkbox` unchecked-before-checked, `range` by its lower bound, `notes` by entry count, and everything else (`text`, `auto_id`, `email`, `phone`, `url`, …) as a natural locale string so `PRJ-2` sorts before `PRJ-10`. Blank / empty values always sort to the bottom in both directions. `mirror` columns are non-sortable (resolved per-render). Sort keys are precomputed once per row (decorate-sort) so a lookup/assignee sort doesn't re-resolve linked records on every comparison.
  - **Sorts the whole dataset, not just the page.** On the paginated surfaces (the Records list page and the Units tab) the sort state is **lifted out of `TableView` into the page**, which sorts the FULL filtered list *before* pagination and passes `TableView` the already-sorted page (`sortField` / `sortDir` / `onToggleSort` props put `TableView` into controlled mode). So clicking a header reorders every page, and page 1 shows the true global top — not just a reshuffle of the rows already on screen. (The read-only Related-Records tables receive the full unpaginated match set, so `TableView` keeps sorting those internally.)
  - **Works on computed / rollup columns.** Because the page rolls records up via `useRolledUpRecordList` *before* sorting, the computed values (e.g. All Projects' Project-Details fields — `unit_count`, `price_range`, `avg_price_per_m2`, …) are present in `record.data` at sort time and key by their declared field type just like stored values. Sorting by a computed column therefore orders correctly across the whole dataset.
  - The lifted sort is seeded from the active saved view's `sort_field_id` / `sort_direction` and resets to it when the view changes, but a header click does **not** rewrite the saved view (that still happens only through the View editor). It **does** drive prev/next nav context, so the record form's arrows follow whatever the user sorted by.
- **Advanced Filter panel (faceted):** A collapsible panel shows one chip per filterable field — above the toolbar in Table and Card modes, and as a floating overlay near the top of the map in Maps mode. Clicking a chip opens a type-aware popover:
  - `dropdown` / `multiselect` / `section_selector` / `lookup` / `assignee` → checkbox list of all possible values (with a search box when > 6 options). A small **Is / Is not** toggle at the top of the popover flips the match: **Is** (default) passes records where ANY picked value matches (OR); **Is not** passes records where NONE of the picked values match — records with no value for the field also pass under "Is not", since they have none of the picked values. Active "Is not" chips show their summary prefixed with `≠`. Mode is persisted alongside the picked values (`{ kind: 'values', values, mode: 'is' | 'is_not' }`).
  - `checkbox` → yes / no tri-state.
  - `date` / `datetime` → from/to range (inclusive; date-only inputs use end-of-day for "to").
  - `number` / `currency` → min/max range.
  - `text` / `textarea` / `email` / `phone` / `url` → "contains" text input.
  - `location` (cascade region → city → district) → a multi-select cascade picker: level tabs (Region / City / District) each with a searchable checkbox list; child candidates are filtered to the picked parent ids when a parent is selected, else all candidates show (capped at 60, search-narrowed). Selections are **OR within a level** and **AND across levels** (e.g. district ∈ {A, B} AND region = X). Matches the record's compound `{ region, city, district }` value in both single (scalar) and multi (id-array) storage shapes. The chip summarizes the deepest active level's names (e.g. "حي النرجس, حي الياسمين"). This is what restores location filtering on `market_listings` (whose region/city/district fields were consolidated into one `location` field on 2026-06-28) and enables it on any other cascade-`location` model.
  - `notes` and `range` → not exposed in the faceted panel (their structured value isn't meaningful with the existing filter kinds).
  - **Mirrored values are filterable too:** scalar `mirror` fields, mirrored sections (`is_mirrored`), and `section_mirror` fields each surface their linked-record value(s) as chips, resolved through the sibling lookup at filter time. A mirror chip borrows the value semantics (options / range / contains) of the source field it points at; mirrored-section & section_mirror children use a `<container>::<sourceField>` filter-state key. Multi-valued sibling lookups match-any for a scalar mirror, first-linked-record for mirrored sections / section_mirror. A mirror whose hop can't be resolved (or whose target type isn't filterable) is simply not offered as a chip.
  - Across different fields, records must pass all active filters (AND).
  - Active chips show a short summary (e.g. "Status: Active, Pending" or "≥ 100") and an X to clear; the panel header shows a count badge and a "Clear all" action.
  - State is persisted **per (user, model, view)** in localStorage (`wassell_adhoc_<modelId>_<userId>_<viewId|default>`). Switching views swaps the ad-hoc filter set; returning to a view restores its ad-hoc filters.
  - **Stale filters self-heal:** a filter keyed on a field that was later deleted in the Builder (or a model rebuilt with new field ids) has no chip to clear it. On load the stored state is pruned to only keys that still map to a live filterable field (`pruneAdhocFilters`), and the cleaned state is re-persisted — so a dead filter can no longer inflate the count badge or silently filter the list. The badge count itself also ignores any active entry with no live field.
  - Collapse/expand state is persisted per model (`wassell_adhoc_collapsed_v2_<modelId>` — the `v2` suffix resets any pre-existing stored state so the new collapsed-by-default takes effect).
  - **Maps overlay:** in Maps mode the same panel floats near the top-center of the map, collapsed by default and expanding downward. It renders on a **solid opaque-white** background — not the translucent fill used over the page background in Table/Card modes — so its label and chips stay readable over the map tiles. It shares Table mode's per-model collapse key, so collapse state follows the user across views.
  - Ad-hoc filters **layer on top of** the active view's saved conditions — view conditions apply first, then ad-hoc, then text search.
- **Record form** renders sections in order; each section renders its fields honoring `width` (half/full) for responsive layout.
- **Collapsible sections (new 2026-04-20):** each section header in the form is a button that toggles the section body open/closed. The initial state seeds from the model's `ModelSection.default_collapsed` flag (configured in the Builder via a chevron toggle in the section header). A per-section `useState` holds the current state, so expand/collapse is local and does not trigger form saves. Collapsed sections still participate in required-field validation — hiding fields does not skip them. Mirrored sections, base sections, and regular sections all behave identically.
- **In-section field groups (new 2026-04-20):** if a section defines `field_groups` (see model-builder.md), the record form splits its body into an ungrouped grid at the top followed by a collapsible mini-card per group. `SectionBlock` extracts its field-rendering logic into a local `renderFieldNodes` helper and runs it twice — once for ungrouped fields, then once per group inside a `FieldGroupBlock` (the collapsible wrapper with the group's label as a clickable header). Each group's collapse state is its own `useState` seeded from `default_collapsed`; collapsing or expanding a group does not affect the parent section's collapse. When the parent section is collapsed, all groups are hidden along with the grid. Groups are display-only — required-field validation still runs across every field, regardless of which group hides it. A field whose `field_group_id` points at a deleted/missing group falls back to ungrouped at render time.
- **Section selector** on the form controls which non-base sections are visible. Base sections always show. Custom (non-section) values on a `section_selector` field (see model-builder.md) render as normal multi-select options but are ignored by the visibility filter — they never hide or reveal a section.
- **Prev/next record navigation (new 2026-04-23):** on the record edit page, two arrow icon-buttons sit at the start of the top-right action cluster (before the optional PDF button, before Delete, before Save). Left chevron → previous record; right chevron → next record, with `rtl:rotate-180` so the direction reads correctly in both LTR and RTL. Arrows cycle through **the same filtered + sorted list the user was browsing in the list view**, not the entire model — `RecordListPage` publishes the ordered id list to `recordNavContext` in the store, and the form reads from it. Arrows disable at the first / last record (no wrap) and are hidden entirely on `/new`. If the form has unsaved edits, clicking prev or next triggers a `window.confirm` asking whether to discard — Cancel keeps the user on the record; OK navigates. When a user deep-links into a record without visiting the list first, the arrows fall back to the full model's insertion order. Column-header sorts now follow through to nav context too: the sort is lifted into `RecordListPage` (see "Column-header sorting") so `orderedFilteredRecords` — and therefore the published id list — reflects whatever column the user sorted by, not just the saved view's default sort.
- **Required fields** block save with inline error messages.
- **Lookup fields** open a searchable combobox of records from the lookup target model, showing the chosen display field. When the field has `is_multi: true`, the combobox becomes a multi-select chip list — picking a record adds it, the X on each chip removes it, and the search input stays open for adding more. Stored value becomes `string[]` (array of record IDs); table/card cells render it as a badge list. **Inline-create (new 2026-04-23):** when the user types a non-empty query into the combobox that doesn't exactly match an existing record's label (case-insensitive), a copper "Create: '<query>'" row appears at the bottom of the dropdown. Clicking it calls `saveRecord` on a freshly-minted record in the target model with the typed text written to the configured `lookup_display_field`, then auto-selects the new record — single-mode closes the dropdown with the new record as the value; multi-mode adds it as a chip and clears the search so the user can keep typing. Because the new record is a regular record write, it fires `auto_id` assignment, formula recompute, workflow `create` triggers, and Supabase sync just like a manually-created record, and it shows up immediately in its own list view. The empty "No results" placeholder is suppressed while the Create row is visible; when matches exist, the Create row renders below them with a top divider.
- **Mirror fields (new 2026-04-18):** render as a read-only, muted input whose value comes from hopping through a sibling lookup. Updates live as soon as the sibling lookup's selection changes. When the sibling lookup is multi-select, the mirror resolves to an array of values and renders as a chip list of resolved cells. In the table view, mirror columns cannot be sorted or inline-edited. In Excel export, mirrors are resolved; in import, they are excluded from the column mapping. Uses `src/lib/mirrorResolver.ts` for all surfaces.
- **Mirrored sections (new 2026-04-18):** a section flagged `is_mirrored` renders its fields from a linked record's source section (resolved at render time). Empty-states: if the sibling lookup on this record isn't set yet, the section shows "Select the linked record first"; if the linked record was deleted, it shows "The linked record has been deleted." When the section resolves OK, each field renders with the linked record's value — fully editable. Edits don't save into the current record; they're collected into `mirrorEdits[targetRecordId]` and, on form save, merged into the linked record's `data` and persisted via `saveRecord`. Required-field validation runs on the effective value (linked record data overlaid with pending mirror edits). Mirrored sections always render regardless of `section_selector` state. Uses `src/lib/sectionMirrorResolver.ts`.
- **Edit-at-source header button (new 2026-06-11):** when a model embeds another record's data through mirrors driven by a **single-select** sibling lookup — a `section_mirror` container field or a legacy `is_mirrored` section — the record-edit header shows a secondary "**Edit <lookup label>**" / "**تعديل <التسمية>**" button (SquarePen icon; one per distinct sibling lookup; only while that lookup holds a value; hidden on `/new` and for multi-select lookups). E.g. an Our Projects record (whose project-data sections are read-only mirrors of the linked All Projects record) shows **Edit Project / تعديل المشروع**. Clicking it opens the source record's own edit form carrying `state.backTo` = the current page's full URL (incl. `?tab=` params) — the same origin-preserving mechanism Units-tab row clicks use — so on the source form **both** the back arrow and the post-save exit return to the exact originating record, not the source model's list. Reaching the source model any other way (list, sidebar, deep link) passes no state, so its exits keep the default return-to-list behavior. The click goes through the unsaved-changes guard (`tryExit`): dirty local edits prompt Save & Exit / Discard & Exit / Cancel before navigating.
- **Notes fields (new 2026-04-18):** render as an append-only journal of entries — a composer at top (textarea + "Save note" button; ⌘/Ctrl+Enter submits) and a reverse-chronological list below. Each entry captures text, the `currentUserId` as author, and an ISO `created_at`. The form's usual Save must still be pressed to persist new entries; entries are never edited or deleted in this UI (no undo — edits would be adds). In the table, a notes column shows a compact "N notes · <latest preview>" summary and isn't inline-editable (click through to the record). In Excel export, entries serialize to a multi-line `[YYYY-MM-DD] text` block separated by `---`; import is skipped (no way to re-author history). Stored shape is `NoteEntry[]` (see `src/types/index.ts`).
- **Range fields (new 2026-04-18):** two number inputs side-by-side (min — max), configurable in the Builder with `range_min`, `range_max`, `range_step`, and optional `range_unit_ar` / `range_unit_en` (unit suffix shown inside each input and in the read-only cell). Stored shape is `{ min?: number; max?: number }` — either bound is optional so the user can express "≥ X" or "≤ Y". The table cell renders `min – max <unit>` (or the one-sided form). Import is skipped because the structured shape can't be parsed from a free-form cell.
- **Auto ID fields (new 2026-04-18):** render as a read-only copper-tinted badge in the record form (Fingerprint icon + the formatted string, e.g. `CLT-0001`). On create, the form submits no value for the field; `appStore.saveRecord` detects the `auto_id` type, calls `assignAutoIds`, writes the generated value into `record.data[slug]`, and bumps the counter on the model's schema JSONB — both state updates happen in one atomic `set(...)` transition. On edit, auto_ids are immutable: `assignAutoIds` skips fields that already have a value. Scoped counters (per-value-of-another-field) use a slugified scope key; IDs are NOT re-assigned when the scope field's value changes on an existing record. Table cells render as a mono-font copper string. Not importable from Excel, not exposed in the advanced filter panel.
- **Formula fields (new 2026-04-18):** render as a read-only strip (Calculator icon + live-computed value) in the record form. The form recomputes as the user edits other fields using `evaluateFormula(field.formula_expression, formData)` on every render — no save required to see the preview. On save, `appStore.saveRecord` calls `computeAllFormulas(model, data)` which topo-sorts formula fields by their `{slug}` dependencies, evaluates in order, and writes the result into `record.data[slug]` as a snapshot. Cached values are what filters, exports, dashboards, and table cells read (the engine never re-runs at render time in those surfaces). Error sentinels (`#DIV0`, `#REF`, `#ERR`, `#CYCLE`) render red in both form and table. **Known staleness tradeoff:** if a formula references a lookup-or-mirror-derived value and the source record changes later in another model, the stored formula value doesn't auto-refresh — it refreshes on the next save of this record. This matches Excel/Airtable behavior and keeps reads cheap. Not importable from Excel, not exposed in the advanced filter panel.
- **Dropdown / multi-select** show colored option chips. When the field defines `option_groups` (see model-builder.md), the menu organizes options into **collapsible group headers**: ungrouped options render first at the top, then each group header shows its label and option count (or `selected/total` for multi-select), collapsed by default. Clicking a header expands that group inline with indented option rows. On reopen, the group containing the currently selected value (or any selected values, for multi-select) auto-expands so the user sees their picks immediately. The query resets when the menu closes — single-select menus close on pick (query naturally resets for the next open), multi-select menus stay open after each pick and preserve the query so the user can keep selecting matches. In **table inline-edit mode (new 2026-04-22)**, these field types render the same picker popovers used in the record form via a new `compact` prop on `DropdownSelect` / `MultiSelect`, so inline editing has full option-group support, search, and color chips — not the trimmed native `<select>` and flat checkbox strip that v1 used. **Inline-create (new 2026-04-23):** regular `dropdown` and `multiselect` fields in the record form now show a copper "Create: '<query>'" row at the bottom of the menu when the user types a search that doesn't exactly match any existing option label (case-insensitive, either language). Clicking it calls a new optional `onCreateOption(label) → string` prop on `DropdownSelect` / `MultiSelect` — `DynamicField` implements it by appending a fresh `FieldOption` (uuid id + uuid value + both labels = the typed text + rotating palette color) to the field inside its owning model's schema and calling `saveModel`, then returning the new value so the picker selects it immediately (single-select closes; multi-select adds the chip, clears the query, and keeps focus for more creates). When `onCreateOption` is set the search input is always shown regardless of the 6-option threshold, so fields with few options aren't locked out. `section_selector` fields are intentionally excluded because their options encode section ids. Inline-created options are fully editable in the Builder afterward (rename, recolor, regroup) just like any other option.

Cells containing longer values open wider so the full text is visible while editing.

- **Legacy public-URL image values (fixed 2026-06-11):** an `image` / `multi_image` value that is a raw `http(s)` URL (pre-Files-system data, still written by the marketing/image flows — e.g. `all_projects.image_url`, `marketing_operations.raw_photo`) renders directly instead of being treated as a `files.id`. Table cells already had this shim; the FORM inputs now match — direct `<img>` thumb, click → the shared `LegacyImagePreview` lightbox, Replace writes a proper `files.id`. Deliberate posture: leave-and-render, no backfill.
- **Google Maps URL auto-shortening (new 2026-06-08):** when the value entered into a `url` field is a long Google Maps link (the `/place/…/@lat,lng,zoom/data=!3m…` share monsters), it is automatically collapsed to the compact `https://www.google.com/maps?q=<lat>,<lng>` form that opens the same pin. Fires **on blur** of the input, and **on paste** when the paste replaces the whole value (empty field or full text selection) — partial pastes defer to blur. The coordinate is taken (in priority order) from `!3d/!4d`, `@lat,lng`, or the `q` / `query` / `ll` query params, validated to a real lat/lng range (and never `0,0`), and the rewrite is kept only if it is actually shorter — so it is idempotent and never lengthens a link. Everything else is left untouched: non-Maps URLs, `/maps/dir/` multi-stop directions, opaque `maps.app.goo.gl` / `goo.gl/maps` share links, unparseable strings, and google-look-alike hosts. Same behavior on every URL-edit surface — `DynamicField` (record form), `MultiLinkFieldInput` rows, the inline `UrlInlineEditor` (on commit), and `url` columns inside `table` fields. Logic is the pure `shortenGoogleMapsUrl` helper in `src/lib/urlUtils.ts` (unit-tested in `src/lib/__tests__/urlUtils.test.ts`).

## User flows
1. **Browse records:** Click model in sidebar → `/model/:modelName` → see list. Switch between table/card view with toggle.
2. **Create record:** Click "+ New" → form opens with all sections → fill required fields → Save → redirected to the edit page for the new record.
3. **Edit record:** Click a row/card → form loads with existing values → change any field → Save.
3a. **Step through records:** From any record edit page, click the left or right chevron at the top of the header → jumps to the previous or next record in the same filter/sort order the user was browsing. If there are unsaved edits, the unsaved-changes guard appears first (see 3b).
3b. **Exit a dirty record:** Clicking the back arrow at the top-left of the record header — or the prev/next chevrons — while the form has unsaved edits opens an **Unsaved changes** modal with three options: **Save & Exit** (runs the same save flow as the toolbar Save button, then completes the navigation the user originally attempted — back to the list, previous record, or next record), **Discard & Exit** (navigates without saving — pending edits are dropped), and **Cancel** (closes the modal, the user stays on the current record with edits intact). A clean form (no edits since last save / mount) exits immediately with no prompt. If Save & Exit hits a validation or version-conflict failure, the underlying save toast surfaces and the modal stays open so the user can fix the problem.
3c. **View a project's units:** Open any record that is an All Projects record, or any record that references a project through a lookup (an appointment, our-project, project-details record, etc.) → a **Units** tab appears next to Form (and Client Details, if present). Click it → a table lists every unit linked to that project, with the same column / saved-view controls as the Units list page (click the view pill to switch or "Save as new view" to adjust columns), plus a **search box** with a **scope selector** — search across all fields (default) or pick one field, including a lookup or mirrored one (name, status, area, price, linked project, …; Arabic or ASCII digits both match). If the record links to more than one project, a chip switcher above the table flips between them. Open a unit (its "Open record" pencil) and the unit's **back button returns to this project's Units tab** (not the generic units list). The tab is deep-linkable via `?tab=units&project=<id>`.
3d. **Edit a mirrored record at its source:** On a record whose sections mirror a linked record read-only (e.g. an Our Projects record mirroring its All Projects project), click the **Edit <lookup label>** button in the header (e.g. "Edit Project / تعديل المشروع") → the linked record opens in its own edit form. Edit freely; **Save** or the **back arrow** both return to the exact originating record (same tab), where the mirrored sections immediately reflect the changes. Opening the source model normally (from its list) keeps the usual back-to-list behavior.
4. **Filter/search:** Top of list has a search box with a **scope selector** — search across all fields (default) or scope to one field, including a lookup or mirrored field (matches dropdown labels, lookup display values, and Arabic/ASCII digits). Plus (in table mode) an Advanced Filter panel with a chip per field and a ViewSelector for saved views.
5. **Faceted filter a field:** In the Advanced Filter panel, click any field chip → popover opens → select values / set a range / type a "contains" query → popover commits on change → table updates live. Click the X on an active chip to clear that one field, or "Clear all" in the panel header to clear every chip.
6. **Save a custom table view:** In table mode, click the view pill → "Save as new view" → pick columns (drag to reorder), set sort, add filter conditions, toggle "Share with team" and "Set as my default" → Save. The new view becomes active immediately.
7. **Switch views:** Click the view pill → pick any row under "My Views" or "Shared Views" → table re-renders with that view's columns/sort/filters. Pick "Default view" to fall back to `show_in_table`.
8. **Edit / delete a view:** Hover the row in the ViewSelector to reveal pencil / trash / star icons. Star toggles the per-user default.
9. **Section selector in action:** On a Follow-Ups record, user picks "Phone Call" in the section selector → only the "Phone Call Details" section becomes visible along with base sections.
10. **Import:** Click "Import" → modal accepts `.xlsx` → user maps each column to a model field → preview → confirm → records created.
11. **Export:** Click "Export" → downloads the current filtered list as `.xlsx`.
12. **Research PDF (special):** On a research record, click "Generate PDF" → downloads an Arabic-RTL PDF of the comparison table, flipped (projects as rows, fields as columns). The active comparison view scopes both the column set and the row set; default view = all linked projects × all included fields. Landscape A4 for 3+ field columns, portrait for fewer.
13. **Compare projects side-by-side:** Pick multiple projects in the `اسم المشروع` lookup → the `project_comparison` section renders a flipped comparison table (rows = projects, columns = fields). Cells are editable inline; changes sync back to the source All Projects record on save (subject to the container's `edit_mode` / `sync_mode`). A per-cell badge shows "Will sync" (writes to All Projects) or "Local" (stored as an override on this research record) while a change is pending. Use the **view selector** above the table to pick a saved comparison view, or click "Save as new view" to pick which columns + rows appear. The active view is remembered per research record.

## Data touched
- Reads/writes: `records.data` (JSONB per record, keyed by field slug).
- Reads: `models.schema` to know what fields to render.
- Reads: other `records` (for lookup fields).
- Reads/writes: `model_views` rows (per model, per user saved table configurations). Research-comparison views additionally populate the optional `project_ids` (row picker) and `research_container_field_id` (container scope) columns.
- Writes: Supabase storage (for file uploads).
- **Research comparison writes:** editing a cell in the flipped comparison table updates the linked `all_projects` record's `data` JSONB via `saveRecord`. Workflow triggers on `all_projects` update fire as expected. Required-field validation on synced edits runs before fan-out.

## Add an image to a record from Image Chats (added 2026-06-08; ⛔ removed 2026-07-22 with the Image Studio archive — commit `203f410`. Kept for reference; already-attached images keep rendering normally.)

Image Chats v2 can attach a generated image to any record. The **Add to Record** action on a chat image (the per-image ⋮ menu) opens a 4-step picker:
1. **Model** — only models with at least one `image` / `multi_image` / `file` / `multi_file` / `attachment` field are listed (`modelsWithImageTargets`; the custom-UI models `chats` / `ai_chats` / `image_chats` are excluded).
2. **Record** — a search box reusing the Table-View record search (`buildRecordSearchText` + `normalizeForSearch`, indexed once per model load) so the user finds a record by any human-readable value (dropdown labels, lookup display values, Arabic-Indic ↔ ASCII digits, etc.). Titles render via `resolveRecordTitle`.
3. **Field** — the compatible LOCAL image/file/attachment fields on the chosen record's model (`compatibleTargetFields` via `collectViewFields`; mirrored `section_mirror` children are out of scope in v1).
4. **Collision** — if the field already holds content: single `image`/`file` → **Replace** / Cancel; `multi_image`/`multi_file` → **Add** (append, deduped) / **Replace existing** / Cancel; `attachment` → **Add** (append `{type:'file', id}`, deduped).

On confirm the image is promoted to a Files-System `files.id` (reusing the cached id if the image was already promoted — see [files.md](files.md)) and written onto the field via `saveRecord` with `expectedVersion` (optimistic concurrency; `saved` / `queued` / `conflict` are surfaced as toasts). Lives in `src/pages/ImageChats/components/AddImageToRecordModal.tsx` + `src/lib/assets/recordTargets.ts`. See [image-chats.md](image-chats.md).

## Open questions / known limitations
- No record history / audit log. (The unified activity log captures CRUD events with diffs but not field-level versioning. The `records.version` column added in Phase F.2 is for optimistic concurrency, not history — it tracks the current generation, not the past.)
- Bulk edit is live as of 2026-04-20 — mass-assigning field values across selected records. Bulk delete / bulk export have been live since 2026-04-18. Known caveat: bulk edit runs `saveRecord` per record, so for very large selections (hundreds+ of records) the apply step is a long burst of writes (but each is cheap — localStorage + async Supabase upsert + workflow kick). No progress UI yet — the confirmation dismisses and the toast appears once all writes complete. Each per-record save now also pays the `record_save` RPC's version-check round-trip (Phase F.2); if another user edited any selected record mid-bulk, that single record fails with the version-mismatch toast and the rest still apply.
- Non-image file previews go through `FilePreviewModal` (PDFs, video, audio, and a download card for other types) for the new `file` / `multi_file` / `attachment` field types. Other inline file rendering surfaces (e.g. raw URL fields holding a PDF link) are still no-op — click opens in a new tab.
- Saved views apply to the **table** view only; card view still uses `card_config`. (The Advanced Filter panel, by contrast, is available in Table, Card, **and** Maps modes — only the saved-view machinery is table-only.)
- There's no "duplicate view" action yet — users have to recreate from scratch if they want a near-copy.
- Ad-hoc faceted filters are localStorage-only and don't sync across browsers/devices. There's no one-click "promote these chips into the view's saved conditions" because the view's condition model is AND-only and can't express the multi-value OR semantics of a chip pick.
- Filter chips are currently committed live on every popover change; there's no Apply/Cancel — accidental selections require a manual Clear.
