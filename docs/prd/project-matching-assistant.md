## Direction narrowed — Project Finder ONLY (read first, 2026-06-28)
The product direction was deliberately narrowed to **one focused, deterministic capability: the Project Finder.** It does one thing well — turn a client's requirements into a ranked, geography-verified shortlist of the right projects — with no conversational AI, no next-best-action coaching, no message drafting, and no AI deciding which project is best.

The broad conversational assistants that this PRD previously described — the **AI sales agent** (`ai_chats`), the **reel copywriter** (`copywriter_chats`), and the **conversational match co-pilot** (`matching_chats`, with its lead-temperature / next-best-action / WhatsApp-draft / task-creation tools) — are **unwired**, not deleted. A static build flag `PROJECT_FINDER_ONLY` (`src/lib/featureFlags.ts`, currently `true`) hides them from the sidebar and routes their pages to a `RetiredAssistantNotice`; their code and their Supabase models + records are kept intact so a single flip to `false` restores every old surface. The rest of this PRD documents the **two states**: the live deterministic engine (current), and the legacy unified-assistant design retained under the flag for reference/rollback.

**What was REMOVED from the product surface** (code may still exist, but no UI reaches it): next-best-action, lead temperature, WhatsApp message drafting, task/follow-up creation, AI-picked projects, the conversational AI flow, and the copywriter. The deterministic ranked groups are the whole surface.

## What it is (in plain English) — current
The **Project Finder** turns a client's requirements — city, district(s), property type, budget, area, bedrooms, bathrooms — into a ranked, fact-checked shortlist of the best-matching projects, grouped by how well their *location* matches:
1. **Exact district matches** — the project sits in the requested district, coordinate-verified.
2. **Nearby district matches** — a different district, ranked by real distance (closest first).
3. **Same-city matches** — the requested city, a different district.
4. **Broader fallback** — outside the requested area, surfaced only when the better groups are thin.

Every group is built by deterministic code. A project's district is decided by **where its map pin actually falls** (PostGIS point-in-polygon against 3,732 district boundaries) — the stored `location.district` text is NEVER blindly trusted; a stored district that conflicts with the pin is flagged as a `mismatch` and dropped to low confidence. Each match carries an honest `geo_confidence` (high = pin verified inside a polygon, medium = stored district but no coordinates, low = mismatch / outside known boundaries / no geography), `data_gaps`, and `mismatch_warnings`.

The optional AI does exactly two bounded things and nothing else: it **parses** a salesperson's messy free-text note into structured requirements *before* the engine runs, and it **writes a short 1–2 sentence explanation** for each match *after* the engine has ranked them. A hard server guard (`assertRankingUnchanged`) physically prevents the AI from changing which projects appear, their score, band, source, match type, or order — the AI can only swap explanation text for real matches.

The Finder powers the **Suggested Projects** button in the Follow-up Workspace (matching against the rep's live, unsaved preference draft) via the `POST /api/project-finder` endpoint. As of 2026-06-29 the Follow-up modal calls `/api/project-finder` directly (`parse:false` + `explain:false` — fully deterministic, no LLM, four location-centric groups). The legacy `POST /api/suggest-projects` endpoint (the old grouped five-bucket modal) is also boundary-verified (`verifyGeo:true`) but is **no longer reached by any UI** — it is retired from the Follow-up flow.

## Two surfaces for the same engine (current)
The deterministic Finder is reached from **two** places, both calling `POST /api/project-finder` deterministically (`parse:false` + `explain:false`):
1. **Follow-up "Suggested Projects" modal** (`SuggestedProjectsModal`) — client-scoped. Matches against the rep's live, unsaved follow-up preference draft; passes a `client_id` (so the client's `location_items` geo-preference gate applies) and the full client-action card set (select / bulk-save / save-as-option / eliminate / reactivate into `client_property_options`).
2. **Standalone Project Finder page** (`src/pages/ProjectFinder/ProjectFinderPage.tsx`, route `/project-finder`, sidebar tool) — **no client required.** The salesperson fills structured pickers (sourced from the live `clients` model's own fields, rendered via `DynamicField` — location cascade, preferred districts, unit type, budget, area, amenities — plus Bedrooms / Sources / Minimum-match controls), then runs the same engine with **no** `client_id` (no geo-preference gate, nothing to save). Result cards render **Details only** via `FinderCard`'s `hideClientActions` prop. This is a pure discovery/lookup surface — useful for ad-hoc "what do we have in حي X under Y budget?" questions outside any client conversation. Visibility is per-profile (`project_finder` custom page, `default_access:'all'`).

## Product direction — ONE unified Sales Assistant (LEGACY — unwired)
This is intentionally designed as **one unified sales assistant face** — **"مساعد المبيعات" / "Sales Assistant"** — with multiple internal capabilities, NOT a collection of separate assistants/pages. The salesperson opens one assistant, one chat, one conversation history, and types naturally; the assistant routes to the right internal capability. **Project matching + sales-pitch generation is the FIRST active capability.** Future capabilities — next-best-action / sales consulting, follow-up & task support, project comparison, customer understanding — will be added **inside this same assistant** (same chat, new tool + new structured card type), never as a second face or a new page.

## What it is (LEGACY unified assistant — unwired under PROJECT_FINDER_ONLY)
A live-call sales co-pilot. A salesperson on a call types what the customer wants — city, district, property type, budget, area, bedrooms, lifestyle — and the assistant instantly returns the best-matching projects, ranked, with a ready-to-say sales pitch for each. It searches **our curated projects first**; only if there's no good match there does it fall back to the broad **All Projects** database, clearly flagging those results as needing verification before being offered to the customer. It renders as a split-pane chat (past sessions on the left, the active conversation on the right) under the sidebar item **"مساعد المبيعات" (Sales Assistant)**.

## Why it exists
During a live call the salesperson needs a confident recommendation in seconds, grounded in real inventory — not a hand search through 1,372 projects, and not an AI that invents prices or availability. The assistant turns the customer's words into a ranked, fact-checked shortlist plus the exact sentence to say next.

## Full capabilities (one unified assistant — 2026-06-21)
The Sales Assistant is ONE chat that routes the salesperson's plain-language message to the right internal capability. All capabilities are tools + structured cards inside the same conversation — never a separate page/assistant.

1. **Project matching** — `match_projects` → `ProjectMatchCard`. (Detailed below.)
2. **Location intelligence (lookup-first + dual-read, 2026-06-25)** — `match_projects` is coordinate- AND district-aware. The requested district is resolved to the authoritative `districts` record (id + real centroid) via `resolveRequestedDistrict` (city-aware when a city is given). A project whose **`district_lookup`** equals the resolved district id is an **EXACT relational match** (no text needed). For projects not yet backfilled, the engine **dual-reads** the legacy path: text fuzzy-match on `all_projects.preferred_neighborhoods` + the project's stored `latitude`/`longitude`/`geo_source`/`geo_confidence` (from `2026-06-21_project_geo.sql`: inline map-link coords = high confidence, district centroids = medium, text-only = none). A candidate outside the requested district but within **12 km** of the district centroid is a **"nearby"** match carrying a real `distance_km` (haversine); tiers are exact → nearby → same_city → partial. The agent states the real distance, never invents proximity, and flags medium-confidence (centroid) coords as approximate.
3. **Project comparison** — `compare_projects(project_ids, requirements?)` → `emit_comparison` → `ComparisonCard`: side-by-side facts, deterministic per-project fit score/band, dimension winners (cheapest / largest / most bedrooms / most available), a verdict + recommended pick.
4. **Sales consultant / next best action** — `get_customer_context(client_id|phone|name)` returns the **deterministic** lead temperature (hot/warm/cold/won/lost — computed from stage + activity recency + status), stage, status, the already-scheduled next action (type/due/overdue), and preferences → `emit_next_action` → `NextActionCard` (risk, recommended action, talking points, follow-up timing).
5. **Message drafting** — `emit_message` → `MessageCard`: WhatsApp / SMS / call-script drafts built only from real facts, with a copy button.
6. **Task / follow-up creation (confirmation-gated)** — `propose_task` NEVER writes; it surfaces a `TaskProposalCard` with an editable due date and **Confirm / Dismiss**. Only on Confirm does the client create a `followups` record (via `saveRecord`). The agent is forbidden from claiming the task was created.
7. **Customer understanding** — the agent continuously extracts/refines the customer's structured requirements from the whole conversation (the chat history is its memory); cards re-serialize into history so context carries across turns.
8. **Feedback + telemetry + admin insights** — every assistant answer carries a 👍/👎 control. 👍 saves instantly; 👎 asks "what were you trying to do?" (find project / compare / understand customer / write message / create task / other) with an optional one-line note, so a miss is tagged by the rep's actual intent. Each answer also stores **inline per-turn telemetry** (which capabilities fired, response time, whether the turn errored) on the message — no schema change, no extra write path. An admin-only **Sales Assistant insights** dashboard (`/sales/assistant-insights`, gated by `useIsAdmin`, opened from a chart icon in the session list) aggregates the conversations the admin can see: capability/card usage, helpful rate (👍/👎), requests that didn't land (by intent), written rep comments, errored turns, and average response time. The aggregation (`aggregateInsights`) is pure and unit-tested; it tolerates any malformed message shape.
10. **Grouped Suggested Projects + Add-to-client (2026-06-26)** — a DETERMINISTIC endpoint (`POST /api/suggest-projects`, no LLM) reuses `matchProjectsCore` + a pure `groupMatchResults` to return five honest buckets (`exact_matches` / `nearby_alternatives` / `budget_matches` / `location_matches` / `fallback_matches`), each project carrying `data_confidence` (high = lookup + active + price/unit data; medium = lookup/active but missing price/unit; low = legacy text / requires-verification / partial / sold-out) and normalized `data_gaps`. Honest-data rules: a price-less project can NEVER be a `budget_match` (it surfaces `missing_price_range` instead); a strong-geo project with no price drops to `location_matches`; distance is district-centroid based and labelled as such (no project pins exist). The `SuggestedProjectsModal` renders the buckets as tabs + cards with a missing-preference banner; the **Add to client** card action appends the project to `clients.preferred_projects` (existing field) via the version-aware `saveRecord` — user-triggered only, never from AI text. Every run is logged to `assistant_recommendation_runs`. **No-criteria honesty (2026-06-26):** when the client has NO matchable preference at all (no location/budget/type/area/bedrooms), `scoreProject` has only `availability` left and renormalizes every available project to 100/strong — which is NOT a real match. The grouping detects this (`metadata.has_criteria=false`) and routes everything to `fallback_matches` as **"غير مطابق / Not matched"** (band forced partial, low confidence, reason `no_criteria`), and the modal shows a banner explaining these are general available inventory, not matched to the client — gather a district/budget/type for a real match.

9. **Find a project by name** — `search_projects(query)` resolves a named project to candidate `project_id`s (name, city, district, our_projects vs all_projects, requires_verification) so the agent can fetch its facts (`get_project`) or get the ids it needs for `compare_projects`. Powers the **"معلومات مشروع / Project Info"** quick action (info about a named project) and comparison-by-name; if more than one project matches, the agent asks which one. Added 2026-06-21 to close the long-standing gap where the prompt told the agent to "search first if you only have names" but no search tool existed.

**Deterministic-truth contract (all capabilities):** score / band / match_type / data_source / requires_verification / distance_km (matching, comparison) and lead_temperature / stage / next_action (consultant) are computed in code and quoted verbatim; the server reconciles `emit_recommendation` metadata so the model cannot re-score. The LLM only generates explanation, pitch, message, talking points, and questions — always from verified data.

## Key behaviors — Project Finder (current)
- **Selection, scoring, ranking, and grouping are 100% deterministic code.** `findMatchingProjects` (in `api/_lib/projectFinder.ts`) runs `matchProjectsCore` with PostGIS verification ON, then `groupForFinder` buckets the scored candidates into the four location-centric groups and ranks within each. No AI decides which project is best, scores a project, or sets the order.
- **District is decided by the map pin, not by stored text (boundary verification).** When `verifyGeo` is on, the engine resolves every candidate's containing district once per request via the `districts_for_points` PostGIS RPC (point-in-polygon against the 3,732 `district_boundaries` polygons). The polygon-derived district is the **source of truth** for an "exact" match — a project whose stored `location.district` conflicts with the polygon its pin sits in is classified `mismatch` (low confidence, warned), never a trusted exact. `classifyGeo` (in `api/_lib/geoVerify.ts`) is the pure classifier; its status/confidence recipe is kept **semantically identical** to the SQL audit view `v_all_projects_geo_integrity`.
- **Honest geo confidence + data gaps.** Each match carries `geo_status` (`verified_match` / `verified_derived` / `mismatch` / `outside_known_districts` / `unverified_no_coords` / `no_geography`), `geo_confidence` (high / medium / low), `mismatch_warnings`, and `data_gaps` (e.g. `missing_project_coordinates`, `coordinates_outside_known_districts`, `district_mismatch`). A project with no coordinates can still match — at **medium** confidence, with the gap recorded — never silently dropped or silently trusted.
- **Four location-centric groups.** `exact_district_matches`, `nearby_district_matches` (ranked by REAL haversine distance, closest first), `same_city_matches`, and `broader_fallback`. A `partial`-band item always falls to the fallback group. A `weak` finder band (low/no geo confidence or requires-verification) sorts below `strong`/`good`/`partial`.
- **The AI is bounded to two touchpoints, with a hard ranking guard.** The ONLY LLM calls (`api/_lib/projectFinderAI.ts`, a small/fast model `claude-haiku-4-5`): (1) `parseRequirements` — messy text → structured requirements, BEFORE ranking, with explicit fields always winning over parsed ones; (2) `explainMatches` — a short per-match explanation, AFTER ranking. `applyLlmExplanations` reads ONLY `{project_id → text}` and copies every ranking field straight from the deterministic result, and `assertRankingUnchanged()` throws if any score/band/source/match_type/order/membership differs before vs after. Both AI calls fail safe (return `{}` on any error) — the deterministic engine still runs without them.
- **Deterministic explanation fallback.** Even with no AI key, every match gets a fact-grounded templated explanation (`buildExplanation`) built only from verified facts (district, distance, price range, available units, source verification reminder). The LLM can only replace this string, never the ranking.
- **No matchable preference → ask, don't pad.** When the requirements carry no location/budget/type/area/bedrooms/bathrooms/amenities signal (`hasAnyCriteria` is false), the endpoint short-circuits with empty groups + `needs_preferences:true` + the missing required preferences, instead of returning "everything is a strong match."
- **Three sources, source is orthogonal to quality.** Our portfolio (`our_projects`), the broad database (`all_projects`), and external market listings (`market_listings`) are all scored by the SAME engine; every all_projects/market pick carries a verify-before-offering reminder in its explanation and (for market) `requires_verification`.
- **Audit trail.** Every Finder run writes one row to `assistant_recommendation_runs` (input preferences, group/geo counts, result project ids, whether AI parse/explain were used) — best-effort, never fails the recommendation.
- **RLS-scoped.** `/api/project-finder` runs under the caller's Supabase JWT, so a salesperson only matches projects they can already see.

## Key behaviors — LEGACY unified assistant (unwired)
- **Deterministic matching in code, narration by the AI.** The agent extracts requirements and calls one `match_projects` tool that does ALL filtering, tiering, and scoring server-side. The AI only writes prose over the verified, scored results — so it can't invent a project or fudge a score.
- **Two tiers, never mixed.** Tier 1 = projects in the `our_projects` model (curated, real units). Tier 2 = the rest of `all_projects` (scraped/competitor, unverified). The tool returns them in **separate** arrays and only includes the Tier-2 group when Tier 1 has no good match (`used_fallback`).
- **A third source — Market Listings (`market_listings`), AREA-pre-filtered.** When `includeMarket` is set (the grouped `/api/suggest-projects` endpoint passes it; the LLM `match_projects` tool does not, so its two-tier output is unchanged), the engine also scores the ~46,315 external Aqar ads. To avoid scanning 46k rows per recommendation, it first narrows them server-side to the client's relevant area: district + every neighbouring district within **20 km** of the centroid, else the requested city, else the newest 4,000 (a logged capped scan, never an arbitrary slice). The same `scoreProject` then grades the in-area listings identically to projects (each listing is adapted to the project shape by `adaptListingToScorable`). Two partial JSONB-expression indexes on the model's `district_lookup` / `city_lookup` keep the filtered read fast (~70ms/page). Every market pick carries `data_source:"market_listings"` + `requires_verification:true`.
- **Verification warning on All Projects results.** Every Tier-2 pick carries `data_source:"all_projects"` + `requires_verification:true` and renders an amber "verify price, availability, details before offering" banner.
- **Location is lookup-first + coordinate-aware (dual-read, 2026-06-25).** The requested district is resolved to an authoritative `districts` record; a project whose `district_lookup` equals it is an exact relational match (full credit). For projects not yet backfilled, the engine falls back to the legacy text fuzzy-match on `preferred_neighborhoods` + stored coordinates. A different district within 12 km → a "nearby" match with a real `distance_km`; else same-city → half credit. The assistant states the real distance and never invents proximity. Reverting to text-only matching is a one-line flip (the dual-read fallback is always present).
- **Weighted scoring (0–100):** location 30, budget 25, property type 20, area 10, bedrooms 8, availability 5, amenities/lifestyle 2. Dimensions the customer didn't specify are excluded and the weights renormalize, so an unspecified field neither penalizes nor inflates. Bands: strong ≥75, good ≥55, partial ≥40; below 40 is never surfaced.
- **Budget stretch:** an option up to 15% over `budget_max` is surfaced as a "stretch" (scored down, labelled). Beyond that → no budget credit.
- **Sold-out excluded by default** (`available_units = 0`), unless the request opts in.
- **Anti-hallucination:** the AI states only facts present in the tool output; missing details become "not available in the data" + a question to ask the customer. The recommendation card's specs are built only from present values.
- **Structured recommendation card** (`emit_recommendation` → `ProjectMatchCard`): per pick — name, band + score, why it matches, key specs, selling points, a copy-able pitch, verification warning (if Tier 2), and questions to ask. Plus overall clarifying questions. Display-only (no record is created).

## User flows — Project Finder (current)
1. **Suggested Projects from a follow-up (happy path):** Rep opens a follow-up, captures the client's preferences inline → clicks **Suggested Projects** in the Workspace → the deterministic Finder runs against the rep's live (unsaved) preference draft → the modal shows the four ranked groups (exact district, nearby, same city, broader), each card with score/band, geo confidence, distance, price, data-gap chips, and a short explanation. The perfect (score-100) matches come pre-checked; the rep selects any others, then **Save selected to client options** writes them into the client's unified **Client Property Options** (status `suitable`). Per-card, the rep can **Save as option** or **Eliminate** (with a reason); a source already saved shows its status, and an eliminated one offers **Reactivate**. See [clients.md](clients.md).
2. **Parse-from-text:** A caller passes free-text (`text`) to `/api/project-finder` → the bounded parser extracts structured requirements → the deterministic engine ranks → optional bounded explanations are attached → response returns the four groups + metadata (geo counts, used_ai_parse/explain, generated_at).
3. **Geo mismatch surfaced:** A project whose stored district disagrees with its pin's polygon is classified `mismatch`, dropped to low geo confidence, and its card shows "verify the record" — it is never offered as a trusted exact district match.
4. **No preferences yet:** The client has nothing matchable → the endpoint returns empty groups + `needs_preferences:true` + the missing required preferences, and the UI prompts the rep to capture a district/budget/type.

## User flows — LEGACY unified assistant (unwired; deep-link → RetiredAssistantNotice)

## Production Learnings (write these down so we don't relearn them)
These are the hard-won lessons from building a **write-capable** sales AI. They drove real fixes in `matchAgent.ts` / `api/match.ts` and they govern any future capability that can act on the user's behalf.

1. **Identity resolution is safety-critical — the wrong customer is the unacceptable failure.** The safety hierarchy is explicit: *attaching a task to the wrong client* is unacceptable; *missing a task* is acceptable; *asking one more question* is acceptable. So the assistant must always prefer "I need one more piece of information" over "this is probably the right customer." Concretely: `resolveClient` NEVER accepts a client id echoed by the model unless it resolves to a real record, and `resolveClientFromCandidates` is exact-match-first and requires a **unique** match — it never first-match-guesses on duplicate Arabic names.

2. **A write-capable AI is a different risk class than a read-only one.** Read-only matching that's slightly wrong wastes a few seconds; a wrong write creates a real orphaned record in `followups`. Every action capability therefore (a) resolves identity deterministically in code, (b) is confirmation-gated, and (c) is forbidden from claiming success it can't prove.

3. **Ambiguity must BLOCK execution, not get resolved by a guess.** When a name matches multiple clients, the assistant must surface the candidates and refuse to proceed — at **both** resolution points (`resolveClient` for the proposal *and* `get_customer_context`, which a live test of "عبدالله" proved could otherwise feed a valid-looking id straight into `propose_task`). The `TaskProposalCard` disables **Confirm** until the rep picks a specific client.

4. **User confirmation alone is insufficient if the identity underneath it is wrong.** A rep clicking "Confirm" trusts that the name/phone on the card is who the assistant resolved — so the card must show the resolved name + phone, and `confirmTask` must write only the validated id and report success **only** when `saveRecord` actually returns `'saved'`. Confirmation gates the *action*; deterministic resolution guarantees the *subject*.

## Open questions / known limitations
- **The broad assistants are unwired, not removed.** `PROJECT_FINDER_ONLY = true` hides `ai_chats` / `copywriter_chats` / `matching_chats` and the conversational capabilities; the code + DB models + records still exist. Rollback is one flag flip — but the longer they stay dormant, the more the legacy `/api/match` tools (still present, no UI caller) risk drifting from reality. Decide whether to fully retire or re-enable before they bit-rot.
- **Multi-district is now wired end-to-end (2026-06-29).** The requirements mapper (`src/lib/matching/requirements.ts`) collects ALL district ids from the client's `location` cascade district array (union'd with the `preferred_districts` field if present), resolves each to a name, and sends them as `districts[]`. The `/api/project-finder` endpoint already accepted `districts[]`, and the engine resolves each and treats a project in ANY of them as an exact match — across our_projects, all_projects, AND market_listings (the market RPC is scoped to the full requested-district set). So a client with several preferred districts is now searched against all of them. `district` still = `districts[0]` for single-district code paths.
- **Boundary verification only helps geocoded projects.** A project with no `latitude`/`longitude` cannot be point-in-polygon verified — it matches via its stored district at **medium** confidence with a `missing_project_coordinates` gap, and a project whose pin falls outside every known polygon drops to low confidence. The geo-integrity audit view exists to quantify and chase down those records.
- **Lifestyle matching is best-effort** (low weight): lifestyle keywords like "family/luxury" are fuzzy-matched against Arabic amenity values; many won't literally match. Treat as a tiebreaker, not a filter.
- **Not every project carries a district lookup yet.** 847 of 1,064 projects were backfilled with `district_lookup` (567 by PostGIS point-in-polygon, 278 by normalized-name, 2 by nearest-centroid); the rest carry a `district_match_status` (missing_coordinates / needs_manual_review / outside_known_boundary / ambiguous_match) and fall back to the legacy text + coordinate path via the dual-read. The 437 text-only projects (no coordinates) match on district/city text only; "nearby" distance applies just to geocoded projects, and medium-confidence (centroid) distances are flagged as approximate.
- **Whole-portfolio scan per call** — the tool pages all `all_projects` rows and scores in TypeScript (fine at ~1,372 rows). A `project_search_index` + SQL RPC is the performance path if the portfolio grows materially.
- **Insights are client-aggregated over visible conversations.** The admin dashboard computes from the `matching_chats` records the current admin can see (RLS-scoped), not a server-side rollup — accurate for a single admin's view; a cross-tenant rollup would need a server aggregate.

## Directional zones — "north of Riyadh" (added 2026-06-30)

The matcher only understands **cities + districts** (no cardinal direction). Free-text like "north of Riyadh / شمال الرياض" is now resolved DETERMINISTICALLY to a concrete set of districts:

- **Resolver:** `public.wassell_city_zone_districts(city, zone)` (SECURITY DEFINER) → district ids. A **curated `geo_zone_overrides`** row set (city × zone) WINS; otherwise the **geometric** rule classifies each district by its centroid's relative position within the city's bounding box (north = top 40% by latitude, etc.; diagonals supported). Mirrored for tests in `src/lib/market/zones.ts`. Riyadh "north" is seeded (geometric ∪ marquee districts النرجس/العارض/الياسمين/الملقا/حطين/الصحافة/النفل/القيروان/بنبان).
- **LLM parse** (`parseRequirements`) extracts `zone` from the words only — `{ city, zone }`. The expansion to districts is pure SQL; the AI never picks districts. An explicit named district always overrides a zone.
- **Engine:** `MatchRequirements` gained `zone` (audit) + `district_ids` (pre-resolved). When `district_ids` is set, `matchProjectsCore` batch-loads their centroids in ONE query (fast path) and treats a project in ANY of them as an exact-district match — no per-name lookup. Ranking/scoring unchanged.
- **Files:** `supabase/migrations/2026-06-30_geo_zone_resolver.sql`, `api/_lib/matchAgent.ts` (fast path + fields), `api/_lib/projectFinderAI.ts` (parse zone), `api/project-finder.ts` (RPC expansion), `src/lib/market/zones.ts`.
- **Limitation:** city is matched by Arabic name (`districts.city_name_ar`); an English city name returns nothing (the app passes Arabic). Geometric bands use the bounding box, so a far-flung outlier district can skew them — that's what the curated override is for.
