## What it is (in plain English)
The Model Builder lets a user design their own "data models" — essentially custom database tables — without writing code. A model (for example, "Clients" or "Follow-Ups") is made up of **sections** (groupings), and each section is made up of **fields** (individual inputs like dropdowns, text, dates, phone numbers, lookups). The user visually creates sections, adds fields, picks field types, sets options, and arranges the layout. Once a model is saved, users can start entering records into it.

## Why it exists
Every real-estate team tracks different things. Instead of shipping a fixed schema, Wassell lets the team define their own CRM structure. This is the foundation for every other feature — records, workflows, and dashboards all consume the models defined here.

## Key behaviors
- Models live in the left panel; editing one opens the right-panel editor.
- Each model has three editor tabs: **Fields & Sections**, **Card Builder**, and **Maps Builder**.
- **Sections** have an Arabic and English name, a color, an order, and an `is_base` flag. Base sections are always visible in record forms.
- **Collapsed-by-default sections (new 2026-04-20):** each section has an optional `default_collapsed?: boolean` on its schema. A chevron-toggle button in the Builder's section header flips it, and a "Collapsed" / "مطوي" pill appears on sections that are configured this way. In the record form each `SectionBlock` keeps its own local `collapsed` state that seeds from `default_collapsed` on mount — users can click the section header to expand/collapse any section regardless of the default. This is purely a UI convenience; it does not affect required-field validation or which fields are saved. Mirrored sections and base sections also respect the flag.
- **In-section field groups (new 2026-04-20):** each section can optionally split its fields into collapsible sub-groups — NOT nested sections, just collapsible dividers INSIDE one section. Config lives on the section as `field_groups: SectionFieldGroup[]` (each group has `id`, `label_ar`, `label_en`, `order`, `default_collapsed?`); each field points at its group via `ModelField.field_group_id`. A FolderPlus icon in the SectionCard header opens a "Field groups" modal where the user can add/rename/reorder/delete groups and toggle each group's default-collapsed flag (Collapsed by default / مطوية افتراضياً). Each field's group is picked from the Field Properties panel via a "Group in section" dropdown that only renders when the target section has any groups. Moving a field to a different section clears its `field_group_id` (groups are section-scoped). Deleting a group detaches its members back to ungrouped — the fields are untouched. Base, mirrored, and regular sections all support grouping; mirrored sections' own fields still come from the linked source, so grouping happens at the source model. Groups are display-only — records, imports, formulas, and workflows ignore them.
- **Fields** support 27 types including text, textarea, notes, number, range, date, dropdown, multi-select, lookup, mirror, `section_mirror`, phone, email, URL, `multi_link`, currency, checkbox, assignee, `section_selector`, `auto_id`, `formula`, `table`, `image`, `multi_image`, `file`, `multi_file`, and `attachment` (see below).
- **Drive-backed fields (`image` / `multi_image` / `file` / `multi_file` / `attachment`, new 2026-05-23):** five field types that integrate with the Files System (the `/files` page, the `wassel-files` Storage bucket, and the `files`/`folders` tables). Stored value is always an id pointer (or array of pointers), never a raw URL — so files can be renamed in the Drive without breaking records. Each input renders an "Add from Drive" button that opens the shared `DriveBrowserModal` for browse + pick + upload + new-folder. Click any chip → opens the existing `FilePreviewModal` (image/PDF/video/audio/download card). All five honor the standard `width` / `show_in_table` controls and render compact thumb/chip cells in TableView.
  - **`image`** — single image. Stored as a `files.id` UUID. The picker is MIME-filtered to `image/*` and the cell renders a 40×40 thumbnail.
  - **`multi_image`** — array of images. Stored as `string[]` of `files.id`s. The form shows a row of 96×96 thumbs + an "Add" tile; the cell shows the first thumb with a "+N" badge for overflow.
  - **`file`** — single non-image file. Stored as a `files.id` UUID. Accepts any MIME type allowed by the bucket. The cell shows an icon chip + filename.
  - **`multi_file`** — array of files. Stored as `string[]` of `files.id`s. The cell shows the first file's chip with a "+N" badge.
  - **`attachment`** — multi-value reference to files OR folders. Stored as `AttachmentRef[]` where each ref is `{type:'file'|'folder', id}`. The picker is multi-select across both kinds. File chips open the preview modal; folder chips re-open the picker scoped to that folder so the user can drill in without leaving the record. Reference a folder when you want the record to point at a moving target (e.g. "all photos for this property") rather than a frozen list.
  - **Per-field config:** all five accept `attachment_default_folder_id` (preferred destination — user can override at upload time, just like Google Drive), `attachment_max_items` (soft cap on the multi types), and the legacy `image_accept` / `image_max_size_mb` (MIME pattern + per-file size cap, repurposed from the pre-Drive era). The old `image_folder` prop on the field type is kept for backwards-compatible JSONB parsing but is no longer read by the new inputs.
  - **Upload tagging:** when the user uploads a new file through any of these field inputs, the resulting `files` row has `model_id` and `record_id` populated so the file is discoverable from the record (the Files page can show "Files attached to record X") AND from the Drive root (the user's normal `/files` view). Files appear in both places — the Drive is the source of truth for the bytes, the field stores a pointer.
- **Notes fields (new 2026-04-18):** type `notes` — render as an append-only journal in the record form (composer + chronological list). Each entry stores `{ id, text, author_id, created_at }`; author defaults to the current user at add-time. No extra Builder config; the field has no options, no width-sensitive behavior beyond full/half. Not sortable in the table, not importable from Excel, and not exposed in the advanced filter panel.
- **Multiple links field (new 2026-05-31):** type `multi_link` — stores an array of URL strings (`string[]`). The record form renders an editable list: each row is a URL input (`dir=ltr`, placeholder `https://...`) with a click-to-open icon and a remove button, plus an "Add link" / "إضافة رابط" button that appends a fresh empty row. The table cell renders each non-empty link as a compact numbered button — "Button 1" / "زر 1", "Button 2" / "زر 2", … — that opens the URL in a new tab (`target=_blank`, `stopPropagation` so it doesn't trigger the row click); bare hosts are prefixed with `https://`. No Builder config (no options, no lookup). A required `multi_link` field is "missing" only when the array has no non-empty entry. Not importable from Excel (added to the import skip-list) and not exposed in the advanced filter panel.
- **Range fields (new 2026-04-18):** type `range` — stores a structured `{ min?: number; max?: number }` value, rendered as two number inputs side-by-side. Builder config: `range_min`, `range_max`, `range_step` (all optional; passed to the native `<input type="number">` attributes), plus `range_unit_ar` / `range_unit_en` (a unit suffix shown inside each input and in read-only cells — e.g. "م²" / "m²" or "ر.س" / "SAR"). Not exposed in the advanced filter panel because the kind doesn't exist yet. Importable from Excel via two separate column mappings — see import-export.md for the `slug.min` / `slug.max` split.
- **Section selector field (unique):** a special field type whose options are the non-base section names in the same model. When the user picks values in this field on a record, only those sections become visible — base sections always show. Used in the Follow-Ups model to show different fields per follow-up type. **Custom non-section options (new 2026-04-20):** `section_selector` fields also accept user-added options that are NOT tied to a section. Section-linked options are auto-generated by `SectionManager.updateSectionSelectorOptions` with `is_section_option: true` and render as read-only/locked rows in the Field Properties' options editor; custom options (no flag) are added, edited, coloured, and grouped like any dropdown option. Custom values appear in the record's multi-select alongside sections but do NOT unhide any section — the record form still filters visibility by matching selected values to section ids. Use this when a classification field needs extra labels that don't correspond to a dedicated section (e.g. a "Cancelled" status on Follow-Ups that should hide all type-specific sections).
- **Lookup fields** reference another model (`lookup_model_id`) and display a chosen field from that model (`lookup_display_field`). The display-field picker allows scalar types: text, email, phone, number, currency, date, datetime, url, dropdown, and `auto_id` (so auto-incrementing identifiers like `CLT-001` can be used as the lookup's human-readable label). A `lookup_max_records` number input (default 20, range 1–500) caps how many records appear in the search combobox dropdown — applies to both single and multi-select modes, in the record form and in editable table cells.
- **Multi-select lookup (new 2026-04-18):** the Field Properties panel shows an "Allow multiple values / السماح بتحديد أكثر من قيمة" checkbox for `lookup` fields. When enabled (`is_multi: true`), the record form's lookup combobox shows selected records as chips (with an X to remove) and the search input stays open for adding more. Stored value becomes `string[]` instead of `string`. Table cells render the list as badges; cards comma-join the display values.
- **Mirror fields (new 2026-04-18):** a read-only field that displays a value from a *different* record, reached by hopping through a sibling `lookup` field on the same record. Configured via two dropdowns in the Field Properties panel:
  1. **Source lookup field** — any sibling `lookup` field in the same model (`mirror_via_lookup_field_id`). Can be single OR multi-select; when the sibling is multi-select the mirror resolves to an array of target values (rendered as a chip list).
  2. **Field to display** — a field on the lookup's target model (`mirror_target_field_name`). Allowed target types: text, textarea, number, email, phone, url, currency, date, datetime, dropdown, **lookup** (so a mirror can surface another record's lookup, e.g. the project on a linked appointment).

  Guard rules: mirrors cannot be `required` (the `required` checkbox is disabled when the type is `mirror`), cannot participate in Excel import, and cannot be sorted in the table view. Chained mirrors (mirror → mirror) are explicitly forbidden. The field row shows an orange warning icon when its configuration is broken (sibling missing, sibling no longer a lookup, or target slug removed from the target model).
- **Section Mirror field (new 2026-04-18):** type `section_mirror` — a FIELD (placed inside any regular section) that pulls a picked subset of another record's section INLINE into its parent section, with per-child-field edit and sync-back controls. Each mirrored child renders as a normal grid item alongside local fields (respecting the source child's width), with a small "Mirrored" / "Synced" / "Local" tag next to its label. The container itself has no width / show_in_table controls — it's invisible; only its expanded children show up. Configuration (in Field Properties):
  1. **Sibling lookup field** (`section_mirror_via_lookup_field_id`) — single-select lookup on this model that points at the source record. Establishes the link (same pattern as single-field mirror).
  2. **Source section** (`section_mirror_source_section_id`) — section on the lookup's target model whose fields are candidates to mirror.
  3. **Fields to show** (`section_mirror_field_mode`) — `all` or `custom`. When `custom`, user multi-selects child field slugs into `section_mirror_field_names`.
  4. **Edit permissions** (`section_mirror_edit_mode`) — `all` / `none` / `custom`. When `custom`, user picks editable child slugs into `section_mirror_editable_field_names`. Non-editable children render read-only.
  5. **Sync-back** (`section_mirror_sync_mode`) — only shown if any field is editable. `all` / `none` / `custom`. Fields in the sync set flow into the existing mirrored-section fan-out path and save to the linked record on submit. Fields NOT in the sync set save as **local overrides** on THIS record (stored under `record.data[section_mirror_field.name]` as a map of child-slug → value).
  Child field types `section_mirror` and `section_selector` are always excluded (avoid nesting / model-local semantics). Child fields of type `mirror` still render (read-only via DynamicCell). Container fields cannot be `required`, imported from Excel, saved as a template, chosen in the Card Builder, or used as a sort/filter field in views. Mirrored children ARE selectable as columns in the view/column manager (marked with a "Mirrored" tag) and render in TableView as read-only cells; inline-edit and sort on virtual mirrored columns are v2. Known v1 limitation: required-field validation on mirrored children only runs for the sync-back path; local-override edits bypass required validation.
- **Mirrored sections (new 2026-04-18):** a whole section can be flagged as mirrored from another model's section. Configure via the Link2 icon in the section header → modal asks for a sibling single-select lookup field on this model and a target section on the lookup's target model. The mirrored section contains no local fields; at render time its fields come from the linked record's source section. Unlike single mirror fields, mirrored sections are **fully editable with write-back**: edits save back to the linked record when the parent form is saved. Mirrored sections always render regardless of the `section_selector` selection (they're not classification — they describe the linked record). Required-field validation runs on mirrored-section fields too; blocking save if the user cleared a required field on the linked record through the mirror.
- **Auto ID field (new 2026-04-18):** type `auto_id` — an auto-incrementing identifier assigned at record creation and immutable thereafter. Builder config: `auto_id_prefix` (any text, including Arabic — e.g. `"CLT-"` or `"عمل-"`; empty = number only), `auto_id_padding` (zero-pad width, default 3), `auto_id_start_value` (first number, default 1), and optional `auto_id_scope_field_id` (sibling text/dropdown/number/checkbox/email/phone/URL/multiselect field whose **value** scopes the counter — each distinct value gets its own counter, e.g. RYD-0001 / JED-0001 when scoped by city). Counters live on the field definition in `auto_id_counters: Record<string, number>`, keyed by slugified scope-value or `"__global__"`. Assignment happens in the store's `saveRecord` chokepoint; the updated model (with bumped counter) is persisted in the same transaction as the record. Editing prefix/padding/scope after records exist does NOT rewrite stored IDs (they're immutable) — only new records use the new format. A **Restart counter** button in the Field Properties panel opens a modal with two modes: *Reset counter only* (next new record starts from start_value; existing IDs untouched, duplicates possible) and *Renumber all records* (walk every existing record in creation-order per-scope and assign fresh IDs). `required` is forced false; `show_in_table` defaults true. Auto IDs cannot be saved as a field template (counters are per-field state).
- **Formula field (new 2026-04-18):** type `formula` — a read-only computed field. Expression is an Excel-like template using `{field_slug}` tokens that reference other fields in the same record, e.g. `{price} * {quantity}`, `CONCAT({first_name}, " ", {last_name})`, `IF({is_paid}, "PAID", "UNPAID")`, `DAYS({end_date}, {start_date})`, `ADD_DAYS({start}, 7)`. **Dot-path refs (new 2026-04-19):** a range field's two halves are addressable as `{slug.min}` and `{slug.max}` — each resolves to a scalar so expressions like `{area.max} / {area.min}` work. Only `range` fields support sub-paths; any other field with a dot suffix, or an unknown sub-path on a range, is reported as an unknown reference by the Builder's live validator. Supports numeric math (`+ - * /` with parentheses and unary minus), string concatenation (via `+` when either operand is a string, or `CONCAT`/`CONCATENATE`), comparison operators (`=`, `!=`, `<>`, `<`, `>`, `<=`, `>=`), and booleans. Built-in functions: `IF(cond, then, else)`, `CONCAT(...)` / `CONCATENATE(...)`, `DAYS(end, start)`, `ADD_DAYS(date, n)`, `ROUND(n, digits?)`, `ABS`, `MIN`, `MAX`, `SUM`. Errors return Excel-style sentinels: `#DIV0` (division by zero), `#REF` (unknown field), `#ERR` (parse/eval failure), `#CYCLE` (formula dependencies loop). **Compute-on-save snapshot:** the engine runs during `saveRecord` (after auto_id assignment, before state commit) in topological dependency order and writes the result into `record.data[field_slug]` — so downstream reads (filters, exports, cells) use the cached value without re-evaluating. **Nested formulas (formula-on-formula):** a formula can reference another formula's slug — `({avg_min} + {avg_max}) / 2` — because `computeAllFormulas` topo-sorts dependencies before evaluating. The record form's live preview now calls the dedicated `evaluateFormulaInModel(field, model, data)` helper which re-runs the full model graph against the current form state, so edits to an upstream formula's inputs propagate through every dependent formula in real time instead of leaving `#REF` / stale snapshots. **Output formatting (new 2026-04-20):** each formula field carries `formula_output_type` (`number` / `currency` / `percentage` / `text`) plus `formula_decimals` (0–6, default 2), `formula_thousands_separator` (default true), and `formula_currency` (e.g. `SAR`, `USD`, `EUR`, `GBP`, `AED`, `KWD` — default `SAR` when type is currency). Formatting is applied by the shared `formatFormulaValue(value, field, locale)` helper so table cells, form previews, and card view all render identically — numbers get rounded + localized (thousands + digit script), currency appends `ر.س` / `SAR` / currency code, percentage multiplies by 100 and appends `%`. Text-type output passes through unformatted. Error sentinels pass through unchanged so renderers can highlight them in red. **Structured Field Properties UI (new 2026-04-20):** the expression textarea is flanked by three chip rows — Insert field (per-slug token chips including `{slug.min}` / `{slug.max}` for range halves), Operators (`+ − × ÷ ( ) = ≠ < >`), and Functions (IF, ROUND, SUM, MIN, MAX, ABS, CONCAT, DAYS, ADD_DAYS) — each chip inserts a snippet at the caret (with surrounding whitespace / valid arg placeholders) and restores focus. Below the expression the "Output formatting" block exposes the type / decimals / thousands-separator / currency controls; irrelevant controls collapse out when the type doesn't use them (e.g. decimals hidden for text, currency picker only for `currency`). Build-time Field Properties validation blocks Save when the expression fails to parse, references an unknown slug, or introduces a cycle; FieldRow shows an amber warning icon for broken formulas on already-saved fields. `required` is forced false; `show_in_table` defaults true; formula fields cannot be saved as a template.
- **Field templates (new 2026-04-18):** any saved field can be saved as a reusable template via the "Save as template" action in the Field Properties footer. The template captures the field's full snapshot (type, options, width, lookup target, is_multi, range config, mirror config, etc.) minus the `id`/`section_id`/`order`. Templates appear in a "Templates" catalog below the Field Type Catalog in the Builder's right panel. Click a template to insert a copy into the active section — the copy gets a fresh `id`, fresh option `id`s, and its slug is auto-suffixed (e.g. `district_2`) if it collides with an existing field on that section. Copies are **independent**: editing the template or the original source field does NOT affect previously inserted copies. Templates are global across all models for the current user. Hover a template in the catalog to reveal a delete (X) action. Templates can't be saved for type `section_selector` or `mirror` (their config is inherently model-local — they reference sibling IDs on the current model).
- **Fallback when empty (new 2026-04-22):** every non-computed field has an optional per-field setting in the Field Properties panel — **"Fill from another field when empty"** / **"املأ من حقل آخر عند ترك الحقل فارغًا"**. Stored as `ModelField.fallback_source_field_id`. At record-save time, if the target field's value is empty (`undefined` / `null` / `""` / `trim === ''` / `[]`), the save pipeline copies the referenced source field's current value into the target. The resulting value is real record data — the user can edit it later, and if they clear it and save again, the fallback refills on the next save (matches the "empty always gets filled" mental model). Allowed **target** types: text, textarea, number, email, phone, date, datetime, currency, url, dropdown, multiselect, lookup, range — the control is hidden entirely for formula, mirror, section_mirror, section_selector, auto_id, notes, checkbox, assignee (computed / structural / always-has-a-value types). Allowed **source** types: everything except formula, mirror, section_mirror (which resolve in different phases of the save pipeline), section_selector, notes, checkbox, assignee — plus self-reference is blocked. Motivating use case: the Clients model's `client_name` falls back to `client_code` (an `auto_id` field) so new clients without a typed name show `CLT-0042` in tables, cards, and lookups instead of a UUID slice. Lookup sources: the stored value is a UUID, so the resolver hops to the linked record's `lookup_display_field` — never writes a raw UUID into a text field. If the linked record is missing or its display value is empty, the fallback skips (the target stays empty rather than propagate emptiness or a UUID). Single pass — no chain resolution across multiple fallback fields. An **"Apply to existing records"** button appears in the Field Properties panel immediately below the source dropdown when the currently-saved field has a fallback configured (not just a pending edit); clicking it shows a confirmation dialog with the target + source field labels, then re-saves every record where the target is empty via the standard `saveRecord` path — so auto_id / formulas / update-trigger workflows fire per record, and a toast reports the count filled (or "No records needed filling."). Implemented in `src/lib/fieldFallbackResolver.ts` (pure function `applyFieldFallbacks`); wired into `src/stores/appStore.ts` `saveRecord` between `assignAutoIds` and `computeAllFormulas`; store action `applyFallbackToExistingRecords(modelId, targetFieldId)` backs the bulk button. Required-field validation in the record form still fires on empty required fields — users who want the fallback to be the single source of truth for a field should uncheck `required` on that field (or type a value themselves).
- **Editable API names (new 2026-04-19):** every field's `name` slug is editable in the Field Properties panel under "API name" / "اسم API". For new fields the slug auto-syncs from `slugify(label)` until the user types into the input; for existing fields it stays put until edited. Validation enforces `/^[a-z][a-z0-9_]*$/` and uniqueness within the model; the Save button is disabled while invalid. Renaming an existing field triggers a confirmation modal that reports the propagation impact — record count, formula count, cross-model lookups / mirrors / section-mirrors, workflow conditions + mappings, and saved views — before committing. On confirm, a single atomic store action (`renameField` in appStore) walks every location that holds the slug and rewrites it: record data keys (`data[old]` → `data[new]`), formula expressions (`{old}` → `{new}`, including `{old.min}` / `{old.max}` dot-paths), `lookup_display_field` and `mirror_target_field_name` on OTHER models targeting this one, `section_mirror_field_names` / `..._editable_field_names` / `..._sync_field_names` arrays, all workflow `field_id` / `target_field_id` / `trigger_field_id` / `dedup_target_field_id` / `filter_field_id` / `assignment_field_id` references scoped to the relevant model, and virtual view column IDs of the shape `${containerId}::${oldSlug}`. Field IDs (UUIDs) back every SAME-model non-slug reference (views, card config, ad-hoc filters, `section_selector_field_id`, `auto_id_scope_field_id`, mirror sibling pointers) so those never need migration. Works on system models too. The helper lives in `src/lib/fieldRename.ts`; the slug-only formula rewriter is `rewriteFormulaSlug()` in `src/lib/formulaEngine.ts`.
- **Duplicate Check Field (new 2026-04-19):** each model has an optional model-level setting stored as `schema.duplicate_check_field_id`. Configured via a dropdown at the top of the Fields & Sections tab (above the section list). The picker shows every eligible field in the model — types `textarea`, `checkbox`, `multiselect`, `section_selector`, `assignee`, `notes`, `range`, `mirror`, `section_mirror`, and `formula` are excluded because their stored value isn't a stable scalar identity. Default is "No check" (null). Selecting a field activates duplicate detection on Excel import (see import-export.md) — rows whose value for this field matches an existing record are skipped. Deleting the chosen field auto-clears the setting.
- **Dropdown options** each have `label_ar`, `label_en`, `value` (slug / api_name), an optional color, and an optional `group_id`. The Options Editor surfaces `value` as an **api_name** column. **Live-translated api_names (new 2026-05-31):** as the user types an option's label in either language, the api_name auto-fills via the same debounced `/api/translate` flow used for field api_names (`useDebouncedTranslation` in `OptionRow`) — Latin input slugs instantly via `slugify`, Arabic input fills the English-derived slug once the translation lands, and the empty opposite-language label is filled too; a spinner shows in the api_name cell while in flight. Auto-fill is gated: a value that is already a real slug (snake_case or an Arabic inline slug records may rely on) is pinned and never overwritten, and only **empty or bare-UUID** values (e.g. an orphaned `section_selector` option still holding its old section id) re-derive — and only on a user label edit, never silently on open. Manually editing the api_name input also pins it. **Bulk "Translate all" (new 2026-06-02):** the options modal footer shows a `Translate all (N)` button whenever N options still lack their other-language label or a real api_name; clicking it translates every blank option **in parallel** (one round-trip's latency instead of N staggered debounced calls) and only fills blanks — never clobbering a typed label or pinned slug. It shares `translateLabel`'s in-memory cache with the live per-row flow, so anything already translated this session resolves instantly. `/api/translate` itself runs on the Vercel **edge** runtime (migrated off `nodejs` 2026-06-02) so the first translation each session no longer pays a Node cold-start — the main cause of the old "very slow" feel.
- **Option groups (new 2026-04-20):** `dropdown` and `multiselect` fields can optionally organize their options into **collapsible sections**. Groups live on the field as `option_groups: FieldOptionGroup[]` (each group has `id`, `label_ar`, `label_en`); each option can reference a group via `group_id`. Options without a `group_id` (or whose `group_id` references a deleted group) render as ungrouped at the top of the menu. In the Builder's Options Editor, clicking **"+ إضافة مجموعة"** / **"+ Add Group"** adds a new group header; each option row then shows a small group-picker dropdown. Group headers support inline rename (click the label), collapse/expand (chevron), and delete (trash); deleting a group clears the `group_id` on all its members — it doesn't delete the options themselves. At record-render time, `DropdownSelect` / `MultiSelect` show group headers collapsed by default with an option count, expand on click, and auto-expand the group containing the currently selected value(s) when the menu reopens. Groups affect display only — record storage is unchanged (still `field_slug: "option_value"`), so existing records work without migration and groups can be added or removed at any time without breaking data.
- **Phone fields** expose a **Default country code** setting in the Field Properties panel (stored as `default_country_code` on the field). This code is used to prefix local-format numbers entered by users in that field. It falls back to `+966` (Saudi Arabia) when unset.
- **Card Builder tab** lets the user pick which field is the card title, subtitle, badge, and which fields show on a compact card view.
- **Maps Builder tab (new 2026-04-23):** configure the Maps view for this model. Global per-model (like `card_config`), stored as `AppModel.maps_config: MapsConfig`:
  - **Location source:** `location_url_field_id` points at a `url` or `text` field holding a Google Maps link — **or a `mirror` field whose target is a url/text field** (so a project can pin from a location mirrored off the master All Projects record without storing the link locally; the dropdown lists such mirrors via `resolveMirrorTargetField`). Optional `manual_lat_field_id` + `manual_lng_field_id` (number fields) fall back when the URL can't be parsed client-side (shortened `maps.app.goo.gl` redirects are CORS-blocked).
  - **Pin appearance:** `pin_color_field_id` is a dropdown/multiselect — the first selected option's color becomes the pin color; records with no selection fall back to `model.color`. `pin_label_field_id` is the hover tooltip.
  - **Click action:** `click_action: 'popup' | 'navigate'`. Popup opens an InfoWindow with `popup_title_field_id`, `popup_subtitle_field_id`, `popup_badge_field_id`, and `popup_shown_field_ids[]`. Navigate routes to the record detail page.
  - **Theme:** raw Google Maps style array pasted into `map_style_json` with a "Validate JSON" button. **Left empty (or invalid), the map inherits the shared Wassel-branded theme** (cream geometry, chocolate labels, copper roads) via `resolveMapStyles` / the `WASSEL_MAP_STYLE` constant — so every model's map matches All Projects out of the box. Paste `[]` to opt back into Google's stock theme. The preview map reflects the resolved theme live.
  - **Default viewport:** `default_center_lat`, `default_center_lng`, `default_zoom`. Null values center on Riyadh (24.7136, 46.6753) at zoom 11.
  - The right column live-previews up to 5 real records with the current config. Requires `VITE_GOOGLE_MAPS_API_KEY`; otherwise shows a "key not configured" message.
- **Width** on a field (`full` / `half`) controls form layout.
- **`show_in_table`** flags which fields appear as columns in the records list.
- **System models** (`is_system: true`) can be edited but NOT deleted — delete button is disabled for those. Edits persist like any other model; changes to `seedModels.ts` in code only affect fresh installs that have never seen the model before. To push a structural change to a system model that already exists in an install, add a versioned migration in `schemaMigrations.ts`.
- **Freeze (new 2026-05-05):** every freezable model exposes a "Freeze" action in the editor header that promotes it from a JSONB row in `records` to a real Postgres table. Frozen models display a "Frozen · `<table_name>`" pill, a read-only banner, and lock the four editor tabs from any edits via a `readOnly` prop. The Freeze modal previews coercion failures (records that can't move into the new typed columns) before the irreversible action — the user must clean those up first; freeze refuses to silently NULL data. Custom-UI models (`chats`, `ai_chats`) are excluded — the Freeze button doesn't render for them. Once a model is frozen, schema changes happen via Claude writing a migration — both the Builder UI tabs and the Builder Agent's schema-mutating tools refuse to make changes. See data-storage.md's "Frozen models" section for the storage / view / RPC architecture and the field-type → column mapping.
- Every label (model, section, field, option) requires both Arabic and English values.
- Saving a model writes the whole `schema` JSONB object to `models.schema` and also updates localStorage immediately.

## User flows
1. **Create a new model:** Click "+ New Model" → modal asks for Arabic name, English name, icon, color, group → on submit, the model appears in the list with one empty section.
2. **Add a section:** In the editor, click "+ Add Section" → inline row appears, user fills in AR/EN name and color → saved on blur.
3. **Add a field:** Inside a section, click "+ Add Field" → field type catalog opens → user picks a type → field row appears → user fills AR/EN label, options (if dropdown), lookup target (if lookup), width, required flag, show_in_table flag.
4. **Reorder:** Drag-and-drop to reorder sections and fields (@dnd-kit).
5. **Configure section selector:** Create a section_selector field at model level → its options auto-populate from non-base section names.
6. **Card Builder:** Switch tab → pick title/subtitle/badge fields from dropdowns → toggle which fields show on the card.
7. **Delete model:** Trash icon (hidden for `is_system: true` and frozen models) → confirm modal → model and its records are removed.
8. **Build by chatting (AI Builder):** Click the "AI Builder / مساعد ذكي" button in the Model Builder's left-pane model list → lands on `/builder/agent` → describe the model or change in plain Arabic / English ("create a Properties model with sections for general info, photos, and price"; "add a phone field to Clients"; "delete the inventory model") → the agent asks any clarifying questions, confirms destructive actions, then calls the right tool → the page syncs the result into Zustand so the sidebar and Builder editor see the change immediately, and a chip appears in the chat with an "Open in Builder" link. The agent refuses schema mutations on frozen models (any add/update/delete of section / field, or model deletion) — the user is directed to a regular Claude Code chat to write a migration that ALTERs the dedicated table AND updates the JSONB schema.
9. **Freeze a model (new 2026-05-05):** Once the model's schema has stabilized, click the "Freeze" button in the editor header. A modal first reports any records that would fail to coerce into typed columns (with field, raw value, and reason) — fix those first, then re-open the modal. With a clean preview, the modal asks the user to type the model's name (`clients`, `all_projects`, etc.) to confirm and explains that the action is one-way. On confirm, the SQL `freeze_model(model_id)` RPC creates the dedicated table, copies records, drops the legacy JSONB rows, and flips the `is_hardcoded` flag — a green success banner reports the row count moved. Going forward, the Builder UI is read-only for that model.

## Data touched
- Reads/writes: `models` table — especially `models.schema` (JSONB), `models.card_config` (JSONB), and `models.maps_config` (JSONB, new 2026-04-23).
- Reads: `model_groups` (for the group dropdown).
- Reads: other `models` (for lookup field target selection).

## Open questions / known limitations
- No field-level permissions yet (visibility controlled only at model level via Profiles).
- No versioning — editing a field can change how existing record data is interpreted (risk with rename/type change).
- No import/export of a model schema as JSON for sharing between environments.
- Mobile layout stacks the three editor panes vertically but doesn't adapt drag-and-drop reordering for touch — section/field reorder works but is best on desktop.
