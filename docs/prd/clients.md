## What it is (in plain English)
The Clients model is the central record of every customer the agency has touched. Its record page is a 360° view: the client's own form on one tab, plus a "Client Details" tab that the user can also reach from any other record in the CRM that points at the client (a Follow-Up, a Visit, an Appointment, a Phone Call, etc.). The Client Details tab shows the client's full record read-only, every WhatsApp message we've exchanged with them across every one of our numbers, every Hatif-logged call to or from any of their phones, and a "Related Records" area — one full table per other model that references this client (Follow-Ups, Visits, Appointments, Phone Calls, …), with sortable, user-adjustable columns. Sales staff can see the whole story of a client without leaving the form they're working in.

## Why it exists
Sales conversations span channels — WhatsApp, calls, in-person visits, email — and span days. Before the 360° view, an agent had to open the client record in one tab, the chats inbox in another, and click through Follow-Ups in a third just to brief themselves before a call-back. Surfacing all of it on one screen, reachable from any record that references the client, makes follow-ups faster and cuts the number of times an agent loses their place.

An eliminated option is **never silently reactivated** — re-saving the same source from the finder returns "already eliminated" instead of reviving it; reactivation is an explicit manual action (back to `suitable`, keeping the notes for history).
  - **Per-row actions** (edit-permitted users): view source (opens `/model/<all_projects|units|market_listings>/<source_id>` in a new tab), mark/clear main, change status via a dropdown, inline-edit the sales note, eliminate, reactivate.
  - **"إرسال للعميل / Send to client" (added 2026-07-04).** Project and market-listing option cards carry a copper Send-to-client action that WhatsApps that option to THIS client without opening the source record: a prepared `chat_templates` message is reused (project → `ProjectWhatsAppFlow`; listing → `ListingWhatsAppFlow`, ready templates only), and when none exists the existing creation flow runs from the card (project: deterministic compose + review; listing: AI text + text-removed photos) before continuing into the chat composer (`StartChatModal`, client preselected; photos + direct video files ride along as separate messages). Unit options have no message flow (no button). See [project-matching-assistant.md](project-matching-assistant.md).
  - **Default sort + filter.** Main + active options sort first (by status order then match score); eliminated options are hidden behind a "Show eliminated (N)" toggle. A status-filter dropdown narrows the list.
  - **Preference chips + search / source filter / sort (added 2026-07-17).** The toolbar shows the client's preference INPUTS as read-only chips (type, budget, area, geo, amenities, direction via `buildAssistantContext` + a bedrooms chip); below them a search box (name / district / ad id), a source-type filter with counts, and a sort dropdown (Best = main→status→score default; match score; price low→high on range min with nulls last; price high→low on range max; area largest-first; newest added). All three narrow/order the same `visible` set the list AND the map render.
  - **List / Map view toggle (added 2026-07-15).** A **قائمة / خريطة** segmented control in the filter bar switches between the card list and a map (`ClientOptionsMapView`): the same filtered set of options plotted as status-colored pins (badge colors) on the branded basemap, clustered by density; the main option is a copper named pill, never clustered, always on top. Clicking a pin opens the identical option card (all actions) in a floating panel; the footer shows the on-map count, a "N without coordinates" note, and a legend of the statuses present. Coordinates read `facts.latitude/longitude` first (snapshotted by the finder at save time), falling back to the source record's own coordinates in the store.
  - **Adding options from the tab (added 2026-07-02).** An "Add option" button in the filter bar (plus "Find projects" / "Add option manually" buttons in the empty state) lets the rep add options without a follow-up: the **manual picker** (`AddOptionModal`) searches projects / units / market listings in-store by name (listings need a ≥2-char query), shows each row's location + price, and saves via `saveClientOption` with `added_from='manual'` and a finder-shaped `facts` snapshot; market-listing rows lead with the ad id (**"@123456 — title"**, added 2026-07-04) so the id is visible in the picker and lands in the saved option's `source_name`; rows already saved show their status chip, and eliminated options refuse re-add (reactivate from the list instead). The "Find projects" button opens the client-scoped finder at `/model/clients/:id/projects`.
  - **Deterministic, version-aware, no AI.** Every save/dedup/main/eliminate/status operation lives in `src/lib/matching/clientOptions.ts` and writes through the store's version-aware `saveRecord` (RLS-correct, surfaces + persists failures). Display facts are snapshotted at save time so the view never re-resolves the 46k market_listings.

  2. The record has at least one populated `lookup` field whose `lookup_model_id` points at the clients model (single OR multi-select; multi counts every populated id).

  Tabs:
  - **Form** — the existing record form (default).
  - **Client Details** (with a Users icon) — embedded read-only view of the linked client. Renders every section of the client (including the new WhatsApp History + Calls panels) followed by a "Related Records" panel.

- **Multi-client switcher.** When a record has more than one populated client lookup (e.g. a record that links a buyer AND a seller, or a Follow-Up that points at two clients), the Client Details tab shows a small chip strip above the embedded client view labeled "Client:" / "عميل:" with one chip per client. Picking a chip writes `?client=<id>` and re-renders the embedded view for that client. Defaults to the first client id in iteration order. Hidden when only one client is in scope.
- **Related Records panel.** Cross-model query, purely client-side off the in-memory `records` slice. Walks every model's schema once (memoized on `models`) to build a lookup-fields-by-target-model index, then for each lookup field that targets the clients model, finds every record whose stored value for that field references this client (single value `=== id` or array `.includes(id)`).   - **Adjustable columns.** Each group's table has a "Columns" picker (a popover, not the full ViewEditor modal) to toggle column visibility and drag-reorder — but no sort/filter/sharing controls. The choice is stored per `(model, user)` in `localStorage` under `wassell_related_cols_<modelId>_<userId>` (a non-critical UI pref, same posture as ad-hoc filters / page size), survives reload, and a "Reset" link clears it back to the default. Default columns mirror `TableView`'s no-view fallback: the model's `show_in_table` fields with the card title field prepended.

- **Sales Operating System fields (added 2026-06-17).** The client record is the spine of the guided sales lifecycle. Beyond the existing stage/status fields, it now carries:
  - **`client_owner`** (assignee, relabeled "Sales Consultant" / مستشار المبيعات on 2026-06-30) — the rep who owns the client. **Auto-derived + read-only** since 2026-06-30: it always reflects the `sales_rep` of the client's most-recently-created follow-up (even one merely assigned, not yet completed), recomputed by `recalc_client_derived_data` on every client write and on every follow-up/call/chat touch. Since 2026-07-13 the derivation **ignores follow-ups whose rep is a deactivated user** — so a departed rep's historical follow-ups can't re-claim ownership after their client book is reassigned (a directly-set owner sticks when no active-rep follow-up exists).
  - **`next_followup_id`** (lookup → follow-ups), **`next_action_type`** (call / whatsapp / appointment / offer / financing / ownership), **`next_action_due_at`** — the denormalized "what's next" for this client. **This trio is auto-maintained, read-only, and derived from the client's open follow-ups** (see next bullet).
  - **`last_activity_at`** — the client's last touch (most recent completed follow-up, call, or WhatsApp message). **Derived + read-only.**
  - **`lost_reason`** + **`lost_at`** — why and when a client became Lost (same lost-reason option set the follow-up uses). **Derived + read-only** (populated only in a Lost / Unqualified stage).
  - **`lifecycle_health`** (on_track / overdue / no_next_action / closed) — a health flag for dashboards. **Derived + read-only.**

  **The stage / status / owner fields are maintained by the Sales Lifecycle workflows; the next-action, activity, lost, and lifecycle-health fields are maintained by Postgres triggers (next bullet) — none are edited by hand.** A rep records an outcome in the Follow-up Workspace, and the bound workflow advances `client_stage` / `client_status` and creates the next task. The Sales Queue and Sales Manager compute the live "needs a next action" picture from the open follow-up set. See [sales-process.md](sales-process.md) and [followups-workspace.md](followups-workspace.md).
- **Auto-maintained derived client fields (added 2026-06-17).** Seven client fields are recomputed by a SECURITY DEFINER Postgres trigger pair (the same pattern as the all_projects unit rollups) and are **read-only** — never typed or written by a workflow:
  - **Next-action trio** (`next_followup_id` / `next_action_type` / `next_action_due_at`) — the client's **earliest OPEN follow-up** (`followup_status` ∈ {open, in_progress}); `next_action_type` is mapped from the follow-up's `followup_type` (whatsapp_follow_up→whatsapp, offer_follow_up→offer, financing_follow_up / reservation_payment_follow_up→financing, ownership_transfer_follow_up→ownership, else→call).
  - **`last_activity_at`** — the most recent of {completed follow-up `actual_datetime`, `phone_calls.call_time`, `chats.last_message_at`} for the client.
  - **`lifecycle_health`** — `closed` (terminal stage: Lost / Unqualified / Closed Won) → `no_next_action` (no open follow-up) → `overdue` (next action past due) → `on_track`.
  - **`lost_at` / `lost_reason`** — only in a Lost / Unqualified stage; reason from the most recent follow-up that recorded one, date from that follow-up (falling back to the last completed follow-up). Cleared otherwise.

  A BEFORE-fill trigger recomputes on every write to a client; an AFTER trigger on **follow-ups, calls, and chats** touches the linked client so the set stays fresh — self-healing across complete / reschedule / delete / move and every create path (UI, client-side workflows, the on-due sweeper, direct DB writes). So "Next Action visible on the client" — plus the activity / health / lost signals — is delivered at the database layer, not by workflow `update_record` actions. Migrations: `supabase/migrations/2026-06-17_client_next_action.sql` (trio) + `2026-06-17_client_derived_fields.sql` (extends it to the activity / lifecycle / lost fields + the calls/chats touch).
- **Extended stage/status taxonomy (added 2026-06-17; two more added 2026-06-21).** `client_stage` gained two **side-exit** stages — **خاسر (Lost)** and **مغلق ناجح (Closed Won)** — joining the existing lifecycle stages. `client_status` gained ten new Arabic values used along the lifecycle: رقم خاطئ (Invalid Number), مكرر (Duplicate), تم رفض العرض (Offer Rejected), يحتاج معلومات تمويل (Needs Financing Info), نقاش عائلي (Family Discussion), بانتظار القرار (Waiting Decision), تم إرسال واتساب (WhatsApp Sent), إعادة تواصل لاحقًا (Recontact Later), بارد (Cold), بانتظار دفعة الحجز (Waiting Reservation Payment) — plus two from the after-visit expansion (2026-06-21): **زار مشروعًا آخر — للمراجعة** (Visited another project — review; an at-risk state, NOT auto-lost, that creates a Sales-Manager review task) and **تعذّر التواصل بعد الزيارة** (Unreachable after visit; terminal after the no-answer cap). Stored values equal the Arabic labels (canonical). A client in any terminal/side-exit stage (Unqualified / Lost / Closed Won) is excluded from the "no next action" health metric.
- **Latest visit-rating mirror (added 2026-06-21).** After a client rates a registered visit (1–5 via the public link), the latest score is mirrored onto the client as **`latest_visit_rating`** + **`latest_visit_rated_at`** — a convenience pointer for the account view only. The authoritative per-visit score lives on the visit (`visit_rating`); all analytics read the visit-level value, never this mirror. Written by the `submit_visit_rating` RPC. See [visit-rating.md](visit-rating.md).
- **Client preferences are also editable from the Follow-up Workspace (added 2026-06-17).** The Workspace's sidebar now shows the five preference fields (unit type, budget, city, direction, district) inline and lets the rep edit and save them straight onto the client record mid-call — and its "View Client" / "Edit Full Preferences" buttons open the full client form in a modal (with an "Open full page" hand-off) rather than navigating away. The Client 360 view itself is unchanged (still read-only inside the Client Details tab). See [followups-workspace.md](followups-workspace.md).
- **Migration for existing installs.** `healClientsSchema` in `src/lib/schemaMigrations.ts` runs on every `initialize()`. It detects the absence of either `whatsapp_history` or `call_history` field types in the user's stored clients model and APPENDS the missing sections from the seed (matched by `label_en`, ordered after the highest existing section order). Idempotent — no-op once both field types are present. Records are untouched (no field on them stores anything for these types). Newly-customized clients models that were edited in the Builder before this rollout still get the new sections appended without losing the customizations.

## User flows
1. **Brief myself before calling a client (happy path):**
   1. Agent opens a Follow-Up record from their queue.
   2. Tab strip shows because the Follow-Up's `client_id` is populated → click **Client Details**.
   3. Page swaps to the embedded client view: client basics, preferences, then WhatsApp History (every chat across every of our numbers, with device labels), then Calls (every Hatif log on this client's phone), then Related Records (every Visit, Appointment, Phone Call record that points at this client).
   4. Agent scrolls the chat history, reads the latest call's transcript, then clicks the Form tab to log the next follow-up.
2. **Open a client directly:**
   1. Sidebar → Clients → pick a row.
   2. Tab strip is visible (record exists, model is clients). Form tab is active by default.
   3. Scroll past the basics into the new WhatsApp History section — messages render exactly like the dedicated chats UI (same `MessageBubble` component, same Realtime subscription).
   4. Below that, Calls — every call from any of the client's phones, deduped by call id.
3. **Two clients on one record:**
   1. A record has two populated lookups pointing at clients (e.g. a deal record with buyer + seller).
   2. Click **Client Details**. The Client switcher chip strip appears with both client names.
   3. Click the second chip → URL becomes `?tab=client&client=<id2>` and the embedded view re-renders for the second client.
   4. Browser back returns to the first client's embedded view.
4. **Empty states:**
   - On `/new` (no record id yet): the in-section panels show "Save the record first to view this section."
   - Client has never WhatsApp'd us: WhatsApp History shows "No WhatsApp conversations linked to this client yet."
   - Client has never been called via Hatif: Calls section shows "No calls logged for this client yet."
   - No other model references the client: Related Records shows "No records in other models reference this client yet."

## Data touched
- **Reads:** `models` (to find clients + every model with a lookup at clients + the `client_property_options` model); `records` (the client's own record + every candidate cross-model record + the client's saved `client_property_options` rows for the Options tab); `chat_messages` (via `chatMessages` slice, populated by the global `subscribeToAllChats` Realtime channel); `call_logs` (via `CallHistoryPanel`'s per-phone `listCallsForPhone` + Realtime subscription).
- **Writes:** the 360° view is read-only EXCEPT the **Options tab**, which writes `client_property_options` records (add manually via `AddOptionModal` with `added_from='manual'` / set main / change status / eliminate-with-reason / reactivate / edit sales notes) through the version-aware `saveRecord` path. NEW options come from the Project Finder OR the tab's own manual picker — always user-triggered. Edits to the client itself happen on the client's own record page (Form/Preferences); edits to a related record happen on that record's page.
- **Storage shapes:** the new section field types `whatsapp_history` and `call_history` store **nothing** on the record — they're virtual. Freeze SKIPS them, `regenerate_model_view` SKIPS them, no `required` toggle, no `show_in_table`.
- **Sales OS fields** (`client_owner`, `next_followup_id`, `next_action_type`, `next_action_due_at`, `last_activity_at`, `lost_reason`, `lost_at`, `lifecycle_health`) live on `records.data` like the rest of the client schema (clients is unfrozen). The stage/status/owner/lost fields are written by the Sales Lifecycle workflows; the **next-action trio** (`next_followup_id` / `next_action_type` / `next_action_due_at`) is written by a SECURITY DEFINER Postgres trigger pair from the client's earliest open follow-up — read-only, never set by hand or the Client 360 view. Base fields added by `supabase/migrations/2026-06-16_sales_os_phase1.sql`; the next-action triggers + the `read_only` flagging by `supabase/migrations/2026-06-17_client_next_action.sql`.

## Open questions / known limitations
- **Client Details is read-only.** Editing a client from inside another record's Client Details tab isn't supported — the user has to click through to the client's own page (which is what clicking a row in the Related Records tables does). The Related Records tables are themselves read-only for the same reason — edits to a related record happen on that record's own page. Saves a lot of complexity around mirrored writes; revisit if the workflow proves slow.
- **Related Records is in-memory.** The cross-model query reads from the Zustand `records` slice. Models that haven't been loaded yet (e.g. a model not on the chrome-critical tier and the record was opened before the slow tail finished) won't show their references until the slice fills in. Acceptable in practice because boot is fast and the panel re-memos when records change.
- **Multi-client chip strip is unsorted.** Chip order follows the order lookups are walked (section order × field order); if a record has two unrelated clients on different sections, the user might prefer alphabetical. Cheap fix when someone asks.
- **WhatsApp History per-device labels depend on `whatsapp_numbers` overlay.** Devices without a friendly name fall back to phone or device id. Configure friendly names in `/settings/whatsapp-numbers`.
- **No "linked client" CTA on a record without a client lookup.** If a model has phone fields but no lookup-into-clients, the tab strip never appears even though the record could conceptually be associated with a client. Adding a lookup field via the Builder is the documented path.
