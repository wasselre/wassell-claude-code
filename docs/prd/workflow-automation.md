## What it is (in plain English)
Workflows let users automate repetitive work without writing code. A workflow has a single **trigger** (what starts it — e.g. "a new Client record is created"), then a tree of **branches**. Each branch is an if / else-if / else arm with its own **conditions** (only run if X is true) and its own **actions** (do these things — send a notification, update a field, create another record, assign to someone). The engine walks branches top-to-bottom and runs the first one whose conditions all pass. It's like Zapier built into the CRM and aware of the user's models, with real branching so a single rule can express "if hot lead do A, else if warm lead do B, else do C".

## Why it exists
Real-estate teams have lots of standard follow-up rules: "when a new lead comes in, create a follow-up task and assign it to the sales lead who owns the region". Hardcoding these would not scale across customers, so we expose them as data.

## Key behaviors
- URL: `/workflow` (list), `/workflow/:workflowId` (editor).
- **Editor surface** is a **node canvas** (React Flow / `@xyflow/react`). Every condition and every action is a separate node; branches are swim-lanes rendered as group nodes. Trigger sits at the top as a single amber node, with smooth bezier edges fanning down into the first node of each branch. Each edge carries a "+" affordance at its midpoint that opens a picker to insert a new condition (before all actions, non-else branches only) or a new action at that specific spot. Clicking a node opens a right-side slide-in drawer (480px wide; mirrors in RTL) that hosts the existing embedded editor for that one node — condition rows, action-type-specific config, or trigger picker — so the canvas stays readable while detail editing happens in a focused panel. Layout is auto-derived from the branch tree every render (no persisted positions) and the canvas ships with zoom/pan controls and a minimap.
- **Triggers** fire on record-level events on a chosen model: `on_create`, `on_update`, `on_delete`, via a declared `webhook` endpoint, on a custom `button_click`, or — for the `followups` model only — `on_due`. The `on_due` trigger fires when a follow-up's `scheduled_datetime` arrives in the past, driven by the `/api/sweep-due-followups` Vercel cron (every 5 minutes). Each row is stamped with `data->>'fired_at'` once the sweeper claims it so it never fires twice. v1 supported actions on `on_due`: `update_record`, `create_record`, `send_whatsapp_message`. Other action types fail loudly with `unsupported_in_sweeper` so missing coverage is visible. Reminder: `on_due` only appears in the trigger picker when the selected model is `followups`.
- **Branches (if / else-if / else)** are the new primary unit of control flow. A workflow always has at least one branch; the editor starts new workflows with a single branch. The user can add more non-else branches (each acts as an "else if"), and at most one final **else** branch that runs when no earlier branch matched. Branches are evaluated strictly top-to-bottom and short-circuit: once one wins, the rest are skipped. Each branch has an optional display name ("Hot lead", "Warm lead") that shows up in the editor and the run detail page.
- **Conditions** live inside a branch and are boolean checks over the triggering record's field values, joined by the branch's `condition_mode` — `'all'` (AND, the default) means every condition must pass, `'any'` (OR) means at least one must pass. The drawer shows an AND/OR toggle above the list once the branch has 2+ conditions; the canvas card's connector chip between rows mirrors the chosen mode (blue "AND" / amber "OR"). Operators supported: equals / not-equals / contains / intersects / greater / less / is-empty / in-list. `contains` treats arrays as supersets (left contains all of right) and falls back to substring for strings; `intersects` returns true when the two sides share at least one element (scalars are treated as singletons). A branch with zero conditions always matches (useful as a catch-all without using the explicit `else` branch).
- **"Only on change" condition mode** (per condition, only meaningful for `on_update`): when checked, the condition passes only on the false→true transition. Editing a record without flipping that condition does not re-fire the rule, which prevents duplicate runs from repeated saves while the condition remains true.
- **Actions** run sequentially and can:
  - Update a field on the triggering record
  - Update a record in any model: pick the target model, pick the field to search by, and give the match value. The match value has its own source toggle — either a **static value** (type it directly) or a **field on the trigger record** (pick from a dropdown). Example: a Follow-Up is created with `client_id = X`, and the workflow updates the matching Client record by searching `id = {trigger.client_id}`. **Lookup-aware matching**: when the trigger field used as the match source is a single lookup pointing at the target model, the stored value is the target record's internal UUID, so the engine matches by record id directly. The run detail page labels this with "Match strategy: by record id" so it's obvious why the match succeeded even though the configured filter field would never equal a UUID.
  - Create a record in another model (with field mappings from trigger record). Optional **"skip if exists"** guard: pick one of the mapped target fields as a dedup key, and the action will not create a duplicate when an existing target record already has the same value in that field.
  - Assign the record to a user, role, or dynamic role-field value (see access-control.md). When assigning by role, each role-field condition (the "where role fields equal…" row) can compare against either a **static value** or a **field on the trigger record** via a per-row source toggle. Example: find a sales consultant whose role `projects` field intersects with the client's `preferred_projects`. The full operator set (equals / not-equals / contains / intersects / greater / less) is available here too.
  - Send a notification (toast)
  - Send an HTTP request to an arbitrary URL
  - **Fire an automated phone call (`outbound_ivr`)** through Hatif: pick the phone field on the trigger record to dial, choose TTS or a pre-uploaded audio file as the message, define ≥1 DTMF menu option. Hatif's webhook writes the call row (including the digit the customer pressed) into `call_logs`, where the Call History panel on the client record shows it with summary + recording + DTMF label.
  - More action types can be added in `src/lib/workflowEngine.ts`
- **Field mapping value sources** for create/update actions: static value, field from the trigger record, current date, current user, trigger record ID, role variable (assignees only), **date expression** (only offered when the target field is `date` or `datetime`), and **formula**. A formula is a live computation written in the same grammar as the `formula` field type — `{field_slug}` tokens reference fields on the trigger record, and the expression supports basic math (`+`, `−`, `×`, `÷`), comparisons, and the `IF` / `CONCAT` / `DAYS` / `ADD_DAYS` / `ROUND` / `ABS` / `MIN` / `MAX` / `SUM` functions. Range fields expose `{slug.min}` and `{slug.max}` sub-tokens. The builder shows inline parse errors and flags unknown field refs. At run time the engine evaluates against the trigger record's `data`; error sentinels (`#ERR` / `#DIV0` / `#REF` / `#CYCLE`) resolve to `null` so records stay clean, and numeric strings are coerced to numbers when the target field is `number` or `currency`. Common use: compute a commission from `{price}`, pro-rate a fee from `{qty} * {unit_price}`, or concatenate a display label from several fields. **Assignee target fields** (type `assignee`, the 👤 ones) get a tailored source set instead of the full list: **Specific user** (static), **From Trigger Record** (copy a user id off the triggering record — e.g. carry the previous follow-up's `sales_rep` onto the next one), **Current user** (whoever triggered the workflow), and **Variable by role** (dynamic by role-field conditions). The *From Trigger Record* + *Current user* options were added 2026-06-23 — the engine already resolved those values into assignee fields, the editor just hadn't surfaced them for assignee targets. A date expression takes a base date — either the current date or a date field on the trigger record — and applies one or more offsets. Each offset is built in the UI from three controls: an operation dropdown (add `+` / subtract `−`), a number input, and a unit dropdown (minute, hour, day, week, month, year). The user can chain multiple offsets via "+ Add offset", and they are serialized to a string of tokens like `+5d`, `-2w`, `+3mo`, `+1y`, `+2h`, `-30min` joined by spaces (e.g. `+5w -2h`). An optional **"Set time of day"** checkbox below the offsets exposes hour + minute inputs that emit a trailing `@HH:MM` token (e.g. `+0d @10:00` for "appointment date at 10:00 AM local"); the time-of-day always applies last so the chosen date keeps it. The engine parses the tokens and writes the result formatted for the target field type: `YYYY-MM-DD` for `date`, `YYYY-MM-DDTHH:MM` (local time) for `datetime`, so the HTML form inputs re-hydrate it correctly. `current_date` is formatted the same way.
- **Orphaned multi-value entries are surfaced (fail-loudly).** For `multiselect` / `section_selector` fields, the static-value and condition-value editors render one checkbox per *current* option. Any stored array value that matches no current option — e.g. an option whose value drifted or an option that was deleted — is shown below the checkboxes in a red "⚠ Unknown values (match no current option)" block, one removable chip per value; clicking the × drops it from the array. This stops orphaned values from sitting invisibly in a saved workflow and being re-written into every record the action creates (see CLAUDE.md "Silent Failures"). The engine's write path stays orphan-tolerant by design — this is purely an editor-visibility safeguard.
- **Execution** happens client-side right after the record save resolves for the `create` / `update` / `delete` / `webhook` / `button_click` triggers. `on_due` is the lone exception: it runs server-side from a Vercel cron because the firing time is decoupled from any user interaction. The workflow engine walks triggers, evaluates conditions, runs actions, and surfaces toasts on success/failure.
- **`on_due` runs now appear in the Workflow Logs.** The server-side mini-engine writes a full `workflow_runs` row for every on_due execution — the same rich trace the client engine produces (branch + condition traces, per-action traces with resolved field mappings, created/updated record ids, status). It uses the existing closed `WorkflowRunStatus` union: an action that isn't supported by the sweeper is recorded as a per-action `failed` entry with reason `unsupported_in_sweeper`, which rolls the run up to `partial_success`/`failed` (no new status invented). The row is realtime-published, so the Logs page shows on_due runs without a reload. A logging failure never fails the sweep — the workflow already executed; the miss is logged loudly to the cron logs. **Caveat:** the sweeper cron is currently inert in production (no `CRON_SECRET`), so no on_due runs are produced yet — see Open questions.
- **Enable/disable** toggle per workflow — disabled workflows don't fire.
- **Workflow can be bilingual** — Arabic/English name and description.
- **The "Sales Lifecycle" group is the engine of the Sales Operating System.** Twelve workflows (W1–W12) in the **دورة حياة المبيعات (Sales Lifecycle)** group automate the whole guided sales process — they react to a completed follow-up / a new appointment / a new offer / reservation / financing / ownership-transfer and do every client stage/status move plus create the next task. No sales transition is hardcoded in React: the Workspace/Queue/Studio write the trigger record and these workflows do the rest. Each is tagged with `metadata = { managed_by: 'sales_process_studio', sales_stage, activity_type, compatibility }`, which the Sales Process Studio reads to show "which workflow implements each activity" and to detect drift (a Studio-generated workflow later hand-edited here). The per-workflow table (triggers, branches, what each does) lives in [sales-process.md](sales-process.md); branch-level detail is in the auto-generated `docs/prd/workflows/` PRDs. Editing one of these here is fine — the Studio only reads, it never overwrites — but a hand-edit changes its shape hash and the Studio will badge it "Advanced."
- **`workflow.metadata`** is a free-form JSONB column (added with the Sales OS) that round-trips automatically through the workflow row. It's used today for the Studio binding above; any future "tag a workflow" feature can hang data off it.
- **The `on_due` sweeper can only time off `scheduled_datetime`, so deadlines are baked into that field.** The sweeper fires a follow-up's `on_due` workflows when its `scheduled_datetime` passes — it can't time off any other field and it can't detect inbound replies. The WhatsApp two-phase flow exploits this: when a rep sends a WhatsApp, the Workspace repurposes `scheduled_datetime` as the **escalation deadline** (attempt 1 → +24h, attempt 2 → day 5) and parks the follow-up in a waiting state. "No response" is simply that waiting state surviving to the deadline. The escalation workflow gates on `whatsapp_state`, so a follow-up that recorded a reply before the deadline is skipped.
- **The self-stamped `source_followup_id` pattern lets an `on_due` workflow close its own trigger record.** An `on_due` workflow's trigger record is the follow-up that came due, but the engine's `update_record` action matches a target by a *field filter*, not by "the trigger record." So at send time the Workspace stamps `source_followup_id = the follow-up's own id`, and the escalation workflow updates the followups row whose `id = {trigger.source_followup_id}` — i.e. itself. This is the general recipe for an `on_due` workflow that needs to mutate (complete/close) the very record it fired on. The companion **WhatsApp Response Completed** workflow is an ordinary `on_update` followups workflow that runs the reply-outcome transitions when the rep records the customer's answer.

## User flows
1. **Create workflow:** `/workflow` → "+ New Workflow" → editor opens with an inline trigger picker (model + event). As soon as the trigger is valid, the node canvas mounts with the trigger node on top and one empty IF lane below it.
2. **Configure trigger:** Pick a model + event; for webhook triggers, pick a declared endpoint. Clicking the trigger node on the canvas later opens the full trigger editor in the right-side drawer.
3. **Fill the first branch:** Click the "+" on the edge between the trigger and the lane to insert a condition or an action. Each new node opens the drawer automatically, preselected and ready to configure. Keep adding via the "+" on any edge between siblings or at the lane's tail.
4. **Add more branches (optional):** "Add branch (else if)" inserts another swim-lane to the right of the last non-else lane. "Add default case (else)" pins a trailing OTHERWISE lane. The lane header exposes duplicate + delete buttons; duplicate on an else lane is disabled because only one else is allowed, and delete is disabled on the last remaining non-else lane.
5. **Edit a node:** Click any condition / action / trigger node → the right-side drawer slides in with the existing embedded editor for that one node. Changes propagate to the workflow as you type and re-render the summary text on the node in real time. Close the drawer via Escape, X button, or clicking the backdrop.
6. **Delete a node:** Click a node then press Delete (or use the trash icon that appears on hover). The neighboring edges auto-reconnect since the chain is derived from the tree; no dangling connections.
7. **Save & enable:** Toggle "Enabled" → save → matching events fire the workflow and the engine picks the first winning branch. Legacy `conditions` / `actions` fields on the workflow row are still mirrored to the first non-else branch on save, so older consumers keep working.
8. **Debug a workflow:** Disable, trigger manually via record edit, re-enable when fixed. Open a run in the log to see the full branch trace — which arms were evaluated, which passed, which won.

## Open questions / known limitations
- **`CRON_SECRET` is set in Vercel** and both `on_due` sweepers are live in production (probing either endpoint without a bearer returns `401`, not the `500` it returns when the secret is unset). The endpoint still refuses to run without auth — a public sweeper would be a DoS vector.
- `on_due` now drives two sweeps: the `followups` sweeper (`scheduled_datetime`, every 5 min) and the appointments no-show sweeper (`appointment_date + 24h`, every 30 min). The execution engine (`runOnDueForRecord`) is model-agnostic — it runs any active `on_due` workflow whose `trigger_model_id` matches the fed record — so each sweep only needs its own "which rows are due" query (inline for followups, the `appointments_due_for_noshow()` SQL function for appointments). Generalizing the *due-row query* to any model + configurable date field is still a future iteration.
- The mini-engine intentionally supports a narrow action surface (`update_record`, `create_record`, `send_whatsapp_message`). Other action types fail loudly with `unsupported_in_sweeper` rather than silently skipping; lifting the rest of the engine to the server is a follow-up.
- Field-mapping sources `current_user`, `role_variable`, and `formula` resolve to `null` on `on_due` (no user context in cron; no formula engine ported yet) and emit a console warn. Fine for v1 since the v1 use cases don't need them; revisit when they do.
- Execution logs exist for both client-fired runs and `on_due` sweeper runs — see `docs/prd/workflow-logs.md` — capped at 500 most-recent runs per installation.
- The appointment no-show flip runs server-side via `record_save`, so it does NOT fire the client-side "No-Show Recovery" workflow (W5, trigger `update`, which only runs on browser saves). To keep the automatic and manual no-show paths identical, the auto-no-show on_due workflow **reproduces W5's two actions itself** (set client `client_status` → لم يحضر الموعد + create a `no_show_recovery_call` follow-up) as a deliberate copy — workflows are JSONB rows and can't share logic, so the migration + the W5 generated PRD both carry a "keep in sync with W5" note. The flip action runs FIRST and is version-guarded; on `version_conflict` the engine aborts the remaining client-move + recovery actions (`runWorkflow` action loop), so a lost race never produces a spurious recovery for an appointment a human just resolved.
- A visit registered after an auto-no-show still advances the client normally: W6 ("Visit → After-Visit", `create` on `visits`) gates only on `client_id is_not_empty` and unconditionally sets `client_stage` → زيارة — it never reads the appointment status, so the prior no_show cannot block it (identical to the manual-no-show → visit path).
- Loops / recursion protection is bounded by a depth limit (3) in the engine and by the per-condition "only on change" mode, but cycles between two workflows that flip each other's fields are still possible.
