## What it is (in plain English)
A two-pane WhatsApp inbox inside the Wassell app. The left pane is the list of every conversation synced from a connected WhatsApp number; the right pane is the open conversation — message history, an image/document composer, and a status + labels header. Staff can reply from the browser, start new chats to numbers they've never messaged, attach images and documents, mark conversations resolved or archived, and see each conversation auto-linked to the matching Client record. New inbound WhatsApp messages appear in the list and the open thread live — no refresh needed.

Chat traffic itself runs through **Haberchat** (`api.haber.chat/v1`), a WhatsApp Business gateway. The app never talks to Haberchat directly — a set of Vercel serverless functions in `api/haberchat/*` proxy every call server-side so the Haberchat API token stays off the client. A webhook handler receives every inbound message + ack update, writes them to Supabase, and Supabase Realtime pushes them to every open browser tab.

## Why it exists
Real estate sales pipelines in Saudi run on WhatsApp. Before this module, staff replied from their personal phones and copy-pasted summaries back into the CRM. Now every conversation lives next to the matching Client record, is searchable, is assignable, and becomes a first-class record the rest of the app (workflows, dashboards, reporting) can act on.

## Key behaviors
- **Sending never blocks typing (fix 2026-08-18).** Pressing Send hands the message to the BACKGROUND and clears the box immediately — the textarea stays enabled and focused, so the rep can type and send the next message while the previous one is still in flight. There is no global "sending" flag any more: progress is **per message**, shown on that message's own optimistic bubble in the thread (clock → single tick → delivered/read, or a red **«لم تُرسل» / "Not sent"** state). Every send is bound to the conversation identity captured at the moment it was dispatched, so an in-flight send can never land in a chat the rep has since switched to. Attachments still upload before their message goes out (that is inherent), but the composer is free the whole time.
- **A failed send is loud, and never eats the text (fix 2026-08-18).** A message whose send fails keeps its bubble in the thread, outlined red, labelled «لم تُرسل» / "Not sent", with a **«إعادة المحاولة» / Retry** button that re-sends the identical payload (`retryChatMessage` — it drops the failed bubble and dispatches a fresh one with a new idempotency key; if the retry itself cannot produce a bubble, the original is put back, so Retry can neither lose nor duplicate the message). Failures that happen BEFORE any bubble exists — an attachment upload that never reached the send, a scheduled send the queue rejected — are toasted AND parked in a red strip above the composer with a **«استعادة» / Restore** button that puts the text and attachments back in the box (appended below anything typed since, never replacing it).
- **The composer only exists once the conversation identity is RESOLVED (fix 2026-08-18).** A conversation needs four things before it can be sent on — the record, its `wid`, its recipient `phone`, and a send-from device — and they arrive at different times (`wid`/`phone` when the chats list or the inbound webhook fills the record; the device overlay from a separate fire-and-forget load at boot). `resolveConversationIdentity` (`src/pages/Chats/lib/conversationIdentity.ts`) collapses them into ONE value: `ready` / `loading` / `unsupported` (group or channel) / `incomplete` (`missing-wid` | `missing-phone` | `no-device`). `ChatDetail` mounts `Composer` **only** for `ready` and passes the resolved identity by value; every other state renders a short bilingual notice instead (spinner + «جارٍ تحميل المحادثة…» while loading, an explicit reason otherwise). It is gated on identity ALONE — never on a previous send being in flight. **The bug this fixes:** the composer was enabled as soon as the record existed, so on a freshly-created or webhook-created chat a rep could type and send inside the resolution window; `sendChatMessage` then threw its identity error BEFORE creating the optimistic bubble, the composer had already cleared itself, and for a plain-text send nothing at all was toasted — the message simply vanished. `sendChatMessage` now returns those failures instead of throwing early: the bubble is created first, then marked failed with a toast, so even a race that slips through is visible and retryable.

Mirroring is triggered by `records_enqueue_listing_mirror` on insert / image_urls change (the weekly reconcile's price-and-sold updates don't re-fetch anything), and the pre-existing 51k listings are filled in by the deliberately throttled operator script `scripts/backfill-listing-mirrors.mjs` — see the cost note in its header. **The image proxy stays** (it is the only working egress from Fly, so it is what the mirror itself downloads through, and it remains the fallback). Kill switch + per-listing photo cap: `listing_mirror_settings`.
- **Multi-media WhatsApp send is SERVER-SIDE (2026-07-19; was browser-side since 2026-06-30).** A template's images + videos are sent as their own WhatsApp messages after the text. The picker merges the sources into one ordered send list (`templateImageSends` in `TemplatePickerModal.tsx`): a project template's `project_image_file_ids` (CRM `files` ids) and a listing template's cleaned `images[].public_url` + curated `videos[]` (public marketing-assets URLs). `src/lib/projectMessageImages.ts#sendProjectImageMessages(chatWid, refs)` now makes ONE small keepalive POST to **`/api/whatsapp/send-media-batch`** (nodejs, maxDuration 300): the endpoint RLS-checks + service-signs CRM file ids, passes raw URLs through, and sequentially gateway-sends each item — WAHA fetches the bytes itself, so no media flows through the browser or the function. REFRESH-SAFE: once the request lands, the server completes the fan-out even if the tab closes (the old in-tab fetch→upload→send loop died on refresh — live incident 2026-07-19: a listing message's text sent, zero of its media followed). Scheduled sends stagger each item +(i+1)×10s after the text via the scheduled_whatsapp_jobs queue (signed URLs padded to outlive delivery). - **A new inbound message pushes the assigned salesperson's phone (new 2026-08-18).** The moment a customer's message lands in `chat_messages`, an AFTER-INSERT trigger (`chat_messages_enqueue_push`, `SECURITY DEFINER`) enqueues «💬 رسالة واتساب جديدة» to the existing `push_outbox` queue and the Fly worker delivers it as Web Push — so a rep with the app closed still hears about it. Body is the client's name plus a preview of the message («صورة» / «رسالة صوتية» / «مستند» … for media); tapping it opens that conversation at `/model/chats/:conversationId`. **Why a trigger and not the webhook:** `chat_messages` is the one place every inbound message lands whatever wrote it (the WAHA webhook, a chats-list sync, a backfill, a future provider), so a webhook-side enqueue would silently miss the other paths. **Recipient resolution**, each rung falling through to the next: the conversation's mirrored `client_owner` → the linked client's own `client_owner` → a phone match against Clients (only when the conversation record doesn't exist yet, because ingest writes the message *before* it upserts the conversation) → the chat's own `owner` assignee. **Nothing resolved means no push — never an error**, and most inbound traffic is on chats with no linked client at all (266 of 436 messages linked over 30 days as of 2026-08-18; 92 of those on a client with an owner), so silence there is intentional. **Bursts collapse**: one `tag` per conversation makes the phone replace the previous alert instead of stacking, and a `dedupe_key` bucketed to 5 minutes of the *message's own* timestamp turns five rapid messages into ONE queue row. Outbound echoes, reactions, WhatsApp system events, and anything dated more than 15 minutes ago (a history import) never enqueue. It also steps aside when the same message is about to fire the follow-up engine's **customer replied** alert for the same rep and client, so one event never buzzes twice. Admin kill switch alongside the other two built-ins at `/profile → الإشعارات` (`push_builtin_settings.whatsapp_inbound_enabled`, defaults ON). Migration: `supabase/migrations/2026-08-18_09_whatsapp_inbound_push.sql`.

## User flows
1. **Reply to an inbound message (happy path):**
   1. WhatsApp user sends a message to the Wassell number.
   2. Haberchat fires `message:in:new` webhook → handler writes to `chat_messages` + bumps the parent record.
   3. Realtime pushes the insert; the list row reorders, unread pill appears. Agent clicks it; thread loads history + shows the new message; unread zeroes.
   4. Agent types a reply, presses Enter; the box clears instantly and an optimistic bubble appears (clock) while the send runs in the background — the agent can immediately type the next message. Webhook + Realtime progress that bubble to sent → delivered → read. If the send fails, the bubble turns red («لم تُرسل») with a Retry button and the reason is toasted; the text is never lost.
   5. If the conversation's identity has not finished resolving (no `wid`/`phone` yet, or the device list is still loading), the composer is replaced by a short bilingual notice until it does — the agent cannot fire a send into a half-resolved conversation.
2. **Start a brand-new chat:**
   1. Click `+` in the list header. The modal opens on the **Existing client** tab.
   2. *Existing client:* search the Clients model (all fields or a scoped field), pick a client → its `client_code • name • phone` shows and the phone auto-fills (read-only). *Manual number:* switch tabs, pick a country code + enter the number (any local format works — `+966` default).
   3. Compose: type free text, and/or click **Insert template** to drop a template's text into the box (appended below any existing text) and edit it before sending.
   4. Send → local record created (linked to the chosen client when one was picked, else phone-matched), first message posted; navigation lands on the new detail pane; the webhook echo reconciles the actual wid.
3. **Resolve a finished conversation:**
   1. Open the chat.
   2. Click the status pill → pick "Resolved".
   3. Status updates optimistically; Haberchat receives the `action: resolve` patch; the chat stays in the list but the header badge is gray.
4. **Turn an unlinked chat into a lead (assisted, 2026-07-21):**
   1. A message arrives from an unknown phone. The chat's header shows **«إضافة كعميل»** next to **«إضافة جهة اتصال جديدة»**.
   2. Agent clicks **«إضافة كعميل»** → `LeadIntakeModal` opens with name + phone prefilled → Approve creates the client (the First-Follow-up workflow makes the booking-call task; the relink sweep attaches the chat).
   3. The modal then asks how to start: **Call now** (booking task pulled to NOW — top of My Tasks with the hot-lead countdown) or **Keep in WhatsApp** (booking task cancelled; a "your turn" WhatsApp task is created since the client wrote first).
   4. **The conversation is renamed to the client's name** (list row, header, avatar) and the header shows a «عميل مرتبط» pill — clicking it (or the avatar / name) opens the full client record in a new browser tab — plus the client's detailed preference chips. (The old manual path — the "create client" CTA opening the raw clients form, with the save-hook sweep back-filling `client_link` — still works.)

4b. **Save an unlinked chat as a plain contact (2026-08-10):**
   1. A message arrives from someone who is neither a buyer nor a real-estate office — a supplier, a maintenance contractor, a government office. The header shows **«إضافة جهة اتصال جديدة» / "Add a new contact"**.
   2. Agent clicks it → `ContactIntakeModal` opens with name + phone prefilled; company / position / notes are optional. If that number is already in the address book, the modal says so before saving.
   3. Save → a `contacts` record is created. No client, no follow-up task, no stage.
   4. **The conversation is renamed to the saved name** — list row, thread header and avatar letter all switch from the WhatsApp push name (or the bare number) to it. A **«جهة اتصال»** pill appears in the header (click → the contact record) with a matching chip on the row, and the "Add a new contact" button disappears. The chat stays in the **Other** tab.
5. **Send an image:**
   1. Click paperclip → pick an image.
   2. Preview chip shows filename + size. Type optional caption. Send.
   3. Upload runs through the proxy (spinner on send button); on success, `sendChatMessage` posts with the returned `mediaFileId` + inferred `kind: 'image'`. Outbound bubble renders the image inline.
6. **Empty state (no numbers connected):**
   - The list shows "Conversations will appear here as new messages arrive" and sends fail with "no WhatsApp device configured — set a default in Settings". Admin opens `/settings/whatsapp-numbers` → refreshes the list from Haberchat → picks a default.

## Data touched
- **Reads:**
  - `models` (finds the `chats`, `clients`, and `chat_templates` system models), `records` (conversations for the chats model; clients records for auto-link AND the Start New Chat client picker; `chat_templates` records for the template inserter; `followups` records for the Clients-tab **Waiting for reply** filter and the Log-interaction modal's open-task lookup).
  - `chat_messages` via the global Realtime subscription + direct per-chat queries from the `listMessages` proxy pass-through (history loads come from Haberchat directly, not from this table — the table is populated by the webhook only).
  - `whatsapp_numbers` (overlay for device friendly names + default).
  - Haberchat (via proxy): `GET /chat/{deviceId}/chats`, `GET /chat/{deviceId}/chats/{wid}/sync`, `POST /files`, `GET /chat/{deviceId}/files/{id}/download`, `POST /messages` (optionally with `deliverAt` for scheduled sends), `GET /messages?status=queued&devices=…` (scheduled strip), `DELETE /messages/{id}` (cancel a scheduled message), `PATCH /chat/{deviceId}/chats`, `GET /devices`.
- **Writes:**
  - `records` (chats conversations — id = uuidv5(chat_wid)); `records.data` fields: `wid`, `name`, `phone`, `kind`, `device_id`, `status`, `owner`, `labels`, `unread_count`, `last_message_at`, `last_message_preview`, `last_message_flow` ('in'/'out' — direction of the newest message, stamped by the webhook + the SPA Realtime bump; drives the "Needs reply" filter), `client_link`, `client_owner`.
  - `client_owner` is a **read-only mirror** of the linked client's `clients.client_owner` (a `public.users.id`), kept in sync by DB triggers — NOT user-editable. Its purpose is per-rep chat visibility: because the view-scope engine can't traverse the `client_link` lookup, this stamped field lets an admin scope the chats model in Settings → Profiles with plain conditions — `client_link is not empty` ("only client-linked chats", hides advertisers/contacts/other) and/or `client_owner equals current user` ("only my own clients' chats"). The mirror is maintained by `records_fill_chat_client_owner` (BEFORE-fill on the chat: pulls the linked client's owner) + `records_sync_chats_on_client_owner` (AFTER-sync on the client: re-stamps linked chats when the client's owner changes / the client is deleted). Off by default — no profile carries the scope until an admin sets it. `chat_messages` + the `whatsapp_ai_*` sidecars already defer to the chats view-scope class (`wassell_chat_scope_class`), so restricting the list restricts message bodies + the live feed too. Migration: `supabase/migrations/2026-08-14_chat_client_owner_mirror.sql`.
  - `chat_messages` (webhook only, via service role — bypasses RLS). Columns include `subtype` (Haberchat message subtype; discriminates system events for rendering).
  - `push_outbox` (one row per inbound-message alert, written by the `chat_messages_enqueue_push` trigger — never by the app). Reads `push_builtin_settings.whatsapp_inbound_enabled`, the conversation record's `client_owner` / `client_link` / `name` / `owner`, the linked client's `client_name` / `client_owner`, and the client's open `followups` (only to avoid double-notifying alongside `customer_replied`).
  - `whatsapp_numbers` (admin on the Settings page).
  - `followups` records **server-side via the activity-bridge reconcilers** (`reconcile_outbound_whatsapp` / `reconcile_inbound_whatsapp`, called from the webhook with the service role): waiting-state stamps, reach-out-task cancellations, and bridge-created tasks (`creation_source` = `outbound_whatsapp` / `inbound_whatsapp`).
  - `clients` + `followups` records from the two header modals via the normal store `saveRecord` (Lead intake: new client + booking/WhatsApp task adjustments; Log interaction: task completion or create-then-complete — outcome workflows fire on these saves).
  - `contacts` records from the header's "Add a new contact" modal via the normal store `saveRecord` (`name`, `phone`, optional `company` / `position` / `notes`). Nothing is written to the chat record — the chat↔contact tie is recomputed live by phone match on every render.
  - `clients` + `client_attributions` records **server-side via `mos_capture_ad_acquisition`** (SECURITY DEFINER, called from the webhook on an ad-resolved opening inbound): find-or-create the client (source «ترويج», `creation_source='ad_inbound'`) + append one first/latest-touch paid-ad attribution row. The ledger row stores only ids + when + how — no marketing data is copied onto the client. See [marketing-workspace.md](marketing-workspace.md).

## Open questions / known limitations
- **One WhatsApp account, one gateway (operational rule, 2026-07-27).** WhatsApp allows several linked companion devices, and a second live WAHA session on the same number is not a harmless spare: it re-reports every message under its own addressing mode, which used to double the rows and split the delivery receipts. Ingest now merges those copies on the message hash, but the duplicate gateway still burns a companion slot and races the real one. **After any re-pair, unlink the old device from the phone** (WhatsApp → Linked Devices). The webhook logs `events from UNREGISTERED session "<name>"` when one is talking to us.
- **AI reply session state is now a Fly volume (2026-07-27).** `wassel-wa-agent` mounts `wa_agent_state` at `/home/agent/.claude` so the Claude CLI's conversation store survives a deploy. Without it every machine replacement wiped it, `--resume` failed with "No conversation found with session ID", and each customer message restarted the agent cold — the visible symptom was the agent contradicting itself and re-asking what it had already been told. If the volume is ever detached, that regression returns silently.
- **A restart used to wedge a chat permanently (fixed 2026-07-27).** `WORKER` is derived from `FLY_MACHINE_ID`, which survives a restart, so a job killed mid-flight was claimed by the same id the new process reports — and `claude_jobs_recover_orphaned` deliberately skips same-owner jobs. The job sat in `running` forever, and `whatsapp_ai_enqueue` debounces on any pending/running job for that chat, so that customer could never get another AI reply. The runner now reclaims its own stale jobs at boot (`recoverOwnStaleJobs`).
- **Owner assignment.** The header doesn't expose an "owner" picker yet — requires a Haberchat-agent-id ↔ Wassell-user mapping table that doesn't exist. Haberchat's `owner` field round-trips via the `chat:update` webhook but the app treats it as opaque.
- **Groups and channels.** v1 displays them in the list but disables the composer and doesn't render per-sender labels in group threads. Revisit when real-estate teams need group replies.
- **Ack tier gating.** `message:out:ack` events only fire on Haberchat Business / Enterprise plans. On lower tiers, outbound bubbles stay at "sent" (single tick) forever. Consider inferring "delivered" from a tier check instead of always waiting.
- **Records table is now on Realtime (resolved 2026-05-07).** Phase C.1 added `records` to the `supabase_realtime` publication at `REPLICA IDENTITY DEFAULT` (PK only) — the global `RealtimeOrchestrator` channel for `records` refetches the full row by id when a chats parent record is bumped, so a different browser that missed the window now sees the updated `last_message_preview` live. The earlier "scoped out as too noisy" assessment was reversed during the architecture refactor; per-table kill switches (`localStorage.wassell_realtime_disabled='1'` or `VITE_REALTIME_RECORDS=off`) provide rollback if it becomes a problem.
- **Existing `wa_*` tables.** Schema still has the pre-existing `wa_conversations` / `wa_leads` / `wa_errors` scaffolding for a never-shipped autonomous AI replier. Marked DEPRECATED but not yet dropped. Safe to remove in a future migration once confirmed empty.
- **Deleted / edited messages.** Haberchat's `message:update` event isn't handled — edits and poll votes are ignored. Not urgent for the v1 sales workflow.
- **Status "operative".** Haberchat sometimes returns device status strings we don't map (e.g. `operative`). The UI falls back to showing the raw value. Add missing entries to `statusLabel` as they surface.
- **Secret in webhook URL.** Per Haberchat's recommendation we accept the shared secret as a query param. That value ends up in Haberchat's delivery log but not in browser history. If Haberchat later exposes a HMAC-signed header scheme, prefer it.
- **Template media in Start New Chat (limitation, 2026-06-08).** Inserting a `chat_templates` template into the *new-chat* composer carries only its TEXT — a template's media attachment is dropped for the first message of a brand-new conversation (the `startNewChat` send path is text-only; the in-conversation `Composer` does support template media). Pick the client/number, send the text, then attach media from the conversation's composer if needed. Threading media through `startNewChat` is a future enhancement.
