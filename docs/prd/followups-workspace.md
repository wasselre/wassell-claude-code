## What it is (in plain English)
The Follow-up Workspace is the guided screen a sales rep uses to work a single follow-up task. Instead of the generic record form (a wall of fields), it shows one clear **mission** at the top ("Booking call — book a project visit"), the call/WhatsApp button, a short call script, only the context that matters for this specific task on the side, and an **Outcome** panel where the rep records what happened. The rep picks one of a short list of allowed outcomes, fills the few fields that outcome needs, and hits **Complete & Save**. That save records the outcome on the follow-up and lets the workflow engine move the client to the next stage and create the next task — the rep never touches a stage dropdown.

It is the front door of the Sales Operating System: it replaces the generic Follow-Ups form for the `followups` model. Power users who need the raw form (to edit an unusual field) can still reach it via an "Advanced Fields" link.

## Why it exists
The generic form treated a follow-up like any other record — every field visible, no guidance, and the rep manually deciding what to set on the client afterward. That produced inconsistent data and missed next steps. The Workspace narrows the rep's job to "make the contact, pick the outcome," validates that they captured what the process needs, and hands the rest to automation. It's the difference between a form and a guided task.

## Key behaviors
- **Replaces the generic followups form.** `src/App.tsx` routes the `followups` model's record page to `FollowUpWorkspacePage` unless the URL carries `?generic=1`. The escape hatch (`?generic=1`, reachable from the "Advanced Fields" link or the "رجوع/Back" affordances) renders the normal record form for power editing.
- **Mission-first layout.** A `MissionHeader` shows the follow-up type's bilingual label + objective (the "Goal" — which an admin can now reword per type from the Sales Manager page; see [sales-process.md](sales-process.md)), the client, and the attempt number. The main column holds the primary action (call or WhatsApp, channel chosen by the follow-up type's `primary_channel`), the call `ScriptPanel`, and the `OutcomePanel`. The side column holds the `ContextPanel` (only the context blocks the config lists for this type), a `PreferenceSummary`, and a `TimelinePanel`.
- **Both the mission Goal AND the Call Guidance can be manager-edited.** The objective text the rep reads at the top, *and* the call/message guidance bullets in the `ScriptPanel` ("إرشادات المكالمة / Call Guidance"), are the follow-up type's defaults unless an admin has overridden them in the Sales Manager page's "Follow-up Instructions" editor. The Workspace merges any overrides over the default config (`applyOverridesToConfig`) before rendering, so a reworded goal or a rewritten guidance list shows up here for every rep with no code change. Guidance is edited as one bullet per line, per language. Full detail: [sales-process.md](sales-process.md).
- **WhatsApp opens the existing conversation if there is one, else the in-app composer — never wa.me.** The WhatsApp button no longer hands off to a `wa.me` URL. When the client **already has a WhatsApp conversation**, the button opens that conversation thread directly in a popup (`ChatThreadModal`) so the rep reads the history and replies in place. The existing chat is found from the persisted `chats` records — preferred by explicit `client_link`, else matched by phone digits (suffix-tolerant, the same rule the webhook auto-link uses); chat records are persisted in `records`, so the match works even if the rep never opened the Chats page this session. When there's **no** existing conversation, the button opens the app's own "Start New Chat" popup, already connected to this client (or pre-filled with the client's phone if the record isn't linked), so the rep sends the first message from inside Wassell and the conversation is created + linked in the WhatsApp inbox; on send it then opens the same thread popup. The button is disabled only when there's neither a client nor a phone to message. (The OutcomePanel's own **Send WhatsApp message** action, which drives the two-phase send→waiting flow below, is unaffected — it always opens the composer so the send can stamp the waiting state.) See [chats.md](chats.md).
- **Sending a WhatsApp is an ACTION, not the outcome — it puts the follow-up into a "waiting for response" state.** A WhatsApp follow-up is a two-phase flow: the rep first *sends* the message, then later the customer's *reply* is the real outcome. When the rep sends from the in-app composer, the Workspace runs a new non-completing save path (`handleWhatsAppSent`) that stamps the waiting state instead of completing the task: `followup_status = 'in_progress'`, `whatsapp_state = 'message_sent_waiting_response'`, `sent_at` (now), `first_whatsapp_sent_at` (on the first attempt), `whatsapp_attempt_number`, and `source_followup_id` = **the record's own id** (so the on-due escalation can later close this exact follow-up). The follow-up's `scheduled_datetime` is repurposed as the **escalation deadline**: attempt 1 → now +24h, attempt 2 → day 5 from `first_whatsapp_sent_at`. The `followup_status` enum is unchanged — waiting is `in_progress` + the `whatsapp_state` field, not a new status value.
- **The OutcomePanel is WhatsApp-state-aware (three phases — the task is a reply CHECKPOINT; the project was already sent on the call).**
  - **Fresh** (no `whatsapp_state`): the panel asks "المشروع أُرسل بعد المكالمة — هل ردّ العميل؟" and offers **Send a check-in message** (opens the composer → waiting state), **بانتظار رد العميل / Waiting for reply** (the rep already messaged from the chat — parks the waiting state without composing), **لم تُرسل رسالة / No message sent** (requires a reason + next date), and **العميل ردّ / Client replied** (reveals the response-outcome buttons immediately; no waiting state, no escalation).
  - **Waiting** (`whatsapp_state='message_sent_waiting_response'`): a gold "message sent — awaiting the customer reply · {sent_at}" banner + the response-outcome buttons + a "Send another" link.
  - **Replied** (`whatsapp_state='replied'` — set by the inbound-webhook reconciler `mark_whatsapp_replied` when a client message arrives **while the task is waiting and timestamped at/after `sent_at`** — v2 semantics 2026-07-18; the v1 behavior marked replied on ANY inbound while merely open): a green "client replied — continue the conversation, then record the outcome" banner + the response-outcome buttons, **plus a «ما زلت بانتظار رد العميل» / "Still waiting for a reply" escape hatch** that re-parks the task into the waiting state and re-arms the no-response escalation — for "the client replied once, I messaged again, silence" and for tasks marked replied by the pre-v2 behavior. Replied tasks are promoted into Due Now / My Tasks even when future-dated.
  - `message_sent` / `message_replied` are never offered as outcomes in any phase.
- **WhatsApp response outcomes (the reply is the outcome).** `message_sent` and `message_replied` are **no longer selectable** outcomes — `message_sent` is reused as the `whatsapp_state` send marker, and both remain only as legacy `call_result` values. The selectable response outcomes are: **Interested** (status مهتم, schedules the next WhatsApp +5 days); **Wrong time** / **Recontact later** (both require `reschedule_contact_date`, next WhatsApp at that date); **Not interested** (requires `lost_reason` + notes → غير مؤهل / غير مهتم, terminal); **Appointment booked** (W3 owns the client move, as for calls); **Request offer** (moves the client to عرض سعر / تم طلب عرض سعر). A `no_response` outcome also exists in the catalog but is written **only by the escalation workflow**, never picked by a rep.
- **After-visit follow-up outcomes (expanded 2026-06-21).** On an after-visit call (`follow_up_call_after_visit`) the OutcomePanel now offers, alongside the existing ones, **Requested another visit** (re-enters the booking cycle), **Visited another project** (requires notes → at-risk, NOT auto-lost), **Recontact later** (requires `reschedule_contact_date`), and **Invalid number** (requires `lost_reason` → terminal Unqualified). "Lost to competitor" stays a separate manual outcome. Each maps to a stage/status preview the rep sees before saving; the W7 (After-Visit Completed) workflow does the actual move. A repeated **No answer** retry counts toward a cap — after N=3 attempts W7's "Unreachable after visit" branch terminates the thread (status تعذّر التواصل بعد الزيارة). See [sales-process.md](sales-process.md).
- **"View Client" opens a modal, not a new page.** Tapping View Client (or "Edit Full Preferences" in the preferences panel) opens the client's record in a modal on top of the Workspace, so the rep keeps their place in the task. The modal carries an **Open full page** button to hand off to the full client record when they want the whole Client 360 view.
- **Only config-allowed outcomes render.** The `OutcomePanel` reads the follow-up type's `allowed_outcomes` from `DEFAULT_SALES_PROCESS`. The first allowed outcome is the primary success path, rendered as a big filled button; the rest render as pills. Each button's color comes from the outcome's tone (positive = green, neutral = gold, negative = red). A type with no config entry shows "No guided outcomes for this type — use Advanced Fields."
- **Dynamic field visibility.** Picking an outcome reveals exactly the fields that outcome needs — and no others. The shared predicate `revealedFieldSlugs()` decides which of `appointment_id`, `reschedule_contact_date`, `new_appointment_datetime`, `lost_reason`, `outcome_notes`, and the channel-appropriate evidence link (`completed_by_call_id` for calls, `completed_by_chat_id` for WhatsApp) appear. `actual_datetime` (completed-at) always shows. The **same** predicate is used by the validator, so what's revealed-and-required is exactly what blocks the save — and a hidden field never blocks it.
- **Live validation (hard errors vs warnings).** `validateFollowUpCompletion()` runs as the rep edits. Hard errors (a required field empty, no outcome chosen) disable Complete & Save and show a red message. A missing-required message **names the field in the user's language** — its Arabic/English display label (built via `buildFieldLabels` from the model), not the raw API slug. Warnings (no call/chat evidence attached, or a dead-end outcome that would leave an active client with no next action) are shown in gold and are overridable — they don't block the save.
- **"What will happen" preview.** Below the revealed fields the panel shows a plain-English preview of what the bound workflow will do — which stage the client moves to, what status is set, and the next action that will be created. This is a preview only; the workflow does the actual write.
- **Appointment-Booked requires creating an Appointment.** For the `appointment_booked` outcome the panel does **not** offer a free-text field — it requires a real Appointment record. It shows a "Book Appointment" button that opens the appointment form (prefilled with the client, phone, sales rep, and a back-link `source_followup_id`); on save the new appointment id is stamped onto the follow-up draft (`appointment_id`) and the button flips to "Appointment created & linked ✓". The follow-up's own save records the outcome but never moves the client to موعد زيارة — the **Appointment Created workflow (W3)** owns that move (so the client only advances once the appointment truly exists).
- **Register Visit — evidence, not an outcome.** A persistent **secondary** action ("Register Visit / تسجيل زيارة") sits in its own "Additional evidence / دليل إضافي" card directly under the call/WhatsApp row and is available for **every** follow-up type. It exists because "the client already visited the project" is *evidence the rep learns during the contact*, not a follow-up result — so it **never touches the selected outcome and never completes the task**. Clicking it opens the **Visits** form in a modal, prefilled from the follow-up/client: client, name, phone, sales rep, **today's date** (editable), a default note ("Visit was registered from follow-up after client reported they visited."), and the project *only* when a follow-up project context resolves to one of *our* projects (the visit's Project lookup targets `our_projects`, so an all-projects-only id is left blank rather than shown as a broken ref). The originating follow-up is stamped onto the visit as **`source_followup_id`**. Saving creates the visit, which fires the existing **"Visit → After-Visit" workflow (W6)** normally — client stage → زيارة, after-visit follow-up created, **and the visit-experience rating timer armed** (a `rating_request` follow-up that WhatsApps the client a 1–5 rating link ~2h later; see [visit-rating.md](visit-rating.md)) — with **no** special "visited" outcome or branch. **Duplicate guard:** before opening the form it scans the client's visits for one already dated **today**; if found it shows a warning with that visit's summary (date, project, rep, latest note) and prefers **Open existing visit** / **Cancel** over **Create new anyway** — no duplicate is created by default. If a visit was already registered *from this follow-up*, the control flips to a green **"Visit already registered / الزيارة مسجلة"** badge that opens that visit for editing instead of letting the rep duplicate it.
- **Client preferences are inline-editable in the sidebar.** The `PreferenceSummary` panel always shows the five preference fields — unit type, budget, city, direction, and district — even when they're empty, so the rep can capture them mid-call without leaving the task. Each renders with the same picker the client form uses (budget uses the dropdown-range control), and a **Save preferences** button (shown only when something changed) writes the edits straight onto the client record with optimistic concurrency (a concurrent edit elsewhere is caught and the rep is told to reload). "Edit Full Preferences" opens the full client form in the same modal as View Client, not the generic follow-up form. **The preference edit buffer is now LIFTED into the Workspace** (`prefDraft`) and shared with the Sales Assistant side panel (below), so the assistant can read the rep's *unsaved* preference edits — `PreferenceSummary` runs in controlled mode, seeded from the saved client once per client (re-seeded after a full-modal client save).
- **Project Finder side panel (2026-06-28 — narrowed from the old chat assistant).** A collapsible `SalesAssistantSidePanel` ("مساعد المبيعات") sits on the right of the Workspace. Under `PROJECT_FINDER_ONLY` it is now a **focused launcher for the deterministic Suggested Projects finder — no free-text chat.** Its primary action is **"المشاريع المقترحة / Suggested Projects"**, which opens the `SuggestedProjectsModal` showing the deterministic ranked groups matched against the client's preferences. **The critical behavior is unchanged:** it reads the **draft-first** preferences (`prefDraft` > saved client > missing) via `src/lib/followups/assistantContext.ts`, so the recommendation uses the values the rep is editing **right now, before Save**. The panel shows a "current preferences" chip summary + a "uses current form values, even before saving" note. State is **ephemeral** (not persisted). *(Legacy: before the narrowing this was a contextual face of the broad Sales Assistant — it streamed the `/api/match` brain, rendered comparison/next-action/message cards, and allowed free chat. That conversational surface is dormant under the flag — see [project-matching-assistant.md](project-matching-assistant.md).)*
- **Suggested Projects modal — deterministic, boundary-verified, NO LLM (2026-06-29).** The `SuggestedProjectsModal` now fetches the deterministic geography boundary-verified **`/api/project-finder`** (via `src/lib/matching/projectFinder.ts`'s `fetchProjectFinder`, sending `parse:false` + `explain:false`) — so **no AI runs on this path**: selection, scoring, ranking, AND the per-card explanation are all deterministic server code. It matches against **`our_projects` + `all_projects` only** (market_listings is opt-in and intentionally not used here — its area scan is slow for dense districts, a separate deferred phase). The modal shows the **four** finder groups as tabs — **exact_district_matches**, **nearby_district_matches** (ranked by real distance, closest first), **same_city_matches**, and **broader_fallback** — replacing the old five `suggest-projects` buckets. Above the tabs it shows the current draft-first preferences as chips plus an "ask the client about…" warning for missing required preferences (and, when nothing is matchable, an "ask the client" empty state with `needs_preferences`). Each project renders as a new **`FinderCard`** showing: project name, match band (strong/good/partial/weak), score, match type (exact/nearby/same_city/fallback), geo_confidence, geo_status (verified_match / verified_derived / mismatch / outside_known_districts / unverified_no_coords / no_geography), distance_km (when applicable), data_gaps, mismatch_warnings, key facts, and the deterministic explanation.
- **Suggested Projects → Client Property Options (2026-06-30 — replaces the old "Add to client").** The finder is the entry point for saving an option into the unified **`client_property_options`** store ([clients.md](clients.md)). Each card has a **selection checkbox**: only matches scoring **exactly 100** are auto-checked, everything below 100 is visible but unchecked unless the rep selects it. A footer **"Save selected to client options"** bulk-saves the checked cards (default status `suitable`, `added_from` `project_finder`); the toast tallies created / updated / eliminated-skipped. Each card also has a per-card **"Save as option"** and an **"Eliminate"** action (which opens a required reason-notes prompt). Cards cross-reference what's already saved: an existing active option shows a "Saved · {status}" chip, and an eliminated one shows "Eliminated" + a **"Reactivate"** action — re-saving an eliminated source is **never a silent reactivate** (it returns `eliminated_exists`; reactivation must be explicit). Source is routed to `source_type` (`market_listings` → `market_listing`, else `project`) and the card's snapshot facts are stored on the option's `data.facts`. **The old per-card "Add to client" (which appended to `clients.preferred_projects` / `preferred_market_listings`) is removed** — the `preferred_*` fields stay preference INPUTS, no longer the finder's save target. The card's only other action is **"Details"** (opens the all_projects record for a project, or the market_listings record for a listing). There is no chat pane, no compare, no WhatsApp draft, no pitch/ask, no next-action, and no task creation.
- **Evidence linking (auto + bidirectional).** For call outcomes the `EvidencePicker` **auto-links the most recent matching outbound call** (matched by `client_link` or by canonicalized phone) as the call that completed this follow-up (`completed_by_call_id`) — no manual click. It shows the linked call's time and a **Change** action; a pre-existing link and an explicit detach are respected (it latches after the first attempt, so it won't immediately re-attach — re-picking is the rep's call). On Complete & Save, the Workspace also stamps `linked_followup_id` back onto that phone call record — so the link is visible from both sides. (See [calling.md](calling.md).) When no matching call exists, the picker shows "no recent outbound calls" and attaching stays a soft warning, not a hard block.
- **The save writes the outcome; the workflow does the rest.** Complete & Save sets `call_result` (the outcome), `actual_datetime` (now, if unset), `followup_status = 'completed'`, `completed_by_user`, and the stage/status snapshots (`source_stage_snapshot` / `source_status_snapshot`, captured from the client at completion time), then calls `saveRecord` with the form-mount version for optimistic-concurrency. The fired Sales Lifecycle workflow then moves the client and creates the next task.
- **Optimistic concurrency.** The page snapshots the record's version at mount and passes it as `expectedVersion`. A concurrent edit by someone else returns a `conflict` and the rep is told to reload before saving (the completion is not applied). A queued (offline) save shows "saved locally — will sync later." The bidirectional evidence write uses its own version and a conflict there does not undo the completion (the pending-sync queue retries).
- **Permissions respected.** The Workspace honors the same view/edit permission hooks as the generic form. A user who can view but not edit sees the read-only Workspace (outcomes and Complete & Save disabled).
- **Bilingual + RTL throughout.** All labels, the script, the previews, and validation messages render Arabic/English and mirror under `dir="rtl"`.

## User flows
1. **Complete a booking call — interested (happy path):**
   1. Rep opens a booking-call follow-up → mission "Book a project visit," call button, script.
   2. Rep dials, talks, clicks the **Interested** outcome → `actual_datetime` auto-fills, the preview reads "set status مهتم; create the next action."
   3. Validation passes → rep clicks **Complete & Save** → toast "Follow-up completed."
   4. The Booking Call Completed workflow (W2) sets the client status and schedules the next task; the rep returns to **where they came from** — the Sales Tasks queue (with its view/filters preserved) if the follow-up was opened from there, otherwise the follow-ups list. (The entry point passes a `returnTo` via location state; `handleComplete` honors it.)
2. **Appointment booked:**
   1. Rep picks **Appointment Booked** → the panel shows "Book Appointment."
   2. Rep clicks it → the appointment form opens prefilled → rep saves → `appointment_id` is stamped on the draft and the panel shows "Appointment created & linked ✓."
   3. Rep clicks **Complete & Save** → the follow-up is completed; W3 (fired by the new appointment) moves the client to موعد زيارة and creates the confirmation follow-ups.
3. **A losing outcome:**
   1. Rep picks "Offer Rejected" (on an offer follow-up) → the `lost_reason` field reveals and is required.
   2. Rep selects a reason → preview reads "move the client to خاسر; set status تم رفض العرض." → Complete & Save.
   3. W9 moves the client to the Lost side-exit with the reason; no next task is created (terminal).
4. **A WhatsApp follow-up (two phases — send, then record the reply):**
   1. Rep opens a WhatsApp follow-up → the OutcomePanel shows the **Send WhatsApp / Record customer response** choice. If the client already replied, the rep picks **Record customer response**, the outcome buttons appear immediately, and completing runs the normal flow (`actual_datetime`=now, `call_result`, `followup_status='completed'`) + the WhatsApp Response Completed workflow — no waiting state, no escalation.
   2. Rep sends the first message from the in-app composer → the Workspace stamps the waiting state (`whatsapp_state = 'message_sent_waiting_response'`, `followup_status = 'in_progress'`, `sent_at`, `source_followup_id` = own id) and repurposes `scheduled_datetime` as the +24h escalation deadline. The panel now shows "waiting for response since {sent_at}" plus the response-outcome buttons.
   3a. **Customer replies before the deadline:** rep reopens the task, picks the reply outcome (e.g. **Interested**), fills any required field, and **Complete & Save** → the WhatsApp Response Completed workflow performs that outcome's stage/status move and schedules the next WhatsApp.
   3b. **No reply by the deadline:** the No-Response Escalation workflow (`on_due`) fires on the baked-in `scheduled_datetime`, marks the follow-up `no_response` + completed, and creates the next attempt — WhatsApp #2 on attempt 1, or a booking call on attempt 2 (day 5). See [workflow-automation.md](workflow-automation.md) and [sales-process.md](sales-process.md).
5. **Register a client-reported visit (any follow-up type):**
   1. Mid-contact the client says "I already visited the project." The rep clicks **Register Visit**.
   2. If the client already has a visit dated **today** → a warning shows that visit's summary and the rep picks **Open existing visit** (edit it), **Cancel**, or **Create new anyway**. Otherwise the **Visits** form opens prefilled (client, phone, name, sales rep, today's date, default note; project only if it maps to one of our projects).
   3. Rep saves → toast "Visit registered" → the visit is linked back via `source_followup_id`, and the **Visit → After-Visit workflow (W6)** moves the client to زيارة, creates the after-visit follow-up, and arms the visit-rating timer (the client is WhatsApped a 1–5 rating link ~2h later — see [visit-rating.md](visit-rating.md)). The follow-up's selected **outcome is unchanged** and the task is **not** completed — the rep keeps working the call and records the real outcome afterward. The action now shows **"Visit already registered."**
6. **Power-user escape hatch:** Rep needs to edit a field the Workspace doesn't expose → clicks **Advanced Fields** → the generic record form opens (`?generic=1`) → edits and saves there.
7. **Error / empty states:**
   - Outcome chosen but a required field empty → red message, Complete & Save disabled.
   - No guided config for this follow-up type → "No guided outcomes for this type — use Advanced Fields."
   - Concurrent edit → "This record was just edited by someone else — reload before saving."
   - No recent outbound calls to attach → the evidence picker shows "No recent outbound calls."

## Data touched
- **Reads:** `models` (followups + clients + appointments + phone_calls ids/schema); `records` (the follow-up, its client, linked appointment/project, and the client's recent outbound phone calls for the evidence picker); `users` (to resolve the completed-by / rep names); `sales_process_overrides` (the manager-edited objective text, merged over the default config for the mission Goal). The Suggested Projects modal calls the deterministic `/api/project-finder` (which reads `our_projects` / `all_projects` via `unified_records` plus the `district_boundaries` PostGIS polygons server-side) and reads the client's preference fields draft-first (the lifted `prefDraft` + the saved client record) to build its requirements. It also reads the client's existing `client_property_options` rows to render per-card saved/eliminated status. It never writes project data — the only writes are the user-triggered **Save to client options** (bulk or per-card), **Eliminate**, and **Reactivate**, which create/update `client_property_options` records (status, facts snapshot, match score) via the version-aware `saveRecord`.
- **Writes:** `records.data` for the follow-up (the outcome + completion fields + snapshots) via `saveRecord`; the **WhatsApp waiting-state stamp** (`handleWhatsAppSent` — a non-completing save that sets `whatsapp_state`, `sent_at`, `first_whatsapp_sent_at`, `whatsapp_attempt_number`, `source_followup_id`, and repurposes `scheduled_datetime` as the escalation deadline); `records.data` for the **client** when the rep saves inline preference edits (the five preference fields); a new appointment record when "Book Appointment" is used; a new **visits** record (carrying `source_followup_id` back to this follow-up) when **Register Visit** is used — which fires the Visit → After-Visit workflow; a new WhatsApp conversation + first message when the rep sends from the in-app composer; `linked_followup_id` back onto the attached phone_call record. Registering a visit deliberately writes **only** the visit (and its link) — never the follow-up's outcome/completion. All client stage/status moves, the response-outcome transitions, and next-task creation are written by the **workflow engine**, not this page. The objective text shown in the mission is read (not written) from the merged sales-process config — manager edits to it are written from the Sales Manager page, not here.
- **Storage shapes:** the follow-up's completion writes `call_result`, `actual_datetime`, `followup_status`, `completed_by_user`, `completed_by_call_id` / `completed_by_chat_id`, `lost_reason`, `outcome_notes`, `new_appointment_datetime`, `appointment_id`, `reschedule_contact_date`, `source_stage_snapshot`, `source_status_snapshot` — all on `records.data` (followups is unfrozen JSONB). The WhatsApp two-phase flow adds `whatsapp_state` (`message_sent_waiting_response` / `no_response_expired`), `sent_at`, `first_whatsapp_sent_at`, `whatsapp_attempt_number`, `escalation_reason`, `previous_followup_id`, `source_followup_id`, `sent_by_user`, and `whatsapp_template_id` (`completed_by_chat_id` already existed). New fields added by `supabase/migrations/2026-06-17_whatsapp_followup_fields.sql`.

## Open questions / known limitations
- **Advanced Fields is the only edit-everything path.** The Workspace intentionally exposes a curated field set; anything outside the config (e.g. a custom field a customer added to followups) is only editable via `?generic=1`. That's by design but means the Workspace doesn't auto-discover custom fields.
- **Evidence picker is outbound-only and capped.** It suggests the 5 most recent **outbound** calls. An inbound call the rep wants to cite as evidence isn't offered; the generic form's lookup is the fallback.
- **The "leaves client without next action" warning is heuristic.** It fires on a non-terminal outcome whose preview has no next action. It's a soft nudge, not a guarantee — the actual next action is created by the workflow.
- **One client per follow-up.** Context resolution reads the first `client_id` if the field is an array; the Workspace assumes a single client per task.
- **Appointment-booked depends on W3 being enabled.** If the Appointment Created workflow is disabled, completing an appointment-booked outcome creates the appointment but the client won't advance — the Studio's "Missing/Advanced" badges are how an admin notices.
- **WhatsApp escalation runs on the `on_due` sweeper** (`/api/sweep-due-followups` cron) — **verified live in production**: a waiting follow-up past its baked-in deadline was swept, self-closed as `no_response`, and spawned the next attempt. A sent WhatsApp follow-up sits in the waiting state until either a rep records the reply or the deadline passes. See [workflow-automation.md](workflow-automation.md).
- **A real reply must be recorded by a rep — the app doesn't auto-detect inbound replies.** The waiting state survives until either the rep picks a response outcome or the escalation deadline passes. An inbound WhatsApp message arriving doesn't itself clear the waiting state; the rep marks the outcome.
- **Register Visit's duplicate guard checks today's date only.** The pre-check looks for an existing visit for the same client dated **today** (the visit's default date) and the "already registered" badge keys off `source_followup_id`. If the rep edits the date inside the open visit form to a past day that already has a visit, that specific collision isn't re-checked — the realistic duplicate (a visit registered the same day, by the rep or the project rep) is covered.
- **Register Visit's project prefill is best-effort.** The visit's Project lookup targets `our_projects`, while the follow-up's project context (appointment/visited/preferred) is keyed on `all_projects`. The prefill only fills Project when a candidate id is a real `our_projects` record; otherwise it's left blank for the rep to pick rather than risk a broken reference.
