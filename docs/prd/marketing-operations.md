# PRD: Marketing Operations (Reels + Posts)

**Status:** Live
**Last updated:** 2026-04-23 (editable research table, collapsible, PDF export)
**Related PRDs:** `record-management.md` (project lookup), `data-storage.md` (Supabase), `workflow-automation.md` (future auto-publish hooks)

## What it is (in plain English)

A dedicated Marketing area in the Wassell CRM where the team creates a
"marketing operation" for a real-estate project and gets back reviewable
reels (short video scripts) and Instagram-style posts generated by AI. Each
operation runs through a fixed pipeline: research the project → (answer any
contradiction questions if the agent finds conflicting sources) → generate
the reels and posts → notify the reviewer → human edits/approves. It
replaces the old OMA system that lived in Google Sheets + Apps Script.

## Why it exists

Wassel produces marketing content for dozens of real-estate projects. The
old Sheets pipeline was brittle (mirror tables, merged cells, drive folders
of competitor content). This feature bundles everything into a first-class
app experience: one list of operations, one place to review the output,
and one app-managed library of competitor style references that the AI
agents consult on every run (no redeploy needed to update it).

## Key behaviors

- **Operation as the unit of work.** Every run is one row in
  `marketing_operations`, linked to one project. Reels and posts for that
  run live in `reels` and `posts` rows tied to the operation.
- **Research always runs first.** The moment an operation is created, the
  `marketing-research` edge function fires (fire-and-forget). It uses the
  Anthropic `web_search` tool plus a custom `fetch_url` tool to find facts
  from the project's own sources.
- **Contradictions pause the pipeline.** If the research agent finds
  conflicts between sources, it writes them to `research_questions` and
  flips the operation to `research_waiting_answers`. The UI shows the
  questions inline; a notification fires to the bell.
- **Last answer auto-resumes.** The moment the final unanswered question
  gets an answer, the app fires `marketing-research-resume` — the user
  does not click anything.
- **Reels + posts run in parallel after research.** The orchestrator
  (`marketing-content`) fires `marketing-reels` and/or `marketing-posts`
  depending on what the user selected.
- **Agent knowledge is app-managed.** The `competitors` table holds style
  reference content. Agents pull it fresh on every run with Anthropic
  prompt caching, so updates are instant and do not require a redeploy.
- **Pre-created rows = stable IDs.** When an operation is created, N empty
  reel rows and M empty post rows are INSERTed. The agent UPDATEs them
  with content when done, so the UI can show `3/5 draft_ready` progress
  from the start.
- **Human review gates publishing.** Agent output always lands as
  `draft_ready`. A human opens the reel or post editor, edits freely, and
  clicks `Approve` to move it to `approved`. An Approve All button on
  the operation page flips every `draft_ready` child at once.
- **In-app bell for progress notifications.** Six notification types cover
  the pipeline: research waiting answers, content ready (reels/posts),
  operation ready for review, operation failed.
- **Research table is human-editable.** Once research lands, the reviewer
  can click **Edit** on the research section to adjust any fact (value,
  source, source URL), add rows for facts the agent missed, or delete
  spurious rows. Saving writes the whole `research_output` JSONB back to
  `marketing_operations`. The section is also collapsible via a chevron.
- **PDF export for reels and posts.** Each reel/post card has a selection
  checkbox. The section header exposes **Export selected** (only the
  ticked rows) and **Export all PDF** buttons. Output is an A4 portrait
  RTL-styled Arabic PDF — one PDF per kind — produced client-side via
  `html2canvas` + `jsPDF` with multi-page overflow handling.

## User flows

1. **Main happy path**
   1. Open `/marketing` → click **New Operation**.
   2. Pick a project from the dropdown (from `all_projects` records).
   3. Toggle `Include reels` + pick settings (count, type, platform,
      voiceover). Toggle `Include posts` + pick (count, type, usage).
   4. Click **Start**. The app INSERTs the operation + empty reels + empty
      posts, then fires the research edge function.
   5. Operation detail page shows a spinner under Research. 30–120s later,
      the status flips to `content_generating` and the reels/posts cards
      start filling in as `draft_ready`.
   6. Bell rings with `content ready — {project}`.
   7. Reviewer opens each reel/post editor, edits scenes/texts, clicks
      `Approve`.
   8. When every child is approved, the Approve All button on the
      operation page flips the operation to `approved`.
2. **Contradictions flow**
   1. Research agent finds two sources disagreeing on a fact.
   2. Operation goes to `research_waiting_answers`. Bell rings.
   3. Reviewer opens the operation, sees each question with a textarea,
      answers them one by one.
   4. Last answer triggers `marketing-research-resume`. Operation goes
      back to `research_in_progress`, then `research_complete`, then
      `content_generating`.
3. **Failure**
   1. Any edge function throws an exception → operation goes to `failed`
      with the error in `research_error`, a failure notification fires.
   2. The team investigates in the Supabase Function logs; the UI shows
      the error message inline.

## Data touched

All six new tables — see `supabase/schema.sql` (bottom of file):

- **Reads:** `competitors`, `records` (the all_projects row), `users`,
  `auth.users` (for notification user ids).
- **Writes:**
  - `marketing_operations` — one row per operation.
  - `research_questions` — one row per contradiction.
  - `reels` — one row per reel (updated by the agent with `scenes`).
  - `posts` — one row per post (updated by the agent with 5 text slots).
  - `marketing_notifications` — one row per user per event.

All six tables have RLS enabled with `authenticated full access` (matches
the v1 policy used on `models`/`records`/etc).

## Open questions / known limitations

- **i18n keys:** Marketing pages use inline bilingual strings (`isAr ?
  'x' : 'y'`) rather than `t('key')`. This works but diverges from the
  project convention — a follow-up task should extract every string into
  `src/lib/i18n.ts`.
- **Supabase realtime:** The notification bell does not subscribe to
  realtime yet — the store hydrates on initial load and on sign-in, but a
  new notification arriving while the user is already in the app won't
  show until the next refresh. Wiring `supabase.channel('marketing_notifications')` is a clean follow-up.
- **Edge function secrets:** The plan calls for a `WASSEL_EDGE_SECRET`
  envelope for cross-function calls. The current implementation uses the
  Supabase service-role key as the bearer token instead, which is the
  idiomatic Supabase approach. Document for ops.
- **Auth.users join:** `notifyAllUsers` fans out to every active row in
  the `users` table. Once the v2 role-scoped policies land, narrow this
  to "users who can see this operation".
- **Agent cost:** Prompt caching on the reels/posts system prompt + the
  competitors block keeps re-reading cheap. No cache on the research
  prompt because each project is unique — budget ~$0.05–$0.15 per run.
- **No tests yet.** Manual verification only. Adding unit tests for the
  `projectData.ts` helpers and a smoke test for `createMarketingOperation`
  is a good first follow-up.
