## What it is (in plain English)
A simplified, profile-assignable workspace for sales representatives — two pages that replace the full internal admin-style CRM for day-to-day selling. **My Clients** is a clean, tabbed sales list of the rep's own clients (with strong search/filters and a situational card per client). **My Tasks** organizes the rep's daily work around a single question — "what needs me right now?": an **Actions** tab stacks every actionable follow-up by urgency (a brand-new lead's first call sits on top with a 5-minute countdown, then customers who replied, then overdue, then today), a **Waiting for customer** tab parks the WhatsApp conversations where the ball is with the client, an **Appointments** tab shows the rep's upcoming appointments and no-shows, an **AI questions** tab lists every question the WhatsApp AI agent could not answer so the rep answers them in one place, an **AI notifications** tab collects the notes the WhatsApp AI agent posts when it hands a chat off, plus a placeholder for incomplete-preference tasks and the rep's other tasks. An admin/manager grants the workspace to a sales profile in Settings → Profiles; reps then see only their own clients and tasks, while managers/admins see everyone (with a rep filter / "All reps" toggle). Both pages reuse the existing Client 360 detail and Follow-up Workspace for click-through — only the index/listing surfaces are new.

## Why it exists
The generic model UI and the full Clients/Sales cockpits expose far more than a rep needs and aren't scoped to "my" book of business. Reps needed a focused operating screen: who are my clients, what state are they in, and what do I have to do today — without opening ten records.

## Key behaviors
- **Profile-assignable, opt-in.** Both pages are registered in `src/lib/customPages.ts` as custom (non-model) pages with `default_access: 'admin'` — hidden until an admin grants `my_clients` / `my_tasks` to a profile via the Sales Operations card. Registering the `CUSTOM_PAGES` entry auto-wires the Sidebar link, the `PageAccessMatrix` toggle, and the `RequirePageAccess` route guard. No migration — keys live in the existing `profiles.page_access` JSONB.
- **Self-scoping.** Reps see clients where `client_owner` === their user id and follow-up/other tasks where `sales_rep` / `responsible_officer` (or creator) === their user id. Managers/admins (`is_admin`) see all and get a rep/owner filter (My Clients) + an "All reps" toggle (My Tasks). Server-side RLS remains the trust boundary; this is a UX scope on top.
- **My Clients is one list (2026-10-05).** Every client in scope (retired clients excluded), sorted by last contact, newest first; never-contacted clients at the bottom by name. Filters: search (name / phone / client number), stage (`client_stage`), status (`client_status`), sales rep (`client_owner`; managers only, incl. «بدون مسؤول»), and **last contact** — All / Today / Yesterday / Last 7 days / Never contacted. **Last contact** is the newest of: a COMPLETED follow-up's `actual_datetime`; a WhatsApp chat linked to the client (any lookup to clients, live: `client_link`) — `last_message_at`, labelled «من العميل» / «منا» from `last_message_flow`, or just «واتساب» when an older chat has no flow; a phone call linked the same way — `call_time`. Open follow-ups never count (they are plans, not contact). The old segment tabs (Interested / Serious / Active / Late / Unqualified), the mine/all toggle and the full `ClientsFilterBar` were removed from this page at the operator's request (still used by the generic Clients list page).
- **"Late" is calendar-day-strict.** A follow-up is late only when its scheduled day is strictly before today AND it isn't done (completed/cancelled/skipped). A task scheduled *earlier today* is still today's task, never late — matches the Sales Queue's `computeSla` overdue rule.
- **My Client card** shows: Client ID (the `client_id` auto_id), name, phone, stage, status, assigned rep, lifecycle-health badge, visit-rating stars, latest follow-up type + outcome, next scheduled follow-up (with overdue emphasis), and a related-records summary (appointments / visits / offers / reservations counts). Quick actions: open next follow-up, in-app WhatsApp, call. Clicking the card opens the existing Client 360 (`/model/clients/:id`).
- **My Tasks tabs (redesigned 2026-07-21; AI notifications added 2026-08-24; AI questions added 2026-10-01):** **Actions** / **AI questions** / **Waiting for customer** / **Appointments** / **AI notifications** / **Incomplete Preferences** (still an intentional empty-state placeholder) / **Other Tasks** (the rep's open `tasks` rows — not completed/approved — with a "New task" button when the rep has create permission on the Tasks model).
- **AI questions (new 2026-10-01).** Every open `wa_agent_questions` row the user can see (RLS mirrors chat visibility), loaded by `loadOpenAgentQuestions` (paged, never cut at 1,000) through `useAgentQuestions`, oldest first. Scope: a rep sees questions whose `rep_user_id` is them or empty; a manager sees all and each card names the rep. Each card is the shared `AgentQuestionItem` (the same component as the in-chat card) with a context line: client name (phone when there is no client), project, time waiting, «فتح المحادثة» → `/model/chats/:conversation_record_id`. Answering calls `POST /api/whatsapp/agent-answer`; a question someone else closed first shows a toast and the list reloads.
- **Officer questions and visit checks (2026-10-08).** The same list also holds the questions sent to a project's OFFICER (`asked_to='officer'`) and visit checks, owned by the client's rep. They come from the WhatsApp agent (a visit-details question, a visit it wants confirmed — the agent can no longer book visits itself — or a negotiation hand-off's discount / last-price question). The officer is messaged at once with fixed wording on the operations line, inside 09:00–21:00 Riyadh, with no approval step. These cards are **blue** and show: the officer's name, when the message was sent, the status (waiting until the deadline · officer reminded at … · overdue), the exact message sent, and the officer's replies read from his chat (`GET /api/officer-messages?question_id=`), plus a box to type his answer.
  - **Plain question:** «سجّل الجواب — المساعد يبلّغه» (the agent passes it on), «بلّغت العميل بنفسي» (closes, the agent sends nothing), «المسؤول ما رد — أغلق» (closes; the agent tells the customer it could not be confirmed).
  - **Visit check:** «تأكدت — احجز الزيارة» (optional exact time) books the appointment — the only way an agent-arranged visit becomes an appointment; a booking that fails reopens the task and says why. «الزيارة غير ممكنة» needs a reason or another day typed first; nothing is booked and the agent offers another day. «بلّغت العميل بنفسي» is a tick that makes either button save without the agent messaging the customer. «المسؤول ما رد — أغلق» closes it (labelled «أغلق بدون تأكيد» when the project has no officer and the rep holds the check).
  - **Deadlines** (automation cron, every 5 minutes, 09:00–21:00 only): no answer within 2 working hours → one fixed reminder to the officer; 2 working hours later → the rep is alerted to call him; a visit check still open the day before or on the visit day (from 10:00) → the rep is alerted.
  - **Works with the AI stopped.** An officer-task answer is saved (and a confirmed visit booked) even when the AI is paused or off in that chat; nothing is relayed, so the rep tells the customer. A rep writing in the chat does NOT close these tasks — only the task buttons do.
- **AI notifications (new 2026-08-24).** A feed of operator-facing notes the WhatsApp AI agent posts — on handoff, or when it needs a human's attention. Rows come from the bespoke `ai_notifications` table (NOT an app model, so it can't ride the records store — `useAiNotifications` reads it directly, RLS-gated to authenticated staff). Each card is striped by **severity** — `warning` (terracotta: complaint / stop-contact), `action` (copper: a human must act), `info` (gold: FYI) — shows an unread dot, the body + timestamp, an **"open chat"** button (deep-links to `/model/chats/:chat_record_id`) and a per-card **mark-read**; the tab header carries an unread count badge and a **mark-all-read** button (both via the `ai_notification_mark_read(p_id)` SECURITY DEFINER RPC — `p_id` NULL marks all). v1 shows the feed to all authenticated staff (the schema carries a `target_user_id` for future per-rep routing). The agent writes rows through `POST /api/whatsapp/ai-notify` (shared-secret) — see [chats.md](chats.md).
- **Actions is ONE priority-stacked list, not day buckets.** Every actionable follow-up (due today, late, or promoted early by a reply / client message) is sorted by a five-tier priority stack (`priorityTier` in `myWork.ts`), then oldest-scheduled first: **tier 1 — hot new lead**: a booking call (`appointment_booking_call`) created within the last hour, for a client still in جديد **whose client record was itself created within that same hour** (tightened 2026-07-28 — see below) — its card shows a live **5-minute countdown** (`HotCountdown`, pulsing red; flips to "+m:ss over" past the SLA); **tier 2 — customer replied / messaged** (`whatsapp_state='replied'`, or a fresh task with `client_messaged_at`); **tier 3 — overdue** (scheduled day strictly before today); **tier 4 — due today**; **tier 5 — quiet** (rating requests, undated leftovers). Each card carries a start-edge **stripe color per tier** (red / red / amber / copper / muted). An All / Calls / Conversations chip row filters by channel (resolved from the type's `primary_channel`). Tasks parked waiting on the customer are **excluded** from Actions.
- **Waiting for customer** lists WhatsApp tasks in `message_sent_waiting_response` — regardless of day bucket, including future-dated ones — sorted by newest deadline first, under an explainer banner: the ball is with the client; a task returns to Actions automatically when they reply (the inbound webhook reconciler flips it) or when the 24h silence escalation fires. Since the WhatsApp activity bridge (2026-07-21), ANY outbound message the rep sends on the client's linked chat arms/re-arms this state server-side — see [sales-process.md](sales-process.md).
- **Appointments** shows the rep's appointments in four sub-tabs: **Today** (past-due un-updated appointments deliberately stay here), **Tomorrow**, **Future**, and **No-shows** (a red worklist of `no_show` appointments). Completed/cancelled appointments are hidden; rows show client name + phone + full date/time + a status pill and open the appointment record.
- **"Hot new lead" means the CLIENT is new, not the task (fixed 2026-07-28).** `isHotLead` used `client_stage === 'جديد'` as its only proxy for newness. That stage is sticky: a lead imported months ago and never called still reads جديد (on 2026-07-28, 113 of the 114 clients sitting at جديد were older than a week). So every time a rep worked the backlog — completing an old booking call with a non-final outcome spawns a retry `appointment_booking_call` seconds later — the retry card rendered **«عميل جديد — اتصل الآن»** with a 5-minute speed-to-lead countdown on a three-month-old lead. The rule now also requires the **client record's own `created_at`** to be inside the same 1-hour window (`FollowupTask.clientCreatedAtISO`, resolved from the client record in `buildFollowupTasks` / `buildWaitingTasks`), and **fails closed** when that date is missing or unparseable — a missing badge just leaves an ordinary today task, a false one fakes an emergency. Backlog retries now fall to their normal tier (overdue / due today). Note the notification watcher gates the same moment differently (first-touch: no escalation marker + no earlier booking call) — see below.
- **Sales notifications (new 2026-07-21; hot-lead gate tightened 2026-07-23).** `SalesNotifications` (mounted once in `AppLayout`, so it works from any page) watches the store's realtime-merged followups and fires a toast + a browser Notification for the two moments where seconds matter: (a) a **hot lead** — a new booking-call task lands for a fresh (جديد) client, "call within 5 minutes"; (b) a **customer replied / messaged** — a task transitions into the replied signal. Clicking the browser notification focuses the tab and opens that follow-up (return-to My Tasks). Scoped to the rep's own tasks (unassigned tasks notify everyone); the first pass after boot only seeds the diff baseline so a reload never causes a notification storm. **The hot-lead ping now only fires for a GENUINE first-touch lead:** an old client whose WhatsApp chain went unanswered gets auto-escalated to a fresh `appointment_booking_call` while still tagged جديد, which used to trip the "🔥 عميل جديد" alert (booking-call + stage=جديد were the only signals). Two extra gates now exclude those re-escalations — the task must carry **no escalation marker** (`escalation_reason` / `previous_followup_id`, both stamped by the escalation engine) **and** be the client's **first booking-call task** (no earlier `appointment_booking_call` exists for that client). A truly new inbound lead still pings within its 5-minute window.
- **Conversation cards** surface the WhatsApp sub-state: no state yet → "Message to send" (or **"Client messaged" / «العميل أرسل رسالة»** when the client already messaged before any check-in — `client_messaged_at` set); `message_sent_waiting_response` → "Waiting for reply"; `replied` → "Replied".
- **Reuse:** follow-up cards open the Follow-up Workspace (`/model/followups/:id?returnTo=…`); WhatsApp uses the shared in-app popup (`useClientWhatsApp`); filters reuse the Clients cockpit's `ClientsFilterBar` + `ClientFilters` (owner/rep dropdown hidden for reps via the new `hideOwner` prop).
- **Tools menu (2026-09-27).** A «أدوات / Tools» button in the Sales Workspace header, on every tab (Overview / Clients / Work Queue / WhatsApp) — deliberately NOT in the app-wide header. Items, each gated on what the user can already do: **Search for a client** (clients `view`) — one box matching the client name OR any phone field; phone matching strips a leading `00` / `966` / `0` on both sides so `0536…`, `+966 53…`, `536…` and Arabic-Indic digits all hit the same client; results over 50 say "showing 50 of N — type more" (never a silent cut); picking opens the client page. **Book an appointment** (appointments `create`) and **Record a visit** (visits `create`) — the existing quick forms in `pickClient` mode: the same client search on top, a **required** client, and the chosen client's name + phone copied onto the record exactly as the chat flow prefills them; project + units are chosen in the chat's Projects & Units browser (pick mode — see record-management.md); saving goes through the normal `saveRecord` path so the appointment / visit workflows fire unchanged. **Project Finder** (`project_finder` page access) → `/project-finder`. **Financing calculator** (`financing_calculator` page access) → `/financing`. **New WhatsApp chat** (`sw_whatsapp` access) → the standard new-chat composer. **New client** (clients `create`) → `/model/clients/new`. **Log an unanswered request** (unanswered_requests `create`, added 2026-09-28) → find the client, then the existing "Nothing fits" request form. The button hides itself when no item is available.
- **Portals tab (2026-10-05).** The workspace's sixth tab, gated by its own access id `sw_portals` (default all). One card per broker portal (registered / another broker's / open failures / live now, auto-register on or off, how the code arrives, the last status check), a «يحدث الآن» list of live and parked runs, and three views: every client × portal row, the failed runs (grouped by reason, with what to do and the screenshots; failures settled since are hidden unless «أظهر ما حُلّ لاحقاً»), and every run. A rep sees their own clients (their client RLS); an admin sees all. Rows link to the client's own «البوابات» tab, which stays the one place to edit a registration — see [lead-portal-registration.md](lead-portal-registration.md).
- **Unanswered Requests tab (2026-09-28).** The workspace's fifth tab (Overview / Clients / Work Queue / WhatsApp / **Unanswered Requests**), gated per profile by its own access id `sw_unanswered` (default all). Reps see requests for their own clients; managers get a mine/all switch. It lists open requests with unmet-demand chips and lets the rep send a request to the real-estate offices of the client's districts over WhatsApp and save what they offer — see [unanswered-requests.md](unanswered-requests.md). The Overview tab gained two cards (open requests, overdue searches) that open it.
- **Officer notices (AI route) — rules + auto-send (2026-10-07).** Step 3 of `/api/cron/ai-sales-automation` drafts ONE officer message per interest event. Score-route events (≥ 40) are unchanged. AI-route events must pass `judgeInterest` first (rules A–C in `api/_lib/officerInterestGate.ts`; a `not_strong` result is stored on `client_project_interest.officer_result` with the reason). Passing notices carry the client's quote and, when `officer_notice_auto_send` is on, are queued directly via `scheduled_whatsapp_enqueue` (`context.auto_sent`, `deliver_at`); otherwise they wait in the Work Queue's AI tab.
- **States:** loading (until store `initialized`), per-tab/section empty states, a "no clients assigned to you yet" empty state, and a "Clients/Tasks model unavailable" guard.

## User flows
1. **Assign the workspace:** admin → `/settings/profiles/:profileId` → Sales Operations card → check **My Clients** + **My Tasks** → Save. Reps on that profile immediately get both sidebar links + route access.
2. **Work my clients:** rep opens **Clients** → picks Last contact «Today» (or a stage / status / rep) → searches → clicks a client → handles them in Client 360 → returns.
3. **Work my day:** rep opens **My Tasks** → **Actions** → works top-down (a hot new lead with its countdown always sits first; then replied customers, overdue, today) → taps Call / WhatsApp on the card or opens the follow-up to log the outcome. WhatsApp tasks whose message was sent disappear into **Waiting for customer** and come back on top when the client replies (with a notification). Before a site day, the rep checks **Appointments → Today / Tomorrow** and works the **No-shows** worklist.
4. **Manager view:** an admin opens either page → sees all reps' data → uses the rep/owner filter (My Clients) or the "All reps" toggle (My Tasks).
5. **Everyday actions from Tools:** in any Sales Workspace tab → **أدوات** → e.g. **Book an appointment** → search the client by name or phone → pick → choose project, units, date → Save (toast «تم حجز الموعد»). Saving without a client is refused with «اختر العميل أولاً».
6. **Empty state:** a rep with no assigned clients sees "No clients are assigned to you yet"; an empty tab/sub-tab shows a contextual empty message.

## Data touched
- Reads: `records` for `clients`, `followups`, `tasks`, `visits`, `appointments`, `offer_prices`, `reservations`, `phone_calls` (all via the store; RLS-scoped). `models.schema` for field options (stages/statuses/follow-up types/task status). `profiles.page_access` for the access gate. **`ai_notifications`** (bespoke table, read directly via `useAiNotifications`) for the AI notifications tab. **`wa_agent_questions`** (open rows, via the store's `loadOpenAgentQuestions`) for the AI questions tab — since 2026-10-08 including the officer columns (`asked_to`, `officer_name`, `officer_message`, `sent_at`, `due_at`, `reminded_at`, `escalated_at`, `visit_day` / `visit_slot` / `visit_time`). The officer's replies come from `chat_messages` on the operations line through `GET /api/officer-messages?question_id=` (service role, gated on seeing the question).
- Writes: the Tools menu creates `appointments` / `visits` records through `saveRecord` (same path as the chat quick forms). Otherwise none via the records store — creating a task routes to the generic `tasks` create form; logging a follow-up happens in the Follow-up Workspace. The AI notifications tab marks rows read via the `ai_notification_mark_read` RPC (never inserts — the agent writes those server-side). Resolving an agent / officer question goes through `POST /api/whatsapp/agent-answer` (server-side update of `wa_agent_questions`; a confirmed visit check also creates an `appointments` record and stores its id in `booked_appointment_id`).

## Open questions / known limitations
- **Officer replies are shown, not read (2026-10-08).** The task card displays what the officer wrote in his chat, but nothing interprets it: the rep still has to type the answer and press confirm / not possible. An officer who answers but whose reply nobody records keeps the task open and triggers the reminder and rep alerts.
- **Deadlines skip nights but not weekends or holidays.** "2 working hours" counts only 09:00–21:00 Riyadh; a Friday or a public holiday counts like any other day.
- **Incomplete Client Preferences** is a deliberate empty-state placeholder; the detection logic (which preference fields count as "missing") is not built yet.
- Tab membership is intentionally non-exclusive (a serious client can also be late). Counts on the tab badges reflect the current field-filter context.
- Manager scope follows `is_admin`; there is no separate "team lead sees their team only" tier yet — managers see everyone.
- Resolving the full client list each render mirrors the existing Clients cockpit; if the client count grows substantially, consider a lighter resolver that skips the unused per-client counts inside `resolveClientView`.
