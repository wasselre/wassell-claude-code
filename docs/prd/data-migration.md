## What it is (in plain English)

A guided wizard that turns the messy data developers send us — Excel files, PDFs, screenshots, photos, in any mix — into clean records inside any model, with a human approving every change before it lands. You open **Data Migration** (ترحيل البيانات) in the sidebar, start a new migration, pick which model to import into, and drop in your files. **Before** it extracts anything, you get a planning step: you can write **instructions** for how you want the data read, and the AI reads your files and comes back with **questions about anything that contradicts or is unclear** plus the **table structure it intends to produce** — so you confirm the plan *before* the table exists (or just hit "Start extraction" to skip ahead). Then the app reads them into one table, lets you review and fix that table, figures out which column maps to which field, and — for dropdown / multi-select / lookup fields — proposes how to standardize each raw value to match what the app expects (e.g. "شقه" → the option "شقة", "Apartment" → "شقة"), showing every proposed change as a before→after you approve, override, or redirect to a different field. When you're happy, you click **Migrate** and the records are imported.

Extraction is the smart part. **Before** reading your files the app looks at the target model's fields, so it knows *what to hunt for* (e.g. it knows you want a developer name) — but it captures values raw, never coercing them to the system (that's the later step's job). It writes numbers as plain numbers, and it **reads the floor plans deeply**: for each unit it counts the components (bathrooms, bedrooms, kitchens…) from the drawing and **combines that with the brochure text** — so an ambiguous "2 دورة مياة + الجناح الرئيسي يحتوي على دورة مياة" resolves to **3** because the plan confirms it. After extraction it writes you a **summary** of how it derived every value (especially each number, with its source), and you can **chat with it** to question a value or have it recount / pull a missed column by re-reading the brochure.

You don't have to start from messy files: if you already have a clean table, upload an Excel/CSV and choose **Use as data source** (or paste into the in-app grid) to jump straight to the review/mapping step. The upload step keeps **documents and Excel in two separate fields** so Excel is never silently forced into one behavior — you decide, per Excel file, whether it's analyzed like the rest or used as-is.

## Why it exists

Onboarding a developer's project + units used to be a manual, hours-long job: eyeball the files, retype into a spreadsheet, rename values to match the app's dropdowns, fix number/date formats, match developer/project names to existing records, then import. This wizard builds that whole process into the app, with AI doing the tedious extraction/matching and the operator staying in control via explicit approval gates.

## Key behaviors

- **One migration = one record** in the `data_migration` system model. The entire wizard state (target model, raw table, mappings, value decisions, result) lives on `record.data`, so you can close the tab and resume exactly where you left off.
- **Sidebar list management.** The left list isn't just navigation — each migration can be **renamed** (its `data.title`), **moved into a group** (a free-text `data.group` label; type an existing group or a new one), and **deleted**, all via a per-row ⋯ edit popover. Migrations render under **collapsible group headers** (named groups alphabetical, "Ungrouped" last, each with a count); a group can be **renamed** inline from its header (which re-labels every migration in it). Edits use the same single-writer `expectedVersion: null` save posture as the wizard. (`src/pages/DataMigration/components/MigrationList.tsx`.)
- **Any number of migrations run at the same time.** The two long jobs — AI extraction and the row-by-row import — run in a module-level **job runner** (`lib/jobRunner.ts`), keyed by migration record id and detached from the wizard's component lifecycle. Starting a new migration, switching between migrations, or navigating elsewhere in the app never stops a running job; coming back just re-attaches to its live progress (it never restarts — starting a job for a record that already has one is a no-op, which also kills the old remount-double-import bug). Outcomes (status flips, errors, results) are written onto the migration record, so the left list's pills stay live; rows with a running import also show an inline progress bar (`n/N`). Jobs are in-tab: a page reload interrupts them, and the wizard then shows an explicit **Retry extraction** / **Resume migration** state instead of a stuck spinner (resume re-skips already-imported rows only when the model has a duplicate-check field). Uploaded source files are persisted on the record at upload time (not at extraction end), so an interrupted extraction can always be retried. The import loop yields to the browser every 20 rows so very large offline runs don't freeze the tab.
- **Upload step = two fields, with the Excel choice made explicit.** The drop area is split:
  - **Field 1 — Documents (non-Excel):** PDF, images, screenshots. Always uploaded into the AI extraction set; never offered a "use directly" path (Claude has to read them).
  - **Field 2 — Excel / CSV:** each file you add gets a per-file choice. **Analyze with AI** (the default) treats it like a PDF — the workbook is converted to **one CSV text file per non-empty sheet** (Claude can't ingest raw .xlsx) and joins the AI extraction set, right for messy layouts (title rows, merged cells, sub-tables), multi-sheet workbooks, or combining a price sheet with a brochure. **Use as data source** parses the sheet in the browser (never sent to AI, straight to review — the clean-sheet fast path; first sheet only, multi-sheet warns).
  - **The two are mutually exclusive (block-mixing):** "Use as data source" is only available when that Excel is the **sole** file in the step (no documents, no other Excel); choosing it **locks both drop zones** (a chosen data source IS your whole table). To analyze documents and an Excel together, leave every Excel on **Analyze with AI** — they all merge into one AI-extracted table. Default-Analyze means by default an Excel is analyzed alongside whatever documents you add.
  - Both drop zones are **forgiving** — a file dropped in the "wrong" field is routed by type. You can also **start with a blank table**.
- **The raw table is yours to edit:** edit cells in-app, add/remove rows & columns, **download it as Excel**, fix it externally, and **re-upload** — or keep editing in place. Re-uploading replaces the table and resets downstream mappings (headers may have changed).
- **AI suggests column→field mappings**, you adjust them — and the AI suggestion is **unioned with exact header→label matching** so obvious columns still auto-map even if the AI returns nothing. Range fields expose two targets (min/max); **`table` fields expose one target per sub-column** (`field — sub-column`), and a list cell becomes one table row per item (sibling sub-columns zip by row). Non-importable field types (formulas, mirrors, auto-IDs, files/attachments/images, notes, and unit-derived rollups) are never offered as targets.
- **Value standardization with approval (the core promise):** for each dropdown/multi-select/lookup column, per distinct value you pick one of: select an existing option/record (a **searchable picker** — LookupCombobox for lookups, an option search for dropdowns), **create** a new option/record (with an editable label, only on explicit approval), **leave blank**, or **route** this value's rows to a different field (splitting a column). Nothing is created or changed until you click Migrate. "Accept all high-confidence" bulk-applies the ≥90%-confident proposals.
- **Controlled fields store exact references, never display text.** A lookup decision stores the **exact selected record id** — there is no record-id → display-name → re-match step, so two records that share a display name can't be confused. A dropdown/multi-select decision stores the **exact option value (slug)**. A value that can't be resolved to an option/record (and wasn't explicitly blanked) makes the row invalid; raw labels are never written into a controlled field.
- **Create-new is deterministic and dedup-safe.** New options get the app's shared `slugifyOptionLabel` value (the same hyphenated slug the record-form inline-create uses — not a migration-only scheme), deduped against existing options by Arabic-aware normalized label so "Villa"/"villa"/"فيلا" map to one option. New lookup records are deduped against existing target records by normalized display (link the existing one instead of minting a duplicate). Both are created **only at Migrate**, only for rows that actually migrate (excluded-row creates are pruned).
- **Frozen / system models handled explicitly.** Adding a dropdown/multi-select option to a frozen model is safe and allowed (options live in the JSONB schema — no DDL, same path the record form uses) and is flagged in preview as "added to schema". Creating a lookup record into a target that needs required fields we can't fill (or a custom-UI/system model) is **blocked with an actionable error** in the standardize + preview steps — never a silent invalid record.
- **One shared normalizer everywhere** (`@/lib/textMatch.normalizeMatch`): deterministic pre-match, AI-proposal matching, option/record lookup, and duplicate detection all use the same Arabic-aware normalizer (strips diacritics/shadda, unifies alef/ya/taa-marbuta, lowercases) — no path silently fails where another succeeds.
- **Multi-select stays multi-value end-to-end** — a cell is split per token on comma / Arabic comma `،` / semicolon / newline (one shared splitter), each token standardized independently to its exact option value, never collapsed to one. Any unresolved token blocks the row unless explicitly blanked.
- **Routed values are re-standardized for their destination.** A value moved to another field is resolved against that field's type — dropdown/multi-select → a valid option value, lookup → an existing record id, number/range → validated/converted, text → passed through. An unresolvable routed value makes the row invalid (it is never dumped raw).
- **Pre-extraction prep — instructions + clarify before the table exists.** Every AI extraction first lands on a **prep** step (between upload and extraction). You can write free-text **instructions** (e.g. "use the price list not the brochure for prices; areas in m²; skip sold units; if the plans disagree with the sheet, ask me"). Pressing **Review files & clarify** sends your instructions + the files to the AI, which replies in a **chat** with a short summary/plan, and surfaces every **contradiction between sources** and anything **unclear** as **answer cards** (a quiz) shown below the chat — NOT buried in the chat prose. Each card shows the question (tagged contradiction vs. clarification) + the conflicting specifics, with its own answer box; you answer **in the card or in the chat** (both feed the next turn), and an `n/N answered` counter tracks progress. The AI also proposes a **table structure** (each column + how it'll derive that column's values) in its own panel. Each turn re-reads the files, drops the questions you've resolved, and refines the structure. **Extraction is BLOCKED until every question card is resolved** — "Start extraction" is disabled with an "answer N questions first" lock while any remain (a hand-off with no contradictions surfaces no cards, so it stays one click). Your instructions + the resolved Q&A + the confirmed structure are bundled into an **operator-guidance** block passed into the actual extraction (discover/fuse or project-extract), steering it without ever licensing the AI to clean/translate/coerce raw values. The Excel **Use as data source** and **blank table** paths bypass prep entirely (no AI). State persists on the record (`extraction_instructions`, `prep_chat`, `prep_structure`, `prep_questions`), so you can close the tab and resume. The conversation, cards, and structure render from **local component state** (seeded from the saved record, like the review step's `draft`) so a transient realtime echo can't blank the in-progress view; every turn still persists in one write.
- **Source-fusion extraction (records mode — units, clients, any non-projects target).** Extraction is NOT a spreadsheet import and the Excel is NOT the source of truth: the AI reads ALL uploaded files, identifies every unit, and **merges facts per unit from every source**. Two phases run automatically (the upload spinner shows which): **discover** (scan + classify the files, build the unit index + canonical headers) then **fuse** (resolve units in batches, one row per unit, ≈20 at a time). Each unit's columns are pulled from wherever the data lives — number/status from the sheet, price from the price list, area from the brochure, **bathrooms/bedrooms/components counted from that unit's floor plan**. When sources disagree the AI picks a value (floor-plan for counts, latest price list for price) and records the disagreement in a **Source conflicts** panel for you to verify. Because units are batched (and a too-dense batch auto-splits), arbitrarily large unit lists extract without ever overflowing the model's output — and a genuine truncation fails **loudly** (red Failed + retry), never as a silent empty table.
- **Model-aware extraction (the hunt-list).** The chosen target model's fields are sent to extraction as a "what to look for" list — so the AI knows to find a developer name, a unit type, bathroom/bedroom counts, etc. — and it adds extra columns for any other useful data it finds. It is explicitly told **not** to clean, normalize, or coerce values to fit the system (raw is fine; cleaning is the standardize step). Numeric data comes out as **bare numbers** (`3`, not "3 دورات مياه"). Computed rollup fields (`is_computed` — the All Projects unit-derived ranges/counts) are excluded from both the hunt-list and the mapping targets, since they're recomputed live from units and an imported value would be silently ignored.
- **PROJECT-PROFILE mode (target = All Projects) — three outputs from one extraction.** When the migration target is the projects model, the system understands you want a detailed understanding of the **project as a whole**, not individual unit records:
  1. **The migration table** flips from "one row per unit" to **one row per project** (normally exactly one): the project's general information in detail — developer, location, type, status, unit types/models offered, amenities, guarantees, payment terms, licenses — with units still read deeply (floor plans included) but **aggregated, never enumerated as a unit table**.
  2. **A project-level intelligence briefing** (`data.project_intelligence`): titled sections that explain the project itself — overview, developer, location & neighborhood, concept & positioning, target audience, advantages, amenities, construction status, guarantees, design philosophy, architecture & facades, unit mix, pricing insights, area insights, distinguishing features, unique selling points. Factual and grounded; insights may include arithmetic derived from in-file numbers (clearly phrased as derived) but never external market knowledge; unsupported dimensions are omitted. Shown read-only in its own collapsible panel in the review step; persisted on the migration record; and **on import, flattened to one Markdown document (a `## heading` per section) and written into the project record's `project_analysis` field** (`ANALYSIS_DOC_FIELD`, via `renderProjectAnalysis` in buildRecords — same injection pattern as the marketing document; an explicit column mapped to `project_analysis` wins over the injection).
  3. **The Arabic Project Knowledge Document** (الوثيقة التسويقية): a comprehensive Markdown source of truth for the **sales, content, and marketing teams** — complete description, project story & positioning, location, developer, every unit model with its specs, design & architecture, construction info, finishes, amenities, guarantees, prices/payment plans as stated, key selling points, competitive advantages, target customer profile, and a closing quick-facts list. Informative, marketing-oriented prose — always in Arabic regardless of UI language, grounded only in the files. Appears as its own **editable panel** in the review step, is persisted on the migration record (`data.project_document`), and on import is written into the project record's **`marketing_document`** field (Project Content section) — where the record form shows it and the copywriter agent's `get_project` fact sheet picks it up automatically (sales people keep using the Units model for per-unit detail). An upload-step banner explains the mode; an explicit column mapped to `marketing_document` wins over the injection.
- **Counting happens IN extraction, from the floor plans.** There is no separate step-2 counter. For each unit the AI deeply analyzes its floor plan — matched to the unit by its type label (`نموذج A1` on the plan = the A1 row) — counts the components from the drawing (bathrooms = WC fixtures, bedrooms, kitchens…), and **combines that with the brochure text**, trusting the plan on disagreement. So "2 دورة مياة" + a master en-suite resolves to **3**. Counted values are ordinary numeric columns you map and review like any other; the AI's explanatory text follows the UI language (Arabic in the Arabic app).
- **Post-extraction summary + discussion chat (raw-table step).** Extraction returns a plain-English **summary** of what it captured — especially *how* each number was derived and its source (text / plan / both). Below it is a **multi-turn chat**: ask the AI to explain a value, or instruct it to recount / fill / add a column — it re-reads the brochure (incl. the plans) and returns column edits that are merged into the grid (existing columns are overwritten with its non-empty values, new columns appended; nothing fabricated). The summary + thread persist on the record. (Supersedes the one-shot "Ask AI" enrichment.)
- **Lookups avoid duplicates:** "link existing" stores the matched record's **exact id** (not its display) so the right record is linked even when display names collide; "create new" registers a pending record that is deduped against existing records by normalized display at migrate time. Only a genuinely-new name mints a new developer/project.
- **Standardization matches existing values reliably:** every distinct value is first matched **deterministically** (Arabic-normalized — strips diacritics/shadda, unifies alef/ya/taa-marbuta — so "شقه"→"شقة", "ريا"→"ريّا النخيل") against the field's options or **all** lookup records; only genuinely-unmatched values are sent to the AI. This is essential for large lookups (e.g. all_projects = 1,371 records, far more than fit in one AI prompt). For lookup columns the per-value control is a **searchable record picker** (LookupCombobox); for dropdowns it's a searchable option picker — so you search instead of scrolling.
- **Editable raw grid:** edit cells, add/remove rows & columns, and **fill-down** a column (type a value in the top cell, click ⤓ to apply it to every row). Excel/CSV is read as UTF-8 (Arabic is safe even without a BOM).
- **Final preview = strict + auditable:** before anything is written, the preview shows every record that *will* be created with resolved display values (option labels, linked-record names — including pending "create new" names) plus per-cell **action markers** (link / new / routed) and a summary of pending new options + new lookup records. Each valid record has a checkbox (approved by default); deselect any you don't want. **Rows with a blocking error** (an unresolved controlled value, a mapped-but-blank required field, a blocked create, an invalid number, an invalid routed value) are shown highlighted with their reasons but **cannot be selected and never migrate**; non-blocking issues (e.g. an unmapped required field) show as warnings. Exact duplicates are auto-skipped and counted. Built on a shared, pure `buildMigrationPlan`, so what you approve is exactly what gets saved.
- **Migrate is strict and decision-driven.** The migrator builds records directly from the approved decisions (exact option values / record ids) — it does **not** round-trip through `mapImportedRows` for the migration path, so a raw label is never silently stored in a controlled field. For the approved + valid rows it creates the referenced new options (into the model schema, frozen-safe) and new lookup records, then saves via the standard `saveRecord` path so auto-IDs, formulas, frozen-model dispatch, duplicate-skip, and the offline retry queue all work as elsewhere. Per-row failures are reported, never silently dropped. (`mapImportedRows` remains the core of the separate Excel **Import** modal.)
- **`data_migration` is never freezable and never a migration target** (it's excluded from the target picker and the Freeze modal).

## User flows

1. **Main happy path (messy files):** New migration → pick model → drop PDF/images → *Next: instructions & review* → **prep step** (optionally write instructions; *Review files & clarify* → answer the AI's questions / confirm the proposed structure — or skip) → *Start extraction* → review/fix the raw table → *Suggest column mapping* → adjust → *Review values* → approve/override each value → *Preview records* → approve/deselect each record → *Migrate* → "Imported N records into <model>".
2. **Fast path (clean data — "start at step 5"):** New migration → pick model → drop a clean Excel/CSV into the **Excel / CSV** field → switch it to **Use as data source** (or start blank + paste) → review → mapping → standardize → migrate.
3. **Messy Excel path:** New migration → pick model → drop the Excel into the **Excel / CSV** field → leave it on **Analyze with AI** (add brochures/PDFs to the Documents field too if you have them) → the workbook becomes per-sheet CSVs in the extraction set → *Next: instructions & review* → prep (clarify/confirm or skip) → *Start extraction* → continues like the messy-files flow.
4. **Project onboarding (All Projects target):** New migration → pick **All Projects** (banner explains project-profile mode) → drop the developer's full hand-off (brochure, price list, plans) → *Next: instructions & review* → prep (e.g. instruct "treat each نموذج as a model, not a unit"; let the AI flag any contradictions + confirm the structure, or skip) → *Start extraction* → ONE project row + the project intelligence briefing + the Arabic knowledge document → review (the intelligence and the document each have their own panel; the document is editable) → mapping → standardize (developer lookup, city, unit types…) → preview (note confirms the document is included; long-text cells are clamped) → *Migrate* → one project record created with `marketing_document` filled.
5. **Edit-and-re-upload:** at the review step, Download Excel → fix in Excel → Re-upload corrected (mappings reset) → continue.
6. **Parallel migrations:** start migration A's extract or import → click **New migration** and work on B (or C…) while A keeps running — the list shows each row's live status pill + import progress; click any row to re-attach to its progress.
7. **Error/empty states:** an AI step that fails or times out shows a loud toast + the wizard stays put so you can retry or fall back to manual mapping (a failed extraction/import also flips the record to a red **Failed** pill with the error persisted on the record + a Retry button); a run interrupted by a page reload shows an explicit interrupted state with Retry/Resume; a model with no dropdown/lookup columns skips straight to a "ready to migrate" state; very large tables (>500 rows) render the first 500 for in-app editing with a note that all rows still migrate (edit the rest via download).

## Data touched

- **Reads:** `models.schema` (target field types, options, lookup config), `records.data` of the lookup-target and target models (existing values for matching + duplicate-skip), uploaded files in the `wassel-migrations` Storage bucket.
- **Writes:** `records.data` (JSONB) for the imported rows + any approved new lookup records (created with the plan's stable temp id, deduped against existing), via `record_save`; the target model's `schema` when the user approves new options (deterministic slug; safe for frozen models — JSONB only); the `data_migration` record's own `data` at every step (resume state — including the per-value standardization decisions, preview exclusions, and validation derives from them); uploaded files to `wassel-migrations` (`<auth.uid()>/<recordId>/uploads/...`).
- **AI:** `POST /api/migrate` (`action: plan | extract | discover | fuse_batch | suggest_mappings | standardize | discuss`). **plan** is the pre-extraction prep turn (`runPlan` / forced `emit_plan`): given the conversation so far + the operator's `instructions` + the signed-URL files + the field hunt-list, it returns `reply` + `questions` (contradictions / unclear items) + `proposed_columns` (header + how-derived) + `ready` — it does NOT extract any rows. The extraction actions accept an optional **`guidance`** string (instructions + resolved clarifications + confirmed structure) that's injected into their prompts. For **per-record targets** (units, clients…) extraction runs as **discover** (files → unit index + canonical headers) then a series of **fuse_batch** calls (a batch of units → one merged row each + cross-source `conflicts`); both are vision-deep, and the client prompt-caches the files across batches and **auto-splits** any batch the model truncates (a truncation returns `code:'max_tokens'`, never a partial save). **extract** (now the All Projects / `mode:'project'` path) is model-aware + vision and returns one aggregated row + a `summary`, plus the `intelligence` sections + the Arabic knowledge `document`. Every phase fails loudly on truncation (`requireToolInput` / `ExtractionTruncatedError`). **discuss** is the multi-turn chat (re-reads the brochure to recount/revise). Vision model for extract/discuss-with-files, text model for mapping/standardize. No data is persisted server-side; the endpoint fetches signed-URL files and returns structured JSON. Accepted file kinds: images, PDFs, and **CSV/plain text** (Excel sheets arrive as client-converted CSVs) — text is inlined as fenced blocks, char-capped (120k/file, 300k total) with line-boundary truncation reported via `truncated`/`files_skipped`.
- **Project-profile writes:** the live `all_projects` model gained a `marketing_document` textarea (Project Content section, added 2026-06-11 via SQL on the unfrozen model; `v_all_projects` regenerated automatically). `buildMigrationPlan` injects `data.project_document` into each built record's `marketing_document` (explicit column mapping wins), so preview = exactly what's written.
- **Bulk RPC available (not yet wired into the live path):** `records_bulk_save` + `record_reserve_auto_ids` exist as a future fast-path for very large imports.

## Open questions / known limitations

- **Model-aware extraction verified live (2026-06-03):** `runExtract` was run against the real ريّا النخيل brochure (54 pages, 39 unit models) — it produced model-aware columns, bare numbers, and **plan-derived bathroom counts that combine the plan with the text** (A1 → 3 = "2 دورة مياة" + master en-suite, exactly matching the source), plus an Arabic summary explaining each number's source. `runDiscuss` answered a sourced "how many bathrooms?" question correctly. Mapping/standardization quality still benefit from in-app spot-checks (MFA-gated); the non-AI paths (clean-Excel entry, grid editing, mapping adjustment, value approval, route-to-field, migrate) are fully verified.
- **Extraction size:** records-mode source fusion removes the old single-response output cap — units are discovered as a small index and resolved in auto-splitting batches, so unit count is no longer the limiter (the guard makes any genuine overflow fail loudly, never silently). The remaining bounds are Anthropic per-request **input** limits (images ≤5MB, ≤20 files, ~24MB total / 300k text chars) shared by every phase, and discovery enumerating a very large index in one **non-streaming** call (capped at the SDK's 16k-token non-streaming ceiling — `max_tokens` above that makes the SDK refuse with "Streaming is required…"; a bigger index hits the loud truncation guard → split the input). Cost/latency scale with batch count (prompt caching keeps the per-batch file cost low). All Projects (project mode) is still a single small-output call.
- **Source-fusion not yet live-verified:** the pipeline typechecks (SPA build + `api/` tsc clean) but has not been run end-to-end against a real project yet — needs a live extraction (e.g. the جزيل / Jazeel hand-off: units PDF + brochure + CSV → expect ~116 fused unit rows) to confirm discovery completeness, per-unit fusion accuracy, conflict surfacing, prompt-cache savings, and auto-split. The `/api/migrate` actions only run in the deployed/`vercel dev` environment (vite dev doesn't serve `/api`).
- **Pre-extraction prep step not yet live-verified:** the `plan` action + `StepPrep` + the guidance threading typecheck and build clean, and the UI shell was exercised with a mocked `/api/migrate` (vite dev doesn't serve `/api`). Still needs a deployed run against real contradictory hand-off files to confirm the AI surfaces contradictions, the proposed structure tracks the conversation, and the produced table honors the instructions/guidance (records mode + project mode).
- **Bulk insert path:** the live migrate uses `saveRecord` per row (correct + proven, slower at scale). `records_bulk_save` is built and DB-verified but not yet wired in — a clean follow-up to speed up multi-thousand-row imports.
- **Routed values ARE now re-standardized** (fixed 2026-06-18): a value moved to another field is resolved against that field's type, and an unresolvable routed value blocks the row instead of being stored raw.
- **Excluded-row creates ARE now pruned** (fixed 2026-06-18): a new option / lookup record is created only if a row that actually migrates references it; deselecting that row in preview drops its create too.
- **Required-field validation is two-tier by design:** a required field that was *mapped* but resolved to blank is a hard error (row blocked); a required field with *no source column at all* is a non-blocking warning (the wizard can't fill data it never received). This is a deliberate practicality call — blocking every row for an unmapped required field would make legitimate partial imports impossible.
- **Value-mapping memory not implemented yet** (explicitly deferred): standardization decisions aren't remembered across migrations — each migration re-resolves from scratch. A reusable mapping memory is a planned follow-up.
- **Scope rules on multi-value fields of frozen models** still fail closed (a pre-existing frozen-model RLS limitation, unrelated to this layer) — see data-storage.md.
- **One target model per migration:** units link to projects via the normal lookup auto-match (a "project name" column resolves/creates the project) — there is no combined parent+child wizard.
