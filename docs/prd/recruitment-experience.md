## What it is (in plain English)
A private, guided pre-interview experience for a single shortlisted sales candidate — sent as a personal invitation link **after** we've reviewed their application. Its purpose is to make sure the first office meeting isn't spent explaining the job from scratch: before booking an interview the candidate learns how the daily work happens inside Wassel, watches a short video, tries a small guided task, reviews the offer, and decides whether they're still interested.

**What's built now is only the first content page** of that flow, in two parts. It **opens with the value story** (the visual anchor of the page): a salesperson isn't limited to one project/city/country — at Wassel they can sell across **100+ current projects (Riyadh + Dubai, expanding to new markets)** — and that's possible because the system manages the knowledge, recommendations, customer history and follow-ups, so nothing has to be memorized. **Then** a calm, fully-Arabic/RTL scrolling **workflow walkthrough** provides the evidence — faithful reproductions of the real Wassel interface showing one customer's journey from first call to next follow-up. A "شاهد طريقة العمل" button hands off to **Stage 2, the video** — a full-screen page that plays the walkthrough recording (~7 min, 1080p, hosted in the public Supabase Storage bucket `hire-assets`, not in the repo) with the progress rail on الفيديو — which in turn leads to the practical-task stage (still a stub).

## Why it exists
Real-estate salespeople normally can only carry one or two projects because of how much information a sale involves. The page reassures a candidate that inside Wassel they don't have to memorize projects, units, prices or plans — the system surfaces the right information at the moment they're talking to a customer — so a strong candidate self-selects in (or out) before we spend an interview slot on them.

## Key behaviors
- **Per-candidate link tied to `job_applications`.** From `/careers/applications`, an admin taps **«إرسال رابط التجربة عبر واتساب»** on an applicant → the app mints a per-candidate secret `invite_token`, **auto-sends the personal link over WhatsApp** (operations line if configured, else the active default number; through the same gateway as every other send), and flips the status to **`offer_sent`** (stamping `offer_sent_at`). The drawer shows the link (copyable), a resend button, whether they confirmed, and their decision + decline reason.
- **Confirm gate at entry.** Opening the link resolves the token → the candidate sees «أهلًا {name} 👋» with their real name + phone and a **تأكيد** button (plus a "بياناتي غير صحيحة" note telling them to contact us — no editing, per "they just confirm"); confirming stamps `experience_confirmed_at`. `preview` / unknown tokens fall back to a labelled demo so internal preview + local dev (no `/api`) still work.
- **Decision auto-updates the application status.** At the end of the offer: **«مهتم — احجز مقابلة»** → status **`offer_accepted`** + «سنتواصل معك لتحديد موعد زيارتك للمكتب». **«العرض غير مناسب لي»** → a **2-step questionnaire**: (Q1) «ما سبب عدم اهتمامك؟» with **الراتب / العمولة / سبب آخر**, then (Q2) a follow-up — salary → «ما الراتب الشهري المناسب لك؟», commission → «ما نسبة العمولة المناسبة لك؟», other → free text «ما السبب؟» — → status **`offer_rejected`** + `experience_decline_category` + `experience_decline_reason`. A decision is only accepted from a live pre-hire state. Same statuses the pipeline already uses (للمقابلة → تم إرسال العرض → قبِل/رفض العرض).
- **The WhatsApp message is admin-editable.** `careers_settings.experience_message` (a singleton, `{name}` / `{link}` placeholders) is read by the send endpoint at send time; the admin edits it + sees a live preview from a **Settings gear** on `/careers/applications`. If the template drops `{link}`, the link is force-appended so it's never missing.
- **Offer-experience funnel on `/careers/applications`.** A summary strip computed from the loaded rows: **أُرسل الرابط · لم يُفتح · فُتح · فتح ولم يُكمل · مهتم · اعتذر** — a quick read of how candidates move through (or stall in) the experience. Inside each applicant's drawer, an **`ExperienceTimeline`** shows THAT person's journey — a current-status headline plus a 3-step stepper (أُرسل الرابط → فتح الرابط وأكّد بياناته → القرار) with timestamps, and the decline reason/category when applicable.
- **Security = the token, same as `/share/:token` and `/rate/:token`.** The browser never touches `job_applications`; the confirm/decision go through the rate-limited, token-authed, service-role `api/careers/experience`; the admin send goes through `api/careers/send-experience`, admin-gated by reading the row through the caller's JWT (`wassell_is_admin`) before doing anything. No new RLS.
- **Opens with the "why", phone-first, before any product screen.** A dedicated value intro (`OpeningSummary`) leads the page, designed at phone width (360/390/430) first, in three visually distinct sections: (1) **the scale** — a prominent «+100», الرياض/دبي/أسواق-جديدة chips, and a **swipeable RTL carousel of real Wassel project photos** (Riyadh + Dubai, one card + a peek of the next on phones) ending in an "أسواق جديدة" expansion card; (2) **how it's possible** — a compact vertical overview (preference chips → two matching real-project recommendations → a prepared WhatsApp message with project material + a unit-file preview), labelled an overview with the detail left to the workflow, and any send control illustrative only; (3) **follow-up organized** — a compact auto-scheduled follow-up task (مجدولة تلقائيًا) for the same customer, a ملخص العميل panel, and an obvious next-contact call action. It ends with «شاهد كيف يحدث ذلك أثناء مكالمة واحدة ↓» linking (`#hire-workflow`) into the walkthrough. The three take-aways: one project limits your customers → Wassel gives 100+ across Riyadh & Dubai (expanding) → you can handle that scale because the system manages the knowledge/recommendations/history/follow-ups.
- **Phone-first constraints:** body text 16–18px, focused phone-sized cards, ≥44px touch targets, horizontal scrolling contained to the carousel only (no page-level overflow at 360/390/430), and a compact sticky progress rail that never covers content.
- **Stage 4 — the offer** (`/offer`, progress rail on العرض): compensation cards (3,000 ريال salary · 15% of **Wassel's commission** on each deal, made explicit it's not 15% of the property price · 300+ leads/month), a worked commission example (12,000 → 1,800), and an **interactive first-year income graph** — a self-contained SVG line chart (salary line + income line, tappable points + a keyboard-accessible month slider, no hover reliance) whose series is computed from the exact model (m1=0 sales, m≥2 sales=1.2^(m-2), +3,000 salary, 1,800/sale), with a per-month breakdown (sales to 2dp, currency whole riyals). Then the year-one target card (300×2%=6 sales → 13,800/mo, kept distinct from the model's ~6.19/14,145 in month 12; neither a cap nor a guarantee), working arrangements (6 days · 12–8 · الرياض حي النزهة · office-first with later remote after proven performance + approval), the closing statement, and two actions — «مهتم — احجز مقابلة» (→ `/book`, framed as interest in an interview, not contract acceptance) and «العرض غير مناسب لي» (→ `/decline`). No benefits/insurance/payout-timing are stated. All figures illustrative.
- **Stage 3 — the guided practical task** (`/task`, progress rail on التجربة): a 3-step preset simulation that demonstrates *more projects preserve the deal*. A fictional customer (أبو فيصل) enquires on WhatsApp about a REAL project that's **over his budget** (فلل رِفان, from 2.77M); the candidate **(1)** taps chips to record his needs (the message stays pinned/visible, no typing, no distractors) → **(2)** وصل recommends **two genuinely suitable, in-budget real alternatives** (سديم فلل 2.14M · أديم الفرسان 1.0–1.49M) and the candidate picks one → **(3)** sends its prepared message (simulated). It ends with a passive auto-scheduled follow-up + client summary and a CTA to the offer. No-fail (both options fit), persistent "محاكاة تجريبية" label, everything simulated (no calls/messages/records/matching call). Takeaway: «المشروع الأول تجاوز ميزانيته، لكن كان عندي بديل مناسب أقدّمه — دون أن أحفظ باقي المشاريع».
- **Private, public-link, no auth.** Renders outside `AppLayout`, forces `dir=rtl` / `lang=ar` on mount (restores on unmount), and requires no login. A `:token` identifies the invitation; there is **no token validation yet** (out of scope for stage 1) — the page renders for any token, and `/careers/experience` with no token is a testable preview.
- **Invitation progress rail (sticky).** A five-stage indicator pinned to the top — التعريف ← الفيديو ← التجربة ← العرض ← القرار — with التعريف active. Shows the candidate where this page sits in the wider experience.
- **Scale over documentation.** Each of the seven steps shows ONE **enlarged, focused** product screen (a clean titled `Screen` panel — **no app sidebar**, generous padding, larger type) so the detail is readable without zooming. Deliberately reworked away from the first pass, which shrank whole dashboard pages (with a repeated sidebar) and read like a help article.
- **One continuous journey, not seven screenshots.** The steps hang off a single connected copper timeline spine (numbered nodes), with short causal **flow connectors** between them ("حُفظت التفضيلات — يبدأ واصل بالمطابقة" → "اختار الموظف واحة النرجس" → …). One fictional customer (خالد العتيبي) runs throughout, and the captured preferences are echoed as chips in step 2's matching header. Data is fictional but shaped exactly like real records (field slugs, labels, option colors from the live `clients` / `all_projects` / `units` schemas). **No real client PII and no live data** — deliberate for an external link.
- **Visible, causal interactions:** step 2 runs a ~2s "matching 312 projects" search (IntersectionObserver) that resolves to recommendation cards (ours first); step 4's "إرسال رسالة المشروع الجاهزة" animates the fact-checked message + image gallery + the client's reply into the thread; step 5 selects a unit (updates panel + floor plan) and "إرسال المخطط" shows a sent confirmation; step 6's auto-task pops in. Sections fade up on scroll.
- **Real-looking project imagery, never empty placeholders.** `ProjectImage` renders self-contained, layered SVG architectural scenes (sky + sun/moon + massed building with lit windows + palms + ground) in four variants (villa day/dusk, tower, pool), used in the cards, the project hero, the media gallery and the WhatsApp message. Crisp at any size, on-brand, PII-safe. The unit floor plan is a hand-drawn SVG.
- **Reuses the real design system** (copper/sand/charcoal tokens, Amiri, `.card`/`.form-input`/`.badge`, pure `Button`/`Badge`); store-bound screens are transcribed as static markup.
- **The seven steps:** (1) active call + preference form; (2) recommendation cards; (3) project detail (hero + KPIs + tabs); (4) WhatsApp project message send; (5) units table + floor plan + send; (6) auto-created follow-up task; (7) client 360 + AI-style summary.
- **Dominant video hand-off.** The page ends with a large video-thumbnail block (oversized play button) plus a big «شاهد طريقة العمل» button → the (stubbed) video stage.
- **Off-plan always surfaced** («على الخارطة» pill); **no salary/commission anywhere** (that comes later in the flow).

## User flows
1. **Main happy path:** candidate opens their invitation link → reads the opening copy → scrolls the seven product steps → reads the closing statement → taps **شاهد طريقة العمل** → routed to the video stage.
2. **Preview (internal):** open `/careers/experience` (no token) to review the page.
3. **Next stage (stub):** the video route currently renders a clearly-labelled placeholder ("مرحلة الفيديو … قريبًا") with a link back to the walkthrough.

## Data touched
- **None.** Fully static/self-contained by design (public link, no auth, no PII). No tables read or written.

## Open questions / known limitations
- **Stages 1–5 exist (intro + video + task + offer + decision).** The decision records interested/declined and updates the application; the actual appointment-time *picker* (choosing a slot) is still future — «مهتم» currently means "we'll contact you to schedule."
- **Per-candidate link is wired to `job_applications`** (admin auto-sends over WhatsApp; confirm gate; decision updates status). The endpoints only run on Vercel `/api`, so the DB/WhatsApp path is verified on prod, not local dev.
- **⚠ Unresolved business terms — do NOT present the offer as final to candidates until settled** (and do not invent them on the page): (1) **commission payout trigger + timing** — when the 15% is earned/paid relative to the deal; (2) **remote-work eligibility criteria** — what "proven performance + approval" concretely means; (3) **health insurance** — the owner previously said none, but a mandatory-coverage issue was raised and is unresolved. The page deliberately states none of these. This is why the offer is built but has not been deployed.
- **The video lives in Supabase Storage** (public `hire-assets` bucket), referenced by a hardcoded public URL in `HireVideoPage.tsx` — not in the git repo. To replace the recording, upload a new `system-intro.mp4` to that bucket (or upload under a new name and update `VIDEO_URL`). The object is served with `cache-control: no-cache` (Supabase default); if bandwidth matters, re-upload with a long `cache-control`.
- **Invitation token now exists** (per-candidate `invite_token` on `job_applications`; confirm gate; decision writes back). Note the intro/video/task screens still render for any token value — the token gates the *confirm + decision* (identity + status), not each stage's visibility; a `preview` token is the intentional demo. Tightening every stage behind a valid token is optional future work.
- **The intro and the task use real project photos** (our_projects' `main_image`s re-hosted to the public `hire-assets/projects/` bucket — 8 for the intro carousel + سديم فلل / أديم الفرسان for the task). The **workflow steps below still use self-contained SVG renders** (`ProjectImage` + a hand-drawn floor plan) — fine as an illustrative demo. If a project's `main_image` changes, the intro keeps the copy re-hosted at intro-build time; re-run the re-host to refresh.
