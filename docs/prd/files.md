## What it is (in plain English)
A Google-Drive-style file library inside Wassell CRM, reachable from the sidebar at `/files`. Users can upload images, PDFs, videos, documents, and archives, organize them into nested folders, preview them inside the app, and either share them with other Wassel users by role (viewer / editor / owner) or generate a public `/share/:token` URL for external customers. Folders cascade: sharing a folder grants the recipient access to every file and subfolder inside, recursively. A dedicated "Shared with me" tab shows everything other Wassel users shared with the caller. Public share pages are heavily Wassel-branded — the customer who opens a link sees the Wassel castle logo, brand palette, and Amiri typography front-and-center.

## Why it exists
Today users keep contracts, brochures, site photos, and references on Google Drive or WhatsApp media, disconnected from the CRM. This brings those assets into the workspace so a contract sits next to its client record, a brochure sits next to its project record, and external share links double as a sales asset — opening one is a small "wow" moment for customers.

## Key behaviors
- **Storage is private by default.** No file ever has a public URL — the SPA mints 5-minute signed URLs for previews; the public `/share/:token` endpoint mints 10-minute signed URLs after validating token + password.
- **Path traversal is impossible.** A file's storage path is server-built as `<auth.uid()>/<file_id>.<safe_ext>` from a fixed MIME→extension map. The user's original filename is display-only.
- **Permissions follow a three-rung ladder:** `viewer` < `editor` < `owner`. Owners can delete, regrant, and revoke. Editors can rename / move / share. Viewers can only see and download.
- **Folder sharing cascades.** Granting `viewer` on a folder gives the recipient `viewer` on every file/subfolder inside, transitively. Direct file grants always override the cascade (so a folder-`viewer` can be promoted to `editor` on a single file).
- **Frozen-model record attachments are soft FKs.** `files.record_id` can point at a row in `records` OR in a frozen-model table. No hard FK is enforced — UI handles "linked record gone" gracefully.
- **Record fields can store pointers into the Drive.** The Model Builder offers five field types — `image`, `multi_image`, `file`, `multi_file`, and `attachment` — that store `files.id` (or `folders.id`) on the record instead of inlining bytes or URLs. Uploads through these fields hit `uploadFile` with `model_id` + `record_id` populated, so the file appears under both the record AND the Drive's normal view. The `attachment` type can reference whole folders (`{type:'folder', id}`) so a record can point at "all photos for this property" as a moving target rather than a frozen list. See model-builder.md "Drive-backed fields" for the field-side config.
- **All file ops write to `activity_log`** with `category='file'` and `event_type` ∈ `upload | view | download | move | folder_create | folder_delete | permission_grant | permission_revoke | share_created | share_revoked | shared_view | delete`.
- **External share links** support optional password (bcrypt-hashed via pgcrypto), optional expiry, allow_download toggle, view counter, and one-click revoke.
- **MIME allowlist** (~25 common types: png/jpeg/webp/gif/heic/svg/bmp/tiff, pdf/doc/docx/xls/xlsx/ppt/pptx/txt/csv/md, zip/7z/rar/gz, mp4/webm/mov, mp3/wav/m4a/ogg). Executables and unknown types are rejected by the bucket itself.
- **Max file size:** 500 MB (bucket-level + client-side double-check).
- **`allow_download=false` is casual gating** — the inline-preview signed URL is still reachable, so a determined viewer could scrape it. Sufficient for "please don't download" intent, not for confidentiality.
- **Public share page is brand-first** — Wassel castle logo, gradient cream/sand background, Amiri serif headlines, copper-bronze CTAs. Reuse-of-brand is deliberate: every external customer who opens a link sees Wassel.
- **Bulk select (Google Drive style).** Each tile shows a circular checkbox in the corner — hover-revealed when nothing is selected, always visible once selection is active. Click the checkbox to toggle without opening the file. A rubber-band marquee is available by mouse-dragging from anywhere in the grid; Shift adds to the existing selection, Ctrl/Cmd toggles symmetric-difference. **The marquee edge-auto-scrolls** — dragging into the top/bottom ~64px of the viewport scrolls the page (speed ramps with how close to the edge the cursor is, on a `requestAnimationFrame` loop so it keeps scrolling while the mouse is held still at the edge), letting a single drag select past the fold. The marquee anchor + rectangle are tracked in **grid-relative coordinates** (not viewport coordinates), and the selection box is rendered `absolute` inside the scrolling grid, so the box stays pinned to the tiles it covers no matter how far the page scrolls — manual wheel/trackpad scroll mid-drag stays correct too. Plain-clicking a tile when something else is selected replaces the selection with just that one tile. Keyboard: `Esc` clears, `Ctrl/Cmd+A` selects every visible tile. The selection survives marquee-drag releases but is cleared when the user navigates between folders or tabs. A floating bulk-action bar — pinned to the bottom-center of the viewport (`position: fixed`, deliberately kept out of the document flow so selecting never reflows the grid) — shows `N selected` and `Download` / `Move` / `Delete` buttons; each button is auto-disabled when the user has no permission for any item in the selection (delete + move both gate on per-item ownership). Folder bulk-move is intentionally not exposed yet — the bar's Move button only addresses the file rows in the selection.
- **In-preview rename.** The full-screen `FilePreviewModal` header exposes a Rename button (gated by `canEdit`). Clicking it turns the filename label into an inline input + ✓/✕ buttons; Enter saves, Esc cancels. The same modal also has Download / Share / Permissions / Delete, so the preview is a complete "view + manage" surface — users no longer have to dismiss the preview to rename or delete the file they just opened.
- **Drive picker (`DriveBrowserModal`) is no longer pick-only.** Image files render their actual thumbnail (lazy `signViewUrl`). Every file tile gets a kebab with **Preview / Rename / Delete** (Preview is always shown; Rename + Delete are gated on `uploaded_by_user_id === currentUser`). Every folder tile gets a kebab with **Rename / Delete** (gated on `created_by_user_id === currentUser`). Rename is inline within the tile; Preview opens the full `FilePreviewModal` stacked above the picker so the same Rename/Share/Delete actions are reachable there too. The picker still confirms the picked selection on the footer button — edits are side effects, the primary intent stays "pick".
- **Wassel Documents (`kind='wassel_doc'`)** — first-class native rich-text documents that live in the Files system but never touch the Storage bucket. The Files header has a **New Document** button (next to New Folder) that creates a `wassel_doc` row in the current folder and navigates to `/files/doc/:fileId`. The full-page editor (`DocumentEditorPage`) loads the file's body from `public.wassel_documents`, exposes a TipTap-based rich-text surface, and autosaves on a 1.5 s debounce. The doc title is the file's `original_name` and is editable inline in the editor header. Clicking a `wassel_doc` tile in any Files grid opens the editor instead of the preview modal. Folder/permission/sharing/rename/delete plumbing is unchanged — a wassel_doc is a regular file row with `mime_type='application/vnd.wassel.document+json'`, `size_bytes=0`, and a sentinel `storage_path='doc:<file_id>'`. **Amiri is the only allowed font** — the editor's toolbar has no font-family control, every paragraph/heading/list item is forced to `font-family: 'Amiri' !important` via `.wassel-doc-surface`, and the paste handler runs every incoming HTML fragment through `stripFontFamily` to remove `style="font-family: ..."` attrs, `font: ...` shorthand, `<font>` wrappers, and `font-family:` declarations inside `<style>` blocks before TipTap ingests it. Images are inserted as base64 data URIs capped at 2 MB; larger images get a toast pointing users to "upload as a file and link to it".
- **Document lists behave like Google Docs.** Typing `- ` (or `* `) converts to a bullet list; **markers are explicitly restored in `documents.css`** because Tailwind's preflight resets `list-style:none` globally (the "minus sign disappears" bug) — bullets render as a dash glyph (`list-style-type: "–  "`) so they match the `- ` the user typed. Enter continues the list at the same level; Enter on an empty item lifts out one nesting level at a time (eventually exits to a paragraph). Indent/outdent: **Tab** sinks, **Shift-Tab** lifts, and the **Ctrl+] / Ctrl+[** bracket aliases are mapped by *visual direction* (`ListIndentShortcuts` reads the editor's live `dir`): Ctrl+] always moves the item to the RIGHT, Ctrl+[ to the LEFT — in an RTL doc that means Ctrl+] outdents and Ctrl+[ indents; in LTR it's the reverse. The editor carries a base writing direction from the app language (`rtl` for Arabic) so list markers + indentation stay anchored to one side, while each text block still auto-detects its own direction via `unicode-bidi: plaintext` (the `<li>` is deliberately excluded from that rule so the marker doesn't jump sides per item).
- **Page-on-canvas layout (Google-Docs-style).** The editor renders as a defined **page** — a white ~816px-wide (Letter/A4-ish) rectangle with 1in-ish margins and a soft shadow — centered on a warm-gray **canvas** (`.wassel-doc-page` / `.wassel-doc-canvas` in `documents.css`). The editable area fills the whole page via a flex chain, so clicking anywhere on the page lands the caret. This replaces the earlier "white fills everything, text in a floating column" look — the off-page area is now obviously not part of the document. Applies in both normal and fullscreen views.
- **Fullscreen focus mode.** A Maximize button in the doc header (available to viewers too) flips the editor into a `fixed inset-0 z-[60]` overlay that paints over the app sidebar (which is `position:fixed; z-50`) + header — only the page on its canvas and the doc header remain. **Exit lives in the header** (the Maximize button becomes Minimize), not a floating bottom button. A **hide-header** toggle (`PanelTopClose`) collapses the doc header for a pure page-only view; a small floating control then offers show-header + exit. **Esc** exits, but defers to any open modal (first Esc closes the modal, second exits fullscreen) and resets the hidden-header state. Because the overlay is z-60 (above the z-50 sidebar/modal/toast layer), an `html.doc-fullscreen` class lifts `.modal-overlay` (z-70) and `.wassel-toasts` (z-71) above it so Share/Permissions/Move dialogs and error toasts still reach the user while fullscreen.
- **In-doc Share / Permissions / Move (Google-Docs-style).** The doc header exposes Share, Permissions, and Move (folder location) buttons (edit-gated) that open the **exact same Files-section modals** (`ShareLinkModal`, `PermissionsPanel`, `MoveToFolderModal`) used from the Files grid — so a document can be shared by public link, granted to specific users by role, and relocated into any folder without leaving the editor. After a move, the editor reloads the file row so the Back button targets the new parent folder. Because these reuse the file-level components, a wassel_doc's sharing/location story is identical whether managed from Files or from inside the doc.

## User flows
1. **Upload + organize.** User navigates to `/files`, clicks Upload (or drags files anywhere on the page). Files appear in the current folder. Drag-and-drop overlay covers the full viewport on dragenter; per-file upload tickets stack in the bottom-right.
2. **Internal share via folder.** Owner opens a folder's kebab → Permissions, picks a user, sets role (viewer/editor/owner). The recipient sees the folder under "Shared with me" and can navigate in normally; everything inside inherits the role unless individually overridden.
3. **External share via link.** Owner opens a file → Share. Optionally sets expiry + password + allow_download. Clicks "Create link" — gets a `/share/<token>` URL with a Copy button. Sends to customer.
4. **Customer opens the link.** Customer lands on the brand-heavy share page. If password-protected, they hit a Lock screen with a password input. After unlock (or immediately if no password), they see the file rendered inline — image, PDF iframe, video player, audio player, or a metadata card for downloadable types — with a copper "Download" button (unless `allow_download=false`).
5. **Revoke + audit.** Owner re-opens Share, sees the link's view count and last-viewed timestamp, clicks Revoke. Next attempt at the URL hits the "Link not available" branded page. Every upload/view/download/share/revoke/delete is in `/logs`.
6. **Empty / error states.** Empty folder = an icon, the empty-state copy, and an Upload CTA. "Shared with me" with no grants = the empty-state copy only. Expired or revoked share link = the branded Not-Found card. Anonymous viewer's wrong password = inline red text under the input.

## Data touched
- **Reads + writes:**
  - `folders` — folder tree (`parent_folder_id` self-reference; ON DELETE RESTRICT for safety).
  - `files` — metadata for every uploaded artifact. Bytes live in Supabase Storage; this row is the source of truth for permissions and listing. Includes optional `model_id` + `record_id` for record-attachment.
  - `file_permissions` — per-file grants (override the cascade).
  - `folder_permissions` — per-folder grants (cascade to descendants).
  - `shared_links` — public token-based links; bcrypt password_hash; expiry; view_count.
  - `activity_log` — all file events under `category='file'`. Existing CHECK constraint was extended to include `'file'`.
- **Storage:**
  - Bucket `wassel-files` (private, 500 MB cap, MIME allowlist). Path schema `<auth.uid()>/<file_id>.<safe_ext>`. Four storage RLS policies gate by path prefix.
- **RLS helpers (new):**
  - `wassell_folder_cascade_role(folder_id, user_id)` — recursive CTE up the parent chain; returns the highest role grant found.
  - `wassell_can_access_folder(folder_id, kind)` — admin OR creator OR cascade-role satisfies kind.
  - `wassell_can_access_file(file_id, kind)` — admin OR uploader OR direct file_permission OR folder-cascade.
- **Anon RPCs (new):**
  - `get_shared_file(token, password?)` — SECURITY DEFINER; returns metadata if active+not-expired+password-matches; returns `requires_password=true` if password needed; returns no rows otherwise.
  - `record_shared_link_view(token)` — bumps `view_count`, sets `last_viewed_at`, inserts an activity_log row.
  - `set_shared_link_password(link_id, pw)` — service-role-only helper used by `/api/share-links/create` to hash via pgcrypto.

## Images promoted from Image Chats (added 2026-06-08)

Image Chats v2 can copy a generated image into the Files System. When the user picks **Add to Files** on a chat image, `POST /api/image-chat/promote-asset` fetches the image's public `marketing-assets` bytes server-side and uploads them into `wassel-files` under the caller's `auth.uid()` prefix, then inserts a `files` row in the chosen folder (`kind='image'`, `uploaded_by_user_id` = the app user id resolved from `auth_uid`, mirroring `share-links/create.ts`). The chat's original object is never touched — this is a copy, not a move, so the chat history stays intact.

The same endpoint backs **Add to Record**: the new `files.id` is cached back onto the chat message (`MessageImage.file_id`, server-side, first-promote-wins) so a subsequent Add-to-Record reuses the SAME `files` row — one asset, one storage object, many record references (true dedup). Record `image` / `multi_image` / `file` / `multi_file` / `attachment` fields already store `files.id`, so a promoted asset renders through the normal signed-URL path with no special-casing. See [image-chats.md](image-chats.md) "Generation history becomes assets".

A future `media_assets` + `file_placements` model (documented in image-chats.md) would let one asset live in many folders/records with zero byte copies; until then each Add-to-Files is an independent folder copy (single `folder_id` per file).

## Office document preview (added 2026-06-11)

DOC/DOCX/PPT/PPTX/XLS/XLSX render inline instead of falling to the download-only card. **Architecture decision:** conversion is self-hosted — headless LibreOffice on the existing Fly worker — because the alternative (Microsoft/Google embed viewers) requires giving an external service a fetchable URL of the file. Contracts and price sheets never leave Wassel infrastructure.

**Flow:** opening an office file in `FilePreviewModal` calls `POST /api/files/office-preview`. If the cached preview exists (`files.preview_status='ready'`), the endpoint signs the PDF artifact and the modal renders it through the normal PDF iframe path. Otherwise the endpoint enqueues a `file_preview_jobs` row via the atomic `file_preview_enqueue` RPC (one active job per file, enforced by a partial unique index), pings the worker's `/wake`, and the modal polls every 2.5 s showing "Preparing preview…" (timeout 150 s → failed card). The worker (`runPreviewJob.ts`, third independent poll loop) downloads the original, runs `soffice --headless --convert-to pdf` in an isolated profile (concurrent-safe), uploads the artifact to `<uploader_auth_uid>/<file_id>.preview.pdf` in the same private bucket, and flips the file to ready via `file_preview_complete`. Conversion happens ONCE per file — bytes are immutable, so the cache never invalidates.

**Share links:** `/api/share/view` returns a `preview_url` for office files whose conversion is cached, and the public share page renders it inline like a native PDF. Cold-cache anonymous views (and share-link creation) warm the cache fire-and-forget, so the next viewer gets the inline render.

**Guards:** ≤50 MB conversion cap; 240 s soffice timeout that **kills the entire process group** (`spawn detached` + `kill(-pid)` — execFile's built-in timeout only killed the launcher, leaving an orphaned `soffice.bin` that sent a 512 MB machine health-critical on 2026-06-11); `file_preview_watchdog()` sweeps jobs stuck running >10 min (invoked by the worker on its watchdog interval); complete/fail RPCs only touch `status='running'` rows; fail/watchdog never clobber a `ready` file state. Failure UI is a card with the error + Retry (re-enqueues with `p_force=true`) + Download — never a dead spinner. The Docker image installs `libreoffice-writer/-impress/-calc` + Noto-Arabic (apk) and Amiri TTFs fetched from google/fonts (Alpine has NO font-amiri package — first deploy failed on it).

**Live-verified 2026-06-11:** a 729 KB docx converted in 21.8 s (first/cold run) and rendered inline; the failure path verified with a 17 MB image-heavy pptx that exceeded 240 s on the `shared-cpu-1x:512MB` Fly machines — clean timeout, readable error in the failure card, machine stayed healthy. **Known capacity limit:** very large decks can't convert on 512 MB machines; they degrade to the download card. Options if this matters: scale worker memory (billing decision) or accept the degradation.

## PDF compression (added 2026-06-11)

Any PDF in the library can be compressed to a smaller copy — built for the bulk-brochure use case (real-estate brochures are routinely 20–50 MB of print-resolution images). **Architecture decision:** compression is self-hosted — Ghostscript on the existing Fly worker — for the same reason office previews are: file bytes never leave Wassel infrastructure. The iLovePDF REST API was evaluated (the user supplied its docs) and rejected: every file would be uploaded to their servers, and the free tier's 250 files/month cap makes bulk compression a paid dependency.

**Entry points:** "ضغط PDF / Compress PDF" in the FileCard kebab (visible for `kind='pdf'` when the caller has edit role — compressing creates new content in the folder, more than a viewer should do); "Compress PDFs" in the floating bulk-selection bar (enabled when the selection contains ≥1 compressible PDF).

**Flow:** the SPA calls `POST /api/files/compress-pdf {fileId, start:true}` which (after `wassell_can_access_file(edit)`) enqueues a `pdf_compress_jobs` row via the atomic `pdf_compress_enqueue` RPC (one active job per file via partial unique index; concurrent clicks collapse), logs a `compress_start` activity row, and pings the worker `/wake`. The worker (`runCompressJob.ts`, FOURTH independent poll loop) downloads the original, runs `gs -dSAFER -sDEVICE=pdfwrite -dPDFSETTINGS=/ebook -dAutoRotatePages=/None -dDetectDuplicateImages=true` (150 dpi image downsampling — the sweet spot for screen-viewed brochures), and:

- **Win (≥5% smaller):** uploads the result as a NEW object `<source_prefix>/<new_id>.pdf` and INSERTs a NEW `files` row — name `"<base> (مضغوط).pdf"`, same `folder_id` / `model_id` / `record_id` / `uploaded_by_user_id` as the source. **Originals are never replaced** — file bytes are immutable in this system (the office-preview cache depends on that invariant), and a bad compression must never destroy a source document.
- **No gain (<5% smaller):** completes the job with `result_file_id=NULL`; no copy is created. The UI toasts "already well-optimized".

The SPA polls the same endpoint (no `start`) until the latest job reads `done`/`failed`. Bulk selection enqueues EVERY target up-front (jobs finish server-side across the 5 worker machines even if the tab closes), then watches all of them with ONE sequential round-robin sweep (bounded request rate regardless of selection size, 15-min watch ceiling → "still compressing in the background" toast). Outcome toasts: per-file `from → to` sizes, or a bulk summary `ok/total + total bytes saved`.

**Guards:** PDFs only (`application/pdf`); ≤150 MB input cap; 540 s gs timeout that kills the whole process group (same pattern as soffice); `pdf_compress_watchdog()` sweeps jobs stuck running >15 min (always above the job ceiling); complete/fail RPCs only touch `status='running'` rows; a failed `files` INSERT removes the just-uploaded object (no orphans). Password-protected PDFs fail with gs's password error surfaced in the toast. Known edge: a grantee whose access comes from a DIRECT file grant (not folder cascade) won't see the copy — it's owned by the source uploader in the source folder.

**Capacity reality (measured live 2026-06-11):** gs needs ~95 s of CPU for a 19 MB brochure. Fly `shared-cpu-1x` machines run that in ~2m50s when their burst credits are fresh but throttle to 1/16 vCPU once drained (>9 min → timeout — the first two test runs both landed on the same drained machine while four fresh ones sat idle). Mitigation shipped: a timed-out job is REQUEUED (`pdf_compress_requeue`, ≤3 attempts) so a different machine claims it, and the throttled machine sits out two poll intervals so it doesn't re-claim its own requeue. Sustained heavy bulk (dozens of big brochures back-to-back) will still drain the whole fleet's credits and slow down — that's a machine-scaling (billing) decision, same posture as the office-preview limit.

## Open questions / known limitations
- **Storage orphans on browser crash.** If the user's tab dies between storage upload and DB insert, the storage object is orphaned. Future cron (not in v1): `SELECT name FROM storage.objects WHERE bucket_id='wassel-files' AND NOT EXISTS (SELECT 1 FROM files WHERE storage_path = name AND created_at < now() - interval '1 day')`.
- **`allow_download=false` is casual.** A determined viewer can scrape the inline-preview signed URL. Document as not-confidential; for confidential files use a password and a short expiry.
- **Folder share links not supported in v1.** Only files can have public `/share/:token` URLs. Folder cascade is internal-only.
- **No drag-to-reorder, no versioning, no comment threads.** Out of scope for v1.
- **Effective-role detection in the SPA is now role-accurate** (as of 2026-06-10). The grid batch-resolves the caller's real role per item via `wassell_effective_file_roles` / `wassell_effective_folder_roles`, so cascade/direct grantees get the right Edit/Delete/Share affordances. It still falls back to `uploaded_by_user_id === currentUserId` for the brief window before the role RPC resolves (so owners never lose their own buttons mid-load). RLS remains the authoritative gate.
- **Upload progress UI is per-ticket boolean** (queued/uploading/done/error). Supabase JS doesn't expose progress events for sub-6 MB files in v2; for larger files the tus path inside the JS client provides progress that we don't surface yet.
- **Recursive CTE per permission check** — the cascade helper walks the folder chain on every access check. Fine for typical libraries (≤10k folders/user) but worth re-measuring at scale.
- **`record_id` is a soft pointer.** UI handles "linked record not found" gracefully but doesn't auto-clean files when the linked record is deleted (intentional — the file lives on its own).
