## What it is (in plain English)
All of the app's data — models, records, workflows, dashboards, users, settings — is stored in a Supabase PostgreSQL database, with the flexible parts (schemas, record data, widget configs) held as JSONB. Every save of the **small / chrome data** (models, workflows, dashboards, views, profiles, UI settings) is **mirrored to the browser's localStorage first** so the user sees an instant response, and then synced to Supabase in the background. **Records are the exception:** as of 2026-06-08 they are NOT cached in localStorage (the records mirror blew the browser's storage quota on large datasets — see the dated note above) and load exclusively from Supabase. If Supabase isn't configured at all, the app still runs offline against localStorage for everything **except records**, which simply show empty when the backend is unreachable.

## Why it exists
Real-estate offices in Saudi Arabia sometimes have spotty connectivity. We don't want a hang during save. The localStorage-first approach gives instant feedback, and the JSONB-in-Postgres approach lets us ship schema changes (new field types, new workflow actions) without a DB migration.

## Key behaviors
- **6 Supabase tables:** `models`, `model_groups`, `records`, `workflows`, `dashboards`, `model_views`.
- **JSONB columns** hold the variable parts:
  - `models.schema` — the full sections/fields/options tree. `ModelField.is_multi` (optional bool) toggles a `lookup` field into multi-select mode. `ModelSection.is_mirrored` + `mirror_via_lookup_field_id` + `mirror_source_section_id` mark a section as mirrored from another model (local `fields` stays empty).
  - `models.card_config` — card view layout
  - `records.data` — field-slug → value map. Single-select lookup stores a `string` (record id); multi-select lookup (`is_multi: true`) stores a `string[]`. A `range` field stores a structured `{ min?: number; max?: number }` with **numeric** values — this is true whether the field renders as free number inputs or (when it carries an options list, new 2026-06-17) as two bracket dropdowns, because the dropdown option `value`s are numeric strings that resolve back to numbers before storage. So the `v_*` views (`<name>_min` / `<name>_max` columns), analytics, and PDF/Excel are unaffected by the dropdown variant. Mirror fields and mirrored sections store **nothing** — values are derived at render time by `mirrorResolver` / `sectionMirrorResolver`. `section_mirror` fields store a `Record<childSlug, value>` of **local overrides** only — any child value whose sync-back is on bypasses this map and flows into the linked record via the standard mirrored-section fan-out on save.
  - `workflows.definition` — trigger + conditions + actions
  - `dashboards.widgets` — widget configs + layout
  - `model_views.field_ids` / `model_views.conditions` — per-user saved table view (columns + filters)
- **Save path:**
  1. Update Zustand store in memory (UI re-renders).
  2. Write to localStorage synchronously (instant persistence) — **for everything except records**. Record saves skip the localStorage mirror entirely (retired 2026-06-08, quota fix); `saveLocalRecordsForModel` now only sweeps any stale bucket for the model. The in-memory Zustand update in step 1 still gives the instant UI response, and the `record_save` RPC in step 3 is the durable write.
  3. Sync to Supabase via the `record_save` RPC (unfrozen models) or the dispatcher RPC (frozen models). Failures are surfaced via toast AND persisted to a `wassell_pending_sync` retry queue; the queue is drained on every `initialize()` before any reads, with a per-write attempt cap (`MAX_REPLAY_ATTEMPTS = 5`) that drops with a loud toast + `console.error` after exhaustion.
- **Optimistic concurrency on records (Phase F.2, added 2026-05-07):** the `records` table grew a `version int NOT NULL DEFAULT 1` column with a `BEFORE UPDATE` trigger that auto-bumps on every UPDATE. The 5-arg `record_save(p_model_id, p_id, p_data, p_created_by, p_expected_version)` RPC compares `p_expected_version` against the current row; on mismatch it raises SQLSTATE `40001` (`serialization_failure`) with message `version_mismatch: …`. Frontend `supabaseRecordUpsert` passes the `record.version` we LOADED with as `p_expected_version`; on conflict the toast reads "Another user just edited this record. Reload to see their changes before re-saving." and the write is **not** enqueued (replay would just hit the same conflict). New records and pre-F.2 loaded records pass `null` — the RPC treats null as "skip the check" so backward compat holds. Frozen models intentionally don't have version columns yet (Phase F.2.1 — future). **(2026-06-02 hotfix — local version advance + conflict circuit breaker):** the trigger bumps `version` by +1 on every UPDATE but `record_save` returns only the id, so `saveRecord` used to leave the **local** copy pinned at the pre-save version — meaning the SECOND save of the same record in one continuous session sent a stale `expected_version` and was rejected, with the client relying on the Realtime echo to learn the new version. Under load Realtime drops, the local version freezes, and a flow that auto-saves the same record (the Data Migration wizard) wedges into a permanent `version_mismatch` loop that pinned Postgres CPU. Fix: on a successful unfrozen save `saveRecord` advances the local `version` itself (+1, guarded so it never fights a concurrent Realtime merge), so a single client never self-conflicts; and a **circuit breaker** in `supabaseRecordUpsert` stops issuing `record_save` for a record after `RECORD_CONFLICT_LIMIT` (4) conflicts within 10s, firing one loud reload toast instead of spinning — clears on any successful save or page reload. Forms are unaffected (they pass an explicit mount-snapshot version).
- **Atomic auto-ID assignment (Phase F.1, added 2026-05-07):** auto-incrementing identifiers (the `auto_id` field type) used to live as a JSONB counter on the field definition with a documented client-side read-modify-write race. The new `auto_id_counters(model_id, field_id, scope_key, current_value)` table + `record_assign_auto_id(p_model_id, p_field_id, p_scope_key, p_start)` SECURITY DEFINER RPC use `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` so concurrent saves get strictly increasing distinct values. Backfilled from existing JSONB counters at migration time. Frontend `assignAutoIdsAsync()` calls the RPC; falls back to the legacy sync `assignAutoIds()` for offline mode and for the renumber tool. `saveRecord` is now async and awaits it.
- **Mirrored-section write-back:** when saving a record that contains mirrored sections, `RecordFormPage` first calls `saveRecord` on each linked target record (merging pending mirror edits into its `data`) **before** saving the current record. This fans one user action out to multiple records — always in the same Save click, never piecemeal.
- **Load path (Phase D.1 + D.2, refactored 2026-05-07):**
  1. **Drain the pending-writes queue first.** `replayPendingWrites()` runs before any Supabase read so unsynced edits from the previous session land before fresh reads can clobber localStorage.
  2. **Parallel kickoff.** All ~16 `supabaseLoad` calls are fired up-front via `Promise.all`-style independent promises — they run concurrently across the network instead of sequentially. Boot drops from ~10s to ~5s on the production network. The FK ordering for **backfill upserts** (groups before models, profiles before users) is preserved by the awaits later in the function — only the reads are parallelized.
  3. **Chrome-first.** A new `criticalDataReady: boolean` store flag flips true after the chrome-critical tier lands (models, groups, profiles, roles, users, views, dashboards, workflows, workflow_groups, field_templates, webhook_slugs). Records, workflow_runs, activity_log, whiteboards, whiteboard_folders are deferred to the **slow tail** that runs after the chrome renders. `App.tsx`'s `RequireAuth` gate composes the two so the sidebar + Builder + Settings render before records finish loading.
  4. If Supabase is not configured OR a fetch fails, fall back to localStorage — **except records**, which have no localStorage fallback anymore (`loadLocalRecordsMap` returns `{}` since the records mirror was retired 2026-06-08). An offline or failed load shows no records rather than a stale cache.
  5. If neither has data, seed from `src/data/seedModels.ts` and `src/data/seedUsers.ts`.
  6. Run pending schema migrations (`src/lib/schemaMigrations.ts`) to reshape stored data when the schema evolves.
  7. Run an idempotent heal pass that re-attaches orphaned project system models to the Projects group and re-seeds the group if it was deleted. This runs on every load (not gated by schema version), because a user can orphan models by deleting the Projects group in the Builder.
  8. **Run `refreshSystemModels` on every load.** Inserts any system model from `SEED_MODELS` that isn't already in the user's store (so new default models added in code reach existing installs). Does NOT overwrite system models that already exist — **Builder edits to system models are authoritative and persist across reloads and deploys**, exactly like custom models. To propagate a structural change to a system model that already exists in an install, add a versioned migration in `schemaMigrations.ts` (the `migration_N_to_M` pattern). Non-system models are untouched.
  9. **Start the realtime orchestrator + stale-while-revalidate listeners** once `criticalDataReady = true`. See "Realtime + stale-while-revalidate" below.
- **Stable group IDs for system groups:** the Projects group uses a hardcoded UUID (`PROJECTS_GROUP_ID` in `seedModels.ts`). Re-seeding the group always produces the same id, so stored models' `group_id` references survive a wipe-and-reseed.
- **Supabase configured via env:** `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`. If missing, the client is a no-op shim.
- **All IDs** are UUIDs (via `uuid` package).
- **Dates** are stored as ISO strings.
- **Field slugs** (the `name` prop) are snake_case.
- **Server-side validation IS now enforced via Postgres RLS.** See `access-control.md` for the policy posture (records: per-row `wassell_can_*_record` helpers; activity_log: actor-scoped; admin-write/authenticated-read for marketing/settings tables; webhook tables: SELECT-only for users, INSERT via service_role from `/api/webhook/*`). The client is no longer the trust boundary — non-admin sessions get exactly the rows their profile allows even when querying Supabase directly.

### Records-table query indexes (Phase A.3, added 2026-05-07)
- `idx_records_model_id_created_at` — composite `(model_id, created_at DESC, id)`. Powers cursor pagination via `record_search` with no Sort node.
- `idx_records_updated_at` — single-column `(updated_at DESC)`. Powers stale-while-revalidate refetch on focus/reconnect.
- `idx_records_data_gin` — GIN over `data` with `jsonb_path_ops`. Powers field-level filters (`data @> '{...}'::jsonb`) with O(log N) lookup.

### Server-side cursor pagination (Phase E.1 + E.2, added 2026-05-07)
- **`record_search(p_model_id, p_filters, p_cursor, p_limit, p_search_text)`** RPC. SECURITY INVOKER (RLS applies). Returns up to N rows + `has_more`, ordered `created_at DESC, id DESC` with keyset cursor. Reads through the `unified_records` view so it covers both unfrozen and frozen models. Limit clamped to `[1, 500]`.
- **Paginated cache slice in the store.** `recordsByModel: PaginatedRecordsByModel` (one cache entry per model: `rows`, `nextCursor`, `hasMore`, `loading`, `error`, `filterKey`) backed by pure reducers in `src/lib/recordsCache.ts` (`appendPage`, `upsertRow`, `removeRow`, `setLoading`, `setError`, `buildFilterKey`). The async `loadRecordsPage(modelId, opts)` action calls the RPC and feeds the cache.
- **The legacy `records[modelId]` slice is retained.** `RecordListPage`, `TableView`, and the dashboards still consume the old in-memory slice; migrating them to the paginated cache is **intentionally deferred** (Phase E.3 — future). The orchestrator's `mergeRecord` continues to update the legacy slice.

### Realtime + stale-while-revalidate (Phases C.1 + C.2 + C.3 + D.3, added 2026-05-07)
- **Publication membership.** The `supabase_realtime` publication now includes 14 tables: the original `chat_messages`, `call_logs`, `webhook_payloads` PLUS `records`, `models`, `model_groups`, `workflows`, `workflow_groups`, `workflow_runs`, `dashboards`, `model_views`, `profiles`, `roles`, `users`. Multi-user changes propagate live to every open browser session without a refresh.
- **Replica identity policy.** Small low-write tables (`models`, `model_groups`, `workflows`, `workflow_groups`, `dashboards`, `model_views`, `profiles`, `roles`, `users` plus the original `chat_messages`, `call_logs`) get `REPLICA IDENTITY FULL` — payloads carry the whole row. High-volume tables (`records`, `workflow_runs`) stay at `REPLICA IDENTITY DEFAULT` (PK only) so WAL volume stays bounded — merge handlers refetch the full row by id when the payload only carries the PK.
- **`RealtimeOrchestrator`** (`src/lib/realtime/RealtimeOrchestrator.ts`). One `postgres_changes` channel per table (11 channels). Started after `criticalDataReady = true` in `appStore.initialize()`. Module-scoped singleton on `globalThis.__wasselRealtimeOrch` defends against HMR / strict-mode double-renders.
- **Echo dedup** (`src/lib/realtime/dedup.ts`). Every successful Supabase write registers `<table>:<id>` with a 30s TTL. The orchestrator checks `wasRecentlyWritten()` before applying — payloads originating from this client's own writes are skipped, so optimistic React updates don't double-render.
- **Stale dedup.** Per-table merge handlers in `src/lib/realtime/mergeHandlers.ts` compare the local row's `updated_at` to incoming and skip if local is at-least-as-fresh — defends against out-of-order delivery.
- **Stale-while-revalidate** (`src/lib/realtime/staleWhileRevalidate.ts`). On `window.focus` and `window.online`, refetch each table's rows changed since the last load (`updated_at > lastLoadTs[table]`) capped at a per-table limit, throttled to one sweep per 5 seconds. Reuses the same merge handlers as the orchestrator, so dedup + idempotence + store mutations are identical. `markLoaded(table, iso)` watermarks per table; `initialize()` watermarks all relevant tables before the parallel kickoff so any updates during the load window are picked up by the next sweep.
- **Kill switches.** `localStorage.wassell_realtime_disabled = '1'` skips orchestrator startup entirely. `VITE_REALTIME_<TABLE>=off` (env var, e.g. `VITE_REALTIME_RECORDS=off`) disables a single table's channel.
- **Telemetry globals.** `__wasselRealtimeStats()` returns per-table counters (`received`, `applied`, `echo_skipped`, `stale_skipped`, `errors`). `__wasselSwrStats()` returns the last-sweep summary (`tables_checked`, `rows_applied`, `errors`, `throttled`, `duration_ms`). `__wasselSwrLastLoadTs()` returns the per-table watermarks. `__wasselSwrRefresh()` triggers a manual sweep. All callable from the browser console for ad-hoc diagnosis.
- **Frozen models are NOT covered yet.** Realtime payloads from dedicated frozen tables go to those tables' channels, not `records`. Phase E.4 (future) will add a frozen-model fast path; until then, frozen models are read-snapshot-only — the user must reload to see another browser's edits.

### Performance telemetry (Phases G.1 + G.2, added 2026-05-07)
- **`installPerfMarkers()`** (`src/lib/perfMarkers.ts`) — installs the `__wasselPerf()` browser-console global which returns `{ now_ms, measures, realtime, swr, swr_lastLoadTs }`. Marks placed across `initialize()`: `wassell:init:start`, `wassell:init:loads:start` / `:end`, `wassell:init:critical-ready`, `wassell:init:end`, with `performance.measure('wassell:init:critical', ...)` and `wassell:init:total` measurements.
- **Database-side slow-query log.** `slow_query_log(p_threshold_ms, p_limit)` and `snapshot_slow_queries(p_threshold_ms)` admin-only SECURITY DEFINER wrappers around `pg_stat_statements`. `query_perf_snapshot` table captures periodic snapshots. Lives in `2026-05-07_g1_perf_telemetry.sql`.

### Frozen models (added 2026-05-05)
- **Two storage shapes** coexist in the database. Unfrozen models still live as JSONB rows in the unified `records` table. **Frozen models** live in their own physical table `<model.name>` with proper typed columns, plus per-multi-value-field junction or subtables `<model>__<field>`.
- The `models.is_hardcoded` boolean (default `false`) tells you which shape a given model uses; `models.table_name` holds the physical table name when frozen (equals `model.name` for everything frozen through the standard pipeline).
- **Reads always go through the `unified_records` view** — a `UNION ALL` of `records` (for unfrozen models) and each frozen model's `<name>_v` JSONB-shape view. Same row shape (`id, model_id, data, created_by_user_id, created_at, updated_at`), so consumers don't need to branch.
- **Writes go through SQL RPCs:** `record_save(p_model_id, p_id, p_data, p_created_by, p_expected_version)` upserts; `record_delete(p_model_id, p_id)` deletes. Both dispatch internally on `is_hardcoded` — frozen models hit their dedicated table via `freeze_apply_row` (which splits the JSONB payload into parent UPDATE + junction/subtable replace), unfrozen models hit `records` directly. The frontend store wraps these in `supabaseRecordUpsert` / `supabaseRecordDelete` (replacing the old direct `supabaseUpsert('records', ...)` calls in `saveRecord` / `deleteRecord`). `p_created_by` is COALESCE-preserved on update — first save stamps, edits don't overwrite — same posture as the records-table flow. `p_expected_version` is the optimistic-concurrency hook (Phase F.2): on unfrozen writes the frontend passes the loaded `record.version`; the RPC raises `serialization_failure` (SQLSTATE 40001, message `version_mismatch: …`) on mismatch. Frozen models ignore `p_expected_version` for now (Phase F.2.1 — future). The previous 4-arg signature was dropped to avoid overload ambiguity; the new 5-arg one is fully backward-compatible because `p_expected_version` defaults to NULL.
- **RLS on frozen tables (added 2026-05-06):** frozen tables enable RLS and get four policies generated by `regenerate_frozen_model_artifacts`. They reuse the same `wassell_user_has_action` model-perm helper as the records-table policies, plus two new helpers `wassell_can_view_jsonb` / `wassell_can_edit_jsonb` that build a synthetic `records` row literal from the frozen-table columns and delegate to the existing `wassell_record_passes_scope` evaluator. Per-profile view_scope and edit_scope rules referencing scalar fields keep working after a model is frozen. Multi-value fields (multiselect, multi-lookup, table) are intentionally NOT included in the synthetic JSONB — junction joins inside an RLS expression evaluate per-row and would tank reads. Scope conditions on multi-value fields fail closed on frozen tables; this is a known v1 limitation. Junction tables get their own `frozen_junction_view` / `frozen_junction_write` policies that gate via `EXISTS (SELECT 1 FROM <parent> WHERE id = record_id)`, so reaching into a junction inherits the parent's RLS verdict.
- **Field-type → physical mapping** (used by both `freeze_model` for DDL and `freeze_apply_row` for writes):
  - `text` / `textarea` / `email` / `phone` / `url` / `dropdown` / `auto_id` / `lookup` (single) → `text` column
  - `number` / `currency` / `formula` → `numeric`
  - `date` / `datetime` → `timestamptz`
  - `checkbox` → `boolean`
  - `range` → expanded into `<name>_min`, `<name>_max` numeric columns
  - `notes` / `section_mirror` / `section_selector` / `assignee` → `jsonb` (kept structured)
  - `multiselect` → junction `<model>__<field>` with `(record_id uuid, value text, PK)`
  - `lookup is_multi=true` → junction `<model>__<field>` with `(record_id uuid, target_record_id uuid, PK)`
  - `table` → subtable `<model>__<field>` with `(id, record_id, row_index, ...row columns)`
  - `mirror` → SKIPPED (computed at runtime from sibling lookup; no physical column)
  - `whatsapp_history` → SKIPPED (virtual — derived from `chat_messages` at render via `selectClientChatMessages`; no physical column)
  - `call_history` → SKIPPED (virtual — derived from `call_logs` at render via `CallHistoryPanel`; no physical column)
- **Coercion failures abort the freeze.** `freeze_check_coercion(model_id)` returns the rows that can't coerce (e.g. a "number" field with junk text); the freeze SQL function aborts with a descriptive error if any are present. The Builder modal previews these failures BEFORE the user confirms so they can clean up records first. We never silently NULL data on freeze.
- **Auto-IDs on frozen tables** switch from the JSONB `auto_id_counters` map (which had a documented race condition) to a Postgres `SEQUENCE` per (model, auto_id field), seeded at freeze time above the high-water mark of any existing IDs. Same display format (`CLT-001`); no more race.
- **Records-table guard.** A `BEFORE INSERT OR UPDATE` trigger on `records` raises a loud exception if anyone tries to write to it for a frozen model. The dispatcher RPCs route correctly; this is a safety net for forgotten direct `.from('records').upsert()` calls in legacy code paths so they fail loudly instead of silently writing to a table the app no longer reads.
- **Server-side reads** in `api/` and `supabase/functions/` use `unified_records`. Writes use the `record_save` RPC. Writes to `chats` records (always unfrozen — excluded from Freeze) keep using `.from('records')` directly since the trigger only fires for frozen models.
- **Builder UI for frozen models is read-only.** The "Freeze" button is replaced with a "Frozen · `<name>`" pill plus a banner explaining schema edits go through Claude. The Fields/Card/Maps/Buttons tabs all accept a `readOnly` prop that blocks pointer events. The Builder Agent's schema-mutating tools refuse on frozen models with a message pointing the user at a regular Claude Code chat for migrations.
- **Future schema edits** (adding/dropping a column, adding a new junction) happen via a migration written by Claude that does the DDL AND updates the model's JSONB schema in `models.schema`, then calls `regenerate_frozen_model_artifacts(model_id)` + `rebuild_unified_records()` to refresh the view + UNION.

### Data Migration support (added 2026-06-01)

Backing the [data-migration.md](data-migration.md) wizard:
- **`wassel-migrations` Storage bucket** — private, 32 MB/file, owner-scoped RLS (`<auth.uid()>/...` path prefix). Holds developer files uploaded for AI extraction. The extract endpoint reads them via short-lived signed URLs the client mints (no service-role).
- **`records_bulk_save(model_id, rows jsonb, created_by)` RPC** — inserts many records in one round-trip by looping `record_save` per row in its own subtransaction (frozen/unfrozen dispatch for free), returning `{inserted, errors[]}`. Workflows are intentionally NOT fired for bulk import. Built + DB-verified; reserved as a future fast-path (the live wizard currently imports via `saveRecord` per row).
- **`record_reserve_auto_ids(model_id, field_id, scope_key, count, start)` RPC** — atomically reserves a contiguous block of auto-IDs (reuses `auto_id_counters`), for batch import without the per-row race.

### DB-maintained derived fields (Postgres triggers)

Some fields on certain models are **not written by the app at all** — they're recomputed by SECURITY DEFINER Postgres triggers on `records`, so the database is the single source of truth and a user edit (or a client-side strip) can never wipe them. They are the data-layer alternative to a workflow `update_record` action and run for **every** write path (UI, client-side workflows, the on-due sweeper, direct SQL / importers). All of these fields are marked `read_only` in their model schema.

- **all_projects unit rollups (added 2026-06-15).** The eleven aggregate fields on `all_projects` (`unit_count`, `available_units` / `sold_units` / `reserved_units`, the four ranges, the three per-m² averages) are recomputed from the project's linked units by a BEFORE INSERT/UPDATE trigger on the project rows, plus an AFTER trigger on the units rows that "touches" the linked project(s) (handling the unit-moved-between-projects case by touching both old and new project). Both are SECURITY DEFINER so they count all units / bypass project RLS. Migration: `supabase/migrations/2026-06-15_persist_project_rollups.sql`.
- **clients next-action trio (added 2026-06-17).** `clients.next_followup_id` / `next_action_type` / `next_action_due_at` are recomputed by a SECURITY DEFINER trigger pair (the same pattern) from the client's **earliest OPEN follow-up** (`followup_status` ∈ {open, in_progress}) on every write to a client OR a follow-up. `next_action_type` is mapped from the follow-up's type (whatsapp / offer / financing / ownership / else→call). Self-healing on complete / reschedule / delete / move. These fields existed since the Sales OS Phase 1 work but had no writer (all clients were empty) until this trigger filled them. Migration: `supabase/migrations/2026-06-17_client_next_action.sql`. See [clients.md](clients.md) and [sales-process.md](sales-process.md).

Both `all_projects` / `units` and `clients` / `followups` are **unfrozen** (JSONB in `records`) — the triggers key off `records`. If any of these models is ever frozen, the trigger logic must move to the frozen table's write path.

## User flows
1. **First-run offline:** User opens app with no Supabase env → app seeds from `seedModels.ts` → all data lives in localStorage → fully functional.
2. **First-run online:** User opens app with Supabase configured → parallel kickoff fires every read concurrently → chrome-critical tier renders the sidebar / Builder / Settings as soon as it lands → records / workflow_runs / activity_log / whiteboards finish in the background. The realtime orchestrator + SWR listeners start once chrome is ready.
3. **Normal save:** User clicks Save → UI updates instantly → `record_save` RPC resolves with version-check passing → realtime echoes the change to other browsers. Echo dedup skips re-rendering the row this client just saved.
4. **Concurrent edit conflict:** User A and User B both load the same record (version 5) → User A saves first (bumps to 6) → User B saves with `p_expected_version=5` → RPC raises `version_mismatch` → toast tells User B to reload → reload pulls version 6 → re-saves cleanly.
5. **Offline edit:** User loses connection → save succeeds locally and is enqueued in `wassell_pending_sync` → next `initialize()` (page reload, or realtime reconnect refresh) drains the queue before any read. Writes that fail 5 times in a row are dropped with a loud toast + `console.error`.
6. **Tab returns from background:** User backgrounds the tab for hours → realtime channel was paused → on focus, the SWR listener fires (subject to 5s throttle) → each table refetches `updated_at > lastLoadTs[table]` → merge handlers apply deltas without a full reload.

## Open questions / known limitations
- **`record_search` consumer migration deferred (Phase E.3):** the new paginated cache exists in the store but the major UI consumers (`RecordListPage`, `TableView`, dashboards) still read from the legacy `records[modelId]` slice. They benefit from the new indexes, RLS, and realtime, but they don't yet use cursor pagination — large models (~10K+ rows) still load fully into memory at boot. Migration is intentional follow-up work.
- **Frozen models lack realtime + version columns.** The orchestrator covers `records` but not the dedicated frozen tables. Frozen-model rows are read-snapshot-only — the user must reload to see another browser's edits. Optimistic concurrency (`p_expected_version`) is silently skipped for frozen models. Phase E.4 / F.2.1 (future) extend the regenerator to add per-frozen-table version columns + realtime channels.
- **Scope conditions on multi-value fields fail closed on frozen tables** (carried over from the 2026-05-06 entry). Multiselect / multi-lookup / table fields aren't included in the synthetic JSONB the frozen-table RLS policies build, by design (would force per-row joins). Document this when freezing a model whose profile rules touch a multi-value field.
- **Field-level audit log** — there's no per-record edit history (who changed which field on which record). The unified activity log captures CRUD events with diffs but not field-level versioning. Acceptable at the current scale; revisit when external auditors require it.
- **JSONB size** — very large models or records could exceed practical JSONB limits; no guardrails.
- **`auto_id_counters` is admin-read-only.** Only the SECURITY DEFINER RPC writes; admins can read for diagnostics. Restarting a counter from the Builder still works because the Restart modal calls a different code path that updates the model schema and (for new records going forward) the RPC's `p_start` argument.
- **Auto-ID self-heal (2026-06-01).** `record_assign_auto_id` never returns a value at or below the highest numeric id already present in `unified_records` for a global-scope field, so a drifted counter can't re-issue an in-use id even though import / duplicate / pre-filled saves bypass the RPC entirely. Cost is one extra `MAX()` over the model's rows per record-create (negligible). **Scoped auto-IDs (`auto_id_scope_field_id` set) are NOT self-healed** — re-deriving each row's scope key in SQL would mean duplicating the client-side slugify; there are no scoped auto-ID fields today, so revisit this if one is ever added. Pre-existing collisions were repaired one-time by `2026-06-01_auto_id_dedupe_and_realign.sql`.
- **`B.5` Auth leaked-password protection is a Supabase dashboard toggle**, not a code change. Out of scope for the refactor; flagged for the user to enable manually.
