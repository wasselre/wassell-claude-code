# Market Intelligence

**Last updated:** 2026-07-29

## What it is
A brokerage **command center** built on a deterministic benchmark precompute layer over the data Wassel already holds — **46,561 market listings** (Aqar asking ads), **our verified units**, and **client demand**. It answers: where are prices, where is demand strong, where is supply weak, which of our projects are mispriced, and which districts to source inventory from. It also powers **deal-quality badges** inside the Project Finder and generates **branded PDF reports** (client market snapshot + our-project pricing).

**ZERO AI in any number.** Every figure is a precomputed SQL aggregate or a DB-filtered scan. No LLM computes a benchmark, ranking, badge, or conclusion. (The Project Finder's existing bounded parse/explain + `assertRankingUnchanged` guard are untouched; badges are attached *after* ranking and never affect order.)

**Honest by design.** Asking prices are labelled "current asking market", never "market value". Every benchmark carries `raw_count` vs `deduped_count` + `duplicate_ratio` + a `confidence_grade` (high/medium/low). Transaction data is **not connected yet** (`market_listings.sold_at` is empty) — the schema + readers are transaction-ready and show honest empty states.

## Key behaviors
- **Benchmark precompute** (`market_benchmarks`): per **district × canonical property type × bedrooms bucket × source_type**, the median + P10/P25/P75/P90 of price and **price/m²**, median area, sample/dedup counts, and a confidence grade. `source_type` ∈ `asking` (market listings) | `our_verified` (our units) | `transaction` (reserved). Property type is collapsed from 326 noisy Arabic strings to a stable canon (`wassell_canon_property_type`, mirrored in `src/lib/market/propertyType.ts`). Refreshed by `wassell_refresh_market_benchmarks()` (SECURITY DEFINER, counts all rows; ~1,500 segments in ~2s).
- **Dedup (benchmarks)**: a deterministic fingerprint (district|type|price|area|bedrooms|rounded coords) collapses re-listed ads; `duplicate_ratio` lowers confidence. This is the BENCHMARK-side fingerprint and is separate from the record-level `property_key` below — see Limitations.
- **Property identity — one property, many broker ads** (added 2026-07-29): the same physical property is advertised by several agents at once, each ad its own row. Deed `717823000238` (a 750 m² plot in الخير) is four rows, four brokers, asking 975,000–1,100,002. Every listing therefore carries a `property_key` computed in Postgres, and the listings list collapses rows sharing one into a single row showing how many ads it absorbed, with the members (agent + price, lowest flagged) behind a chip.
  - **Key**: `deed_number + floor(area) + coords@4dp` (**tier 2**), else `coords@4dp + floor(area)` (**tier 3**). Deed alone over-collapses — the worst deed spans 228 rows across 30 areas (a compound where every unit shares one land deed); deed+area *without* coordinates still merged 68 listings spread over 3 km. `property_type` is deliberately excluded: measured against deed ground truth it costs 13 points of recall (93%→79%) for 0.6 points of precision, because Aqar labels one plot "سكني", "أرض", "أراضي", "قطعة أرض" interchangeably. Coordinates stay at 4dp (~11 m): 3dp (~111 m) nearly triples the false-merge rate (11.8%→27.9%).
  - **Tier 3 is grouped by default but labelled** — ~88% precise, so the chip is gold not copper and the modal says "probable, not confirmed" and offers a split.
  - **Split**: a user can ungroup via `market_listing_set_split(uuid[], boolean)`, which patches only `property_split`. It must NOT go through the record store — market_listings is a SUMMARY model, so saving from the list would write the slim projection back over the full row.
  - **Nothing is deleted.** The spread across brokers is the product: on the 4,431 multi-listing groups, 2,592 disagree on price by an average of 441,252 ر.س, which tells a rep the real anchor. 2,290 groups are one agent re-posting rather than competing agents.
  - **Live counts (2026-07-29)**: 53,488 listings → **43,798 properties**; 9,690 rows collapsed (7,149 tier 2 + 2,541 tier 3). 2,668 rows carry neither deed nor coordinates and stand alone.
  - **Tier 1** (same REGA `ad_license_number` = the same advertisement syndicated to two portals) is implemented in `market_listing_bridge_property_keys()` but inert on a single source: inside one portal a licence is unique (33,357 distinct across 33,359 rows — every re-advertisement gets a fresh licence), so it only fires once a second source lands.
- **Demand × supply** (`market_demand_supply_benchmarks`): active-client demand (from each open lead's `location.district[]` ∪ `preferred_projects`' districts, × canon `preferred_unit_type`, × budget bucket) crossed with market / our / catalog supply, yielding `undersupply_score`, `sales_priority_score`, `acquisition_priority_score`. **Demand data is thin today** — confidence grades + UI caveats say so.
- **Page** (`/market-intelligence`, admin/manager by default via `CUSTOM_PAGES`): Overview cards + confidence summary; **Benchmarks** (filterable, paginated table → district drawer); **Demand × Supply** table; **Opportunities** (Sales push / Acquisition / Pricing watch / Thin-market queues); **Our Pricing** (our_verified vs asking median, with PDF export). A loud caveat strip sits above every tab.
- **District drawer**: asking market by type, our inventory here, our demand here, best-value listings (≤P25 on a confident benchmark, marked *verify before offering*), and a one-click branded **market snapshot PDF**.
- **Best-value listings**: deterministic — only surfaced when the segment's benchmark is medium/high confidence; price/m² below P25 (or P10 when high confidence); always flagged external + verify.
- **Project Finder deal badges**: each finder card gets a non-ranking `deal` badge — `strong_value` (≤P25, confident, geo-verified, type matches), `fair_market`, `premium_price` (≥P75), `potential_value` (cheap but weak benchmark/geo → verify), `thin_market`, `no_benchmark`, `missing_price`/`missing_area`. Low-confidence benchmarks can never yield "strong value". External/catalog sources keep "verify before offering".
- **Recompute**: admin-only (`/api/market-intelligence` action `recompute`, server-side `wassell_is_admin` check + service-role refresh). The refresh functions are revoked from `public`.
- **Map + arbitrary areas** (added 2026-07-27): a **Map** tab whose surface is analytical, not a listing browser. Districts are shaded by a chosen metric (median ر.س/م² · our units · client demand) using a **quantile** ramp (equal-width bins collapse on Riyadh's right-skewed prices), drawn as ONE `google.maps.Data` layer. Listing pins are deliberately absent — the Market Listings map already answers "where are ads".
- **An "area" is a `LocationItem[]`** — the exact type stored on a client's `location_items`: districts, `within_radius` of a landmark, a bounded band north/south/east/west of a road, `inside_area`, a freehand polygon, plus excludes. Built by reusing `LocationItemsEditor` (and through it `DistrictMapPicker`), or by clicking districts on the map, or by name search. `wassell_market_area_stats(p_items, p_filters)` returns the full statistic set for it: price + price/m² bands (P10/P25/median/P75/P90), median area, dedup counts + confidence, breakdowns by type and bedrooms, districts touched, **our projects/units inside the same area with our median /m² and the gap vs the market**, and client demand.
- **Area membership is resolved by `wassell_geo_match`** — the SAME predicate the Project Finder uses — so an area's numbers describe exactly the ground the Finder searches. It is NOT a second geometry implementation.
- **Area ≠ district benchmark, on purpose.** Benchmarks key off the scraped `location.district` TEXT field; areas key off COORDINATES. ~3.9% of in-scope ads (2,082) carry no coordinates and can never fall inside an area; `wassell_market_geo_coverage()` returns that number and the UI states it. Areas also default to `active_only` (excluding the 12,882 delisted ads), which the district benchmark refresh does **not** — see Limitations.
- **Client's market, two mounts** (same component, same endpoint, same numbers): a client picker in the Map tab (analyst flow — pick a client, the map + panel snap to their saved preferences), and a **"سوق العميل / Their Market"** tab on the client record (rep flow). Both call `client_area`, which reads `location_items` through the caller's RLS, canonicalizes their `preferred_unit_type` (a multiselect of raw labels) to a benchmark segment, and adds the budget-vs-market read.
- **Area study PDF**: branded A4, deterministic — every figure a SQL aggregate, no AI. Carries the methodology note (asking ≠ sold, what "prevailing range" means in plain words, the no-coordinates count, duplicate share, confidence). Accepts an optional `commentary` string rendered in a visually distinct, explicitly-attributed block so a reader can always tell measured from written.

## User flows
1. **Manager opens Market Intelligence** → Overview cards (active listings, districts, demand, confidence split, supply gaps, high-opportunity districts) → Benchmarks tab, filters by city/type/bedrooms/source/confidence → clicks a district → drawer with price bands, our inventory/demand, best-value listings → downloads a branded PDF snapshot.
2. **Acquisition decision** → Opportunities → Acquisition queue (demand, no Wassel supply, market proves supply exists) ranked by priority.
3. **Pricing our project** → Our Pricing tab → our /m² vs market median + P25–P75, position (below/fair/premium), client demand → Export PDF.
4. **Salesperson in a follow-up** → Suggested Projects modal → each card shows a deal-quality badge (e.g. "Strong value −18%") grounded in the district benchmark.

## Data touched
- **Reads:** `records` (market_listings, units, our_projects, all_projects, clients), frozen `public.districts` (names/city), `market_benchmarks`, `market_demand_supply_benchmarks`.
- **Writes:** the two benchmark tables (only via the SECURITY DEFINER refresh functions), plus — for property identity — `records.data.property_key` / `property_tier` (filled by a BEFORE INSERT/UPDATE trigger on every market_listings write) and `property_split` (only via `market_listing_set_split`, only when a user ungroups). No other client/listing/project data is ever mutated. PDFs are generated client-side (jsPDF) — nothing persisted.
- **Also on a market listing, written by other lanes (not by this page):** `image_mirror_map` — our own copy of each Aqar photo in the public `listing-photos` bucket, keyed by source URL, filled at scan time by the `listing-mirror` worker queue so the photo-cleaning lane never fetches from Aqar's CDN (which 403s Fly's egress since 2026-07-24). Sits alongside `video_mp4_map`, `original_image_urls`, and the REGA `advertiser_phone` / `rega_lookup_*` fields. All of these survive the scanner's weekly reconcile ONLY because it updates through `market_listing_merge` (`data = data || jsonb_strip_nulls(patch)`) rather than a whole-column PATCH. See CLAUDE.md "Listing photo mirror".

## Limitations / follow-ups
- **Two dedup mechanisms coexist.** `market_benchmarks` collapses re-listings with its own fingerprint (district|type|price|area|rounded coords) computed at refresh time; the listings list groups on the stored `property_key` (deed-first). They disagree by construction — the benchmark fingerprint includes PRICE, so the same plot at 975,000 and 1,100,002 is two rows to a benchmark and one property to the list. Unifying them means re-running every benchmark, so it is left as a deliberate user decision, exactly like the delisted-ads item below.
- **Deed coverage was decaying and is now frozen at its 2026-07-01 snapshot.** Only the one-off `bulkFetch.mjs` enrichment ever wrote `deed_number` / `ad_license_number` / `scraped_extras` (34,429 rows). The daily push replaced the whole `data` blob, so every row it touched lost them — of the 3,350 rows the 2026-07-26 reconcile updated, exactly ONE still had a deed. Fixed 2026-07-29 by routing the push through `market_listing_merge` (strip-nulls merge), so nothing decays further — but the regular scrape still does not EXTRACT the deed, so listings first seen after 2026-07-01 have none and fall to tier 3. Folding `bulkFetch.mjs`'s parser (plain fetch of the canonical Aqar URL, no browser, ~370 ms/listing) into the detail step would take tier-2 coverage from 62% toward ~92%.
- **Asking-only**: no transaction/sold prices yet. Schema + UI are transaction-ready; connecting a feed (e.g. Paseetah) lights up `asking_transaction_gap_pct` and a transaction source filter automatically.
- **Single snapshot**: `market_listings` is a ~2-day scrape, so no trends/days-on-market yet. `snapshot_date` is stored per refresh so accumulating snapshots over time unlocks trend widgets later.
- **Thin demand data**: few clients have structured prefs today; demand×supply leans on `preferred_projects`. Treated as a signal with explicit confidence/caveats.
- **Refresh cadence**: recompute is admin-triggered (button). pg_cron is disabled on prod; a Fly-worker tick could automate it later (same pattern as the other queues).
- **Finder badge district match** is by district name (+canon type) against the benchmark; within a city this is unambiguous.
- **District benchmarks still count delisted ads.** `wassell_refresh_market_benchmarks` has no `is_active` filter, so the 12,882 ads the Friday reconcile marked delisted are inside every per-district benchmark and inside the "active market listings" overview card. The area statistics added 2026-07-27 exclude them by default (`active_only`). Aligning the two means moving every district benchmark, so it is a deliberate decision left to the user rather than a silent change.
- **AI commentary on area studies is NOT wired yet.** The study PDF renders a `commentary` block when given one, and the deterministic figures are complete without it, but nothing currently produces that text. Wiring it means a `client_study` job whose payload carries a client/area instead of a `chat_record_id` (the existing `claude_jobs.kind` CHECK already allows `client_study`, so no constraint change — see the hard rule about that CHECK in CLAUDE.md) plus a matching branch in `scripts/claude-study-runner.mjs` and the `/client-study` skill.
- **Demand inside an area counts district preferences only.** A client who expressed the same ground as a drawn shape or a road rule is not counted — comparing two compiled geometries per client is a much more expensive question, and counting them loosely would overstate demand.
