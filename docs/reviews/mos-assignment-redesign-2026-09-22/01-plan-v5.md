## 1. Planned handoffs, deadlines, and risk

**CONFIRMED.** Planned deadline = planned handoff + step allowance (writing/design 24 h; reviews 12 h) on the working calendar; not end-of-day; coherent across the chain; targets only. Early availability keeps the planned deadline. A late handoff gives the full allowance from receipt; the original target stays visible; publication risk is separate from employee lateness.

**1a. Planned handoff times — CHOICE (unchanged from v3).** `mos_step_rules.target_hours` (data; seeds writing 4, writing_review 2, design 4, design_writer_review 2, design_review 2; CHECK ≤ `allowance_hours`; `scheduling` and `publish_check` deliberately have NO target — their time is inside `release_lead_hours`, see 1c). `mos_plan_chain(subject_table, subject_id)` returns, per pinned step, the booked day = `COALESCE(planned_start_corrected, planned_start)` of the subject's LIVE reservation (status in reserved/stale/bound/consumed; keyed by `row_id` for rows, `content_id` for content), `plan_handoff_at`, `plan_due_at`:
```
handoff_1  = booked_day_1 00:00 Riyadh
cand_k     = mos_work_due_at(handoff_{k-1}, target_{k-1})
handoff_k  = GREATEST(booked_day_k 00:00, cand_k)
plan_due_k = mos_work_due_at(handoff_k, allowance_k)
```
Worked values (unchanged): first-step writing booked day D → due D+1 00:00; review handed off D 04:00 → due D 16:00; design at D 06:00 → D+1 06:00; writer's check at D 10:00 → D 22:00; final approval at D 12:00 → D+1 00:00; across Friday, a review handed off Thu 20:00 → Sat 08:00. **[v4]** `mos_plan_chain` is the ONLY chain implementation; the deadline stamp, the correction, and the risk function all read it (the risk resolution's separate inline chain was refuted and dropped).

**1b. Enforced deadline — CHOICE (unchanged).** `plan_due_at` (immutable copy) and `due_at = GREATEST(plan_due_at, mos_work_due_at(assigned_at, allowance))` + approved-leave extension. Anchor = assignment moment, every step. Discipline reads `due_at` only. `handoff_slip = assigned_at − plan_handoff_at`, informational.

**1c. Publication risk — [v4] replaced; [v5] three branches.** `mos_publication_risk(subject_table, subject_id)` STABLE, SECURITY DEFINER; returns `(projected_ready_at, required_ready_at, publish_at, risk, risk_step, risk_reason)`.

*Instants (unchanged from v3):* organic `publish_at` = min `mos_publications.planned_at` over non-cancelled members (row subjects expand members via `mos_content.row_id`); `required_ready_at = publish_at − release_lead_hours` (setting, default 2 h: release-sweep latency + scheduling/publish_check + bundle fetch). Paid: activation day `A` = `mos_creative_slots.activate_on` **resolved by `content_id`** (the slot's `ad_row_id` is empty for all 81 live slots — the content link is the live one); `required_ready_at = A 00:00 − ad_build_lead_hours` (default 2 h); `publish_at = A + 1 day` (end of the activation day, `ads_live_when_ready`; no stored hour).

*Branch selection [v5].* Three states, decided in this order. **(A) Not started** — the subject has no task row at all (for a refresh-cycle shell: no task for that content) and at least one live reservation (`reserved`/`stale`). **(B) In production** — the subject has an open task. **(C) Production complete** — no open task AND the subject's latest task (max `round`, then max pinned position) is `done` at the last pinned step that carries a `target_hours` (today `design_review`) or at any later step, with `result IN ('approved','submitted')`, or the path was closed by `finish`. A subject with tasks, no open task and no completion is **stalled**: `risk='at_risk'`, reason `stalled: no open task` — it should never occur, and if it does the flag is loud. "No open task" alone proves nothing: a reservation-only subject has no task and all of its production still ahead.

*Not started (A):* the chain is the whole pinned production path from the first step: `handoff_1 = GREATEST(now, booked_day_1 00:00)`; `handoff_k = GREATEST(finish_{k-1}, booked_day_k 00:00)`; `finish_k = mos_work_due_at(handoff_k, target_k)` for every step with a target (booked days from `mos_plan_chain`; steps without a target skipped as in B); `projected_ready = finish_last`; verdict as in B. The reviewer's case: at 08:00, an unopened five-step chain booked today (4+2+4+2+2 h) projects 22:00 against an 18:00 slot → `late` (v4 read it `on_track`).

*In production (B, subject has an open task):*
1. Current step `c` = the subject's single open task (`uq_workflow_role_tasks_one_open`). Never a scan for "earliest step without a done row" — after a `changes_requested`, later steps keep their round-1 `done` rows and would be skipped (live subject 5d252cc8 under-projects by half).
2. `c.blocked` → `risk='blocked'`, reason = `blocked_reason`, no estimate.
3. `p` = position of `c.step_key` in the pinned steps (`workflow_versions.definition->'metadata'->'steps'`, read off `workflow_role_tasks.workflow_version_id`). Remaining = pinned steps at positions > p, in order, all treated as not yet created for round `c.round`; done rows of any round are ignored.
4. `handoff_c = c.assigned_at` if assigned, else `GREATEST(now, booked_day_c 00:00)`; `expected_finish_c = GREATEST(now, mos_work_due_at(handoff_c, target_c))` (slides with the clock; a step with no target contributes 0). For each remaining step k with a target: `handoff_k = GREATEST(expected_finish_{k-1}, booked_day_k 00:00)`, `finish_k = mos_work_due_at(handoff_k, target_k)`. Booked days from `mos_plan_chain`; a reopened step reuses its step's booked day (reservations carry no round); a past booked day floors from now. Steps without a target (`scheduling`, `publish_check`) are not folded — they live inside the lead. `projected_ready = finish_last`.
5. Verdict: `on_track` (projected ≤ required-ready), `at_risk` (≤ publish_at), `late` (> publish_at); `unscheduled` when `publish_at` is NULL (organic with no `planned_at`; paid with no slot).
6. Stated limitation: no speculative extra rounds. The forecast assumes the current round completes; each remaining review is counted once. A future send-back extends the chain when it happens (the new open task becomes current).

*Terminal (C, production complete) — reached only through the completion test above; never falls back to on_track:*
- Organic: cancelled-only → excluded. All members `published_at IS NOT NULL` (or `status='published'`) → `published`. Any `bundle_error` → `late` (`publish failed`). `publish_at` NULL → `unscheduled`. `publish_at ≥ now` → `on_track`, or `at_risk` when `now > required_ready_at` and the member is still `planned` (not handed off). `publish_at < now` and not published → `late` (`publish time passed`). Live check: the 69 production-complete posts with a future `planned_at` read `on_track`; the 8 completed drafts with no `planned_at` read `unscheduled`, not `late`.
- Paid: ad = `mos_execution_ads WHERE content_id = subject AND archived_at IS NULL` (latest). `activated_at IS NOT NULL OR auto_ad.ad_status = 'ACTIVE'` → `active`. `platform_ad_id` set and `now < publish_at` → `on_track` (built, awaiting the tick). `now < required_ready_at` → `on_track`; `now < publish_at` → `at_risk` (`ad not built`); else `late` (`activation day passed`). No slot → `unscheduled`. Live: 9 ads with `ad_status='ACTIVE'` read `active`; 31 built-paused read `on_track` until their day ends.

*Recompute points:* every handoff, every block/unblock, and **every 10-minute sweep over not-started subjects with live reservations inside the Band C horizon [v5], in-flight subjects, AND terminal-but-unpublished subjects** (no open task, not published/active, not cancelled). Cache on the task/subject: `risk text`, `risk_reason text`, `risk_at timestamptz` (v3's boolean `at_risk` column is replaced — a boolean cannot carry the seven verdicts). `mos_plan_repair` stops writing risk.

**3b. The single accounting rule (unchanged).** A unit is counted by exactly one ledger arm at every moment: reservation arm while `reserved`/`stale`/`bound` (planned assignee, planned day); task arm once assigned (`consumed`); nobody once done. Early start keeps the cell on the planned day. Conformance assertion: no `consumed` reservation behind an open unassigned task.

**3c. [v4] Two live sets — a hard rule.** The **ledger/guard set** is {reserved, stale, bound} (consumed is counted through its task). The **uniqueness set** (§6b) is {reserved, stale, bound, consumed}. They differ on purpose: a consumed reservation on a plan-stable subject (row, virtual creative) must still occupy the subject+step slot, or a re-plan inserts a fresh `reserved` beside it and the unit is counted twice (once via the task, once via the new reservation). Do not "align" the index to the existing `ix_mos_task_res_*` convention.

## 4. Visibility, optional early work, ordering

**CONFIRMED.** Three bands; offering adds no mandatory workload and no countdown; the early batch is the whole ready batch of ONE future planned day chosen once per refill; blocked work on the earliest future day must not hide later executable reservation-only work; starting early keeps the planned deadline.

**4a. Bands (unchanged partition, column-only predicates):** A «مطلوب الآن» = open, `assignee = me`. B «متاح للبدء مبكرًا» = open, `assignee NULL`, `offered_to = me`, `due_at NULL`. C «قادم حسب الخطة» = (open, my role, `assignee NULL`, `offered_to NULL`) ∪ (reservation `reserved`, `assignee = me`, no task), horizon = the one Band C setting (14 days). `waiting_reason` is NOT part of any band predicate and refill never writes `'offered'` into it. Band C source is `mos_planned_steps(user, horizon)` (definer read).

**4b. [v4] Readiness — one closed vocabulary.** `mos_step_readiness(item)` returns exactly one of: `blocked`, `inactive`, `awaiting:<pred_step_key>`, `reserved_future`, `ready`.
- For an open unassigned task: `blocked` if `blocked`; `inactive` if the subject is archived; else `reserved_future` if `scheduled_start > today`, else `ready`. (A task exists only because the engine opened it after its predecessor; a revision that reopens a predecessor CLOSES the subject's open task — one-open index — so a stale successor never survives as an open task.)
- For a reservation-only item: `inactive` if the subject is archived; `awaiting:<pred>` unless it is the subject's FIRST pinned step and the subject has no task yet (later steps are opened by the engine, never by refill); else `reserved_future` / `ready` by day.
- `mos_item_executable(item) := readiness IN ('ready','reserved_future')` — a positive test. A CI assertion enumerates the vocabulary so a new token can never read as executable by omission.

**4c. [v4] Offer eligibility predicate** (an open task with `offered_to = P` is a valid Band B offer iff all hold):
e1 open, `assignee NULL`, `offered_to = P`; e2 subject active; e3 its reservation is `bound` to this task (`consumed_task_id = task AND status='bound'` — a coexisting `superseded` row from a re-plan does not disturb it); e4 executable (4b); e5 `scheduled_start > today`; e6 P ∈ `mos_role_routine_holders(role)` (`h(uid)` alias — the function returns `SETOF uuid`) and not on leave over the day; e7 the offered day is P's earliest executable future day: no bound-unassigned task of P's and no first-step reservation assigned to P with an executable item on a day strictly between today and the offered day (both item kinds, same horizon setting); e8 P is idle for the capacity key (no open, non-blocked ASSIGNED task of that key; review tasks do not count).

**4d. [v5] Refill, under the lock, scoped to `p_roles` (NULL = all). Assignments first, reconciliation after them, offers last** — a person's idle state is only known once every assignment of the pass has landed:
0. Release strays; open due subjects and refresh-cycle shells (`mos_task_open`).
1. Mandatory: open tasks, dependencies met (`ready`), planned day ≤ today → `mos_task_assign_apply`, ordered by 4e. An OFFERED task whose day arrived is simply a mandatory candidate here; apply clears `offered_to` (conversion, never withdrawal). Planned work is not capacity-gated; the plan and the commit guard are the cap.
2. Unplanned work (revisions, legacy, scheduling, publish_check): open-units rule against `daily_limit`; `mos_capacity_used` survives only here.

## 5. Completion is exactly-once, and so are its side effects

**CONFIRMED.** Bind completion to the expected task or a unique event id validated under the lock; retries and concurrent duplicates cannot complete the successor, advance twice, or duplicate assignments.

**5a. [v4] Event identity = (actor, operation, task, request hash).** `mos_completion_events(event_id PK, operation, task_id NULL for revise, subject_table, subject_id, actor_user_id, request_hash, request_snapshot jsonb, outcome jsonb, side_effects jsonb, created_at)`; partial index on pending effects. `request_hash` = sha256 of canonical JSON of **client-sent fields only**, computed server-side: `content.complete` {op, subject, task_id, result, note, targets sorted, `ad_set_id` exactly as the SPA sent it (or null)}; `row.complete` {…, return_to}; `content.revise` {op, subject_id, scope sorted, note}; `task.transfer` {op, task_id, to_user_id}. **Never** the server-derived `finish` flag or the RESOLVED Meta target: those exist only on the fresh path (resolution is skipped when the task is closed), so hashing them turns every legitimate paid-approval retry into a 409 — the exact launch-day path this exists to protect.

**5b. [v4] Replay rule (RPC, first thing after `mos_ledger_lock`).** Event not found → new. Found → (a) `actor_user_id IS DISTINCT FROM caller` → `MOS:EVENT_OWNER_MISMATCH` (`insufficient_privilege`, 403; checked first so a foreign actor learns nothing); (b) `operation <> p_operation OR task_id IS DISTINCT FROM p_task_id OR request_hash <> p_request_hash` (revise: task excluded, subject inside the hash) → `MOS:EVENT_MISMATCH` (**WS409**, 409); (c) match → stored outcome `|| {replayed:true}`, no writes of any kind.

**5c. [v4] Immutable evidence.** The `submitted` snapshot (`mos_content_versions` upsert on `(content_id, round)`) and the `changes_requested` `rejected_note` write move OUT of the API and INTO `workflow_advance_role_path`, executed after the replay-return and after the `TASK_ALREADY_CLOSED` check, keyed on the LOCKED task's round, before the transition. The API captures the payload (`content.data` + scenes; rows: one element per member) only on a precheck miss and passes `p_submission_snapshot`. Consequences: a replay never writes; a new-event retry on a closed task is refused before any write; a genuinely new event on a still-open round overwrites that round's snapshot once (the intended "resubmit overwrites its own snapshot", now scoped to new events). The snapshot is written at most ONCE per event (the replay-return precedes it; the concurrency note in the resolution overstated "twice"). Note: the write now runs under SECURITY DEFINER instead of the user's RLS client — acceptable behind the task lock and the auth gate, recorded here.

**5d. API order (both completion paths, plus revise and transfer).** Resolve the task by id without a status gate (404 if absent; the content path's 404-on-closed becomes the row path's 409). Cheap precheck `SELECT 1 FROM mos_completion_events WHERE event_id = X`: found → skip snapshot capture AND skip Meta target resolution → RPC (returns stored outcome or raises) → run pending effects → return. Miss → if approved on an `auto_meta_ad` step, resolve the target (a `choose` still returns 409 with no change) → capture snapshot if submitted → RPC with `p_task_id, p_event_id, p_operation, p_request_hash, p_request_snapshot, p_meta_target, p_submission_snapshot` → effect runner → return (`replayed` flag carried). `content_revise` gains `mos_ledger_lock` + the bind (a replay today opens a second revision round because `v_round = max(round)+1` defeats its reuse guard); `workflow_role_task_transfer` gains the bind and skips the note append on replay. The RPC has exactly two completion callers (`:2499`, `:5763`) plus revise (`content.ts:310`) and transfer (`:2741`); the SPA mints one event id per user action for all four.

**5e. [v4] Side-effects manifest and runner.** The RPC records, in the event row, one element per effect: `promote_asset`, `meta_ad` (with the SNAPSHOTTED target {execution_id, ad_set_id, platform_adset_id, ad_set_name, ad_row_id} and `job_id = mos_meta_job_id(event_id)`), `notify` per intended recipient set. Each element is `pending` → `done` only after its **success predicate** holds, `failed` only on a permanent error (recovery does not retry `failed`; transient errors keep `pending` with `last_error` and an attempt count, parked as `failed` + alert after ~6). Predicates: `meta_ad` → the enqueue RPC returned no `.error` (every `reason` it returns — `enqueued`, `replay`, `built`, `in_progress`, `wrong_state` — is a confirmed outcome recorded on the element; only an error keeps it `pending`); `notify` → `emitNotify` returned `true` (**it changes from `Promise<void>` to a boolean**; a dedupe no-op counts as success); `promote_asset` → `.error IS NULL`. Every `sb.rpc()`/insert result is checked for `.error` — Supabase returns it without throwing. The flip goes through `mos_completion_effect_done`; if the flip itself errors, log loudly and leave `pending`. Recovery: a TS cron re-runs `pending` elements older than 2 minutes through the same runner (cadence = decision 5; a dedicated 1–2-minute cron is recommended over the 10-minute sweep on launch days). A replay also runs pending effects synchronously.

**5f. [v4] Meta enqueue is atomic: `mos_meta_ad_enqueue(p_job_id, p_ad_row_id, …)`.** One SECURITY DEFINER transaction: (i) ad row: use the placeholder id, else a deterministic `mos_meta_ad_row_id(event)` with `INSERT … ON CONFLICT (id) DO NOTHING`; (ii) read the row `FOR UPDATE`; (iii) **replay check first [v5]**: if a `generation_jobs` row with `id = p_job_id` already exists, this call replays an enqueue that already happened → touch nothing, return `{enqueued:false, reason:'replay', job_id, ad_state}`; (iv) **phase-aware transition guard [v5]** — a NEW job id is a new intent, and the guard asks whether the ad is in the state this phase starts from: `platform_ad_id IS NULL` AND no live job (`queued`/`running`) is referenced by `auto_ad.job_id` AND `COALESCE(auto_ad.state,'') ∈ allowed_from(p_phase)`, where `allowed_from('caption') = {'', 'failed'}` and `allowed_from('create') = {'caption_review', 'failed'}`; fail → insert nothing, return `{enqueued:false, reason:'built'|'in_progress'|'wrong_state:<state>'}`, and the manifest element is `done` with that outcome (the ad is past this phase or another path owns it — not a failure); (v) pass → `INSERT generation_jobs (id = p_job_id, params.phase = p_phase) ON CONFLICT (id) DO NOTHING; v_inserted := FOUND` (not `GET DIAGNOSTICS` into a boolean — that does not compile), then reset the row (`status='waiting'`, `auto_ad` merged to `{state:'queued', phase, job_id, queued_at, error:null}`); (vi) return `{enqueued, job_id, ad_row_id, ad_state}`. Job-newness alone was refuted as the guard: a manual retry can build the ad under a different job before recovery runs; the state guard is what protects a live ad. v4's single "resettable" set listed `caption_review` as non-resettable and would have turned every FIRST caption approval into a no-op; the guard is now keyed on the phase being started: caption approval starts `create` FROM `caption_review`, its replay is caught by (iii) because its own job id already exists, and a completion-event recovery landing on a row already in `caption_review` is refused by `allowed_from('caption')`. The worker's `platform_ad_id` guard stays as defence in depth.
- **Per-path ids and phases (all four callers go through the RPC):** completion approval → phase `caption`, job `mos_meta_job_id(event_id)`; caption approval → phase `create`, job `mos_meta_job_id(caption_event_id)` (a different event, so a different id); `meta_auto_ad_retry` → a fresh id at the failed phase (admitted from `failed`); `meta_push_structure` → deterministic per `(event_id, ad_row_id)`, phase per row, so a replayed bulk push dedupes per ad. `enqueueMetaAdJob` becomes a thin wrapper; its random-id path is retired.
- Deterministic ids use built-in `md5('meta-ad:'||event_id)::uuid` (no `uuid-ossp`; `uuid_generate_v5` lives in `extensions` and is absent from the CI fixture).
- **`notify_emit` dedupe:** gains `p_dedupe_key` (default NULL, back-compatible); inside its per-recipient loop the key is `p_dedupe_key||':'||uid`; `INSERT … ON CONFLICT DO NOTHING RETURNING id`; when no id comes back, `CONTINUE` — skip `push_outbox` and `notification_deliveries` (else a NULL `notification_id` FK violation and a duplicate push). Unique partial index on `notifications.dedupe_key`.

**Expected results:** same event id, concurrent → both succeed, one transition, effects once; same event, different task or decision → 409 mismatch, nothing changes; foreign actor → 403, nothing revealed; lost response + retry on a pure-paid approval → same success (hash reproducible); crash between commit and enqueue → recovery enqueues exactly one job; manual retry built the ad, then recovery runs → the created ad is untouched, no false `failed`, no reopened caption task; replayed revise → no second round; replayed transfer → one note line; a swallowed notify error → element stays `pending`, recovery completes it once.

## 6. Commit: retire, carry forward, guard once, insert

**6a. [v4] One phased transaction — `mos_campaign_plan_commit_month(p_plans, p_expected_hash, p_actor)`.**
